## 一、定位

平台统一的通知/消息子系统：把各业务域的**领域事件**转成"人可读的提醒"，多渠道投递，用户自选渠道。

一条总规则贯穿全系统：

> **通知一律投递给「个人账号」，接收渠道设置也一律在「个人账号级」；商户不设统一的接收开关。**
> 站内信是**兜底通道，恒发不可关**；短信/微信/邮件为补充通道，按**各接收人自己**的偏好 + 网关就绪双重门控。

---

## 二、模型

### 2.1 实体

`Notification`（表 `Notifications`）：**定向 1 对 1 写扩散**——每个收件人一行。字段：`UserId` / `Type` / `Title` / `Body` / `BizType` / `BizId` / `IsRead` / `ReadAt`。

### 2.2 常量

- **通知类型 `Notification.Type*`**（前端按类型映射图标）：`merchant_approved` / `merchant_rejected` / `nomination_received` / `nomination_accepted` / `staff_join_invited` / `staff_join_accepted` / `correction_processed` / `merchant_closed` / `merchant_grade` / `sourcing` / `gift_shipped` / `gift_refunded` / `gift_order` / `gift_settlement` / `system`。
  - `merchant_grade`（v2.19.0）：牌级有效期到期前 7 天，由 `MerchantGradeSweepJob` 发给商户全部在职成员，BizType=`merchant`；每日巡检仅命中"剩余天数落在 (6,7]"一天，不会连续重复打扰。
- **业务对象 `Notification.Biz*`**（前端据此跳转）：`merchant` / `nomination` / `correction` / `mall_order` / `sourcing_demand`。

### 2.3 事件驱动

业务命令在自己的事务内发布领域事件；订阅者在**命令事务提交后**（`UnitOfWorkBehavior` 之后）写库并独立 `SaveChanges`。通知写失败**不回滚**已成功的业务命令（best-effort）。

**事件携带最终收件人集合（v1.1.0 定案）**：涉及"谁该收"由业务规则决定的场景，命令处理器在**发布事件前解析一次**收件人集合并随事件携带（如 `SourcingDemandPublishedEvent.RecipientMerchantIds`），订阅者只按集合逐户推送、**不再自行匹配**。理由：任何"处理器算一遍、订阅者再算一遍"的写法都会在规则演进时漂移（回传家数与实际推送对象不一致），单一事实源（`SourcingMatcher`）只被调用一次即可对齐两者。

## 三、渠道

| 通道 | 语义 | 门控 |
|---|---|---|
| 站内信 | **兜底通道，恒发** | 无（不可关）；消息中心 + 未读角标 |
| 短信 | 补充通道（预留） | 用户偏好 `SmsNotificationEnabled` + 网关 `Sms:Enabled` |
| 微信 | 补充通道（预留） | 用户偏好 `WeChatNotificationEnabled` + 网关 `WeChat:Enabled` |
| 邮件 | 补充通道（预留） | 用户偏好 `EmailNotificationEnabled` + 网关 `Email:Enabled` |

- **同时多方式发出**：一次事件按偏好**扇出到全部启用通道**（`INotificationService.AddInAppAsync` + `AddExternalAsync`）。
- 未配置网关的通道**只记日志不外发**——"接上网关即生效"，无需改调用方。

## 四、通知设置（个人账户级）

- 存储：`UserPreferences`（键 `UserId`）——`SmsNotificationEnabled` / `WeChatNotificationEnabled` / `EmailNotificationEnabled`（默认：短信关、微信开、邮件开）。
- 端点：`GET/PUT /api/notifications/preferences`（BFF `/mobile/notifications/preferences`）。**站内信不在此接口范围**（恒开）。
- 前端：Taro「我的 → 设置 → 通知设置」（`pages/my/notification-settings`）——站内信展示为恒开不可点；短信**仅网关就绪时显示**（避免"勾了收不到"）；微信/邮件可勾。
- 不设商户级开关：通知投递对象本就是个人账号，"谁开谁收"各自生效。

## 五、分发矩阵（谁收 / 在哪设）

| 触发 | 通知谁 | 落地账号 | 渠道按谁 |
|---|---|---|---|
| 发布寻货（公开） | 有货（在售本轴承）的认证商家在职**管理员** | 各管理员账号 | 各自 |
| 发布寻货（邀请） | **勾选的**（空=全部匹配）认证在售商家在职**管理员**；**豁免日限频** | 各管理员账号 | 各自 |
| 邀请单转为公开 | 不发新通知（收件人集合不变，仅曝光面放开） | — | — |
| 商家应答（**商户名义发布**） | 发布商户**全部在职成员** | 各成员账号 | **各自** |
| 商家应答（个人名义发布） | 发布人本人 | 发布人账号 | 发布人 |
| 发布人选定 | 被选 + 落选商户**管理员** | 各自 | 各自 |
| 发布人取消 | 已应答商户**管理员** | 各自 | 各自 |
| 平台下架寻货 | 发布人本人 | 发布人账号 | 发布人 |

> "全店在职成员"意味着该商户**全部成员**的站内信都会收到；外部渠道按各人设置。
> 商户名义发布时"接单不漏人"——应答不再只通知经办人。

### 5.1 限频规则（v1.2.0）

- **公开**：按 `Sourcing.NotifyMaxPerMerchantPerDay`（默认 3，同型号/人/日）限频，超出跳过——匹配面广，需抑制刷屏。
- **邀请**：**豁免限频**（站内信必发）。理由：受邀是发布人点名勾选的定向邀约（受众可控、非流量噪声），限频会让"受邀必达"落空；与"邀请单必须进收件商家「为你匹配」聚合面"共同构成双保险。
- 判定基于事件的 `Visibility`（公开/邀请），不按收件人当前是否仍有货——后者会让受邀商家事后下架就被拒。

## 六、通知清单（按业务域）

| 类型 | 触发 | 收件人 |
|---|---|---|
| merchant_approved / merchant_rejected | 入驻审核通过/拒绝 | 申请人 / 发起人 |

## 八、预留与不再做

- **预留**：短信/微信/邮件真实网关接入（`ISmsSender` 等，同 `SmsCodeService` 的 DevMode 范式）；微信订阅消息 / JSSDK；按"通知类别"的细分订阅（当前仅渠道级，站内信恒开）。
- **不再做**：商户级统一接收开关；站内信可关闭。

## 五之补、转为公开的差集补发（v1.3.0）

发布人把**进行中**的邀请单放开为公开时（`publish-public`）：

| 项 | 规则 |
|---|---|
| 收件人 | `当前匹配集合（SourcingMatcher，排除发布商户） − 原 InvitedMerchantIds`（差集） |
| 投递 | 差集非空 → 发布 `SourcingDemandPublishedEvent`（`Visibility=Public`、收件人=差集），走**公开单规则**（含 `Sourcing.NotifyMaxPerMerchantPerDay` 限频） |
| 差集为空 | 一条不发（原邀请为"全选"时关系放开后无新人可触达） |
| 原收件人 | **绝不二次打扰**（已收过邀请通知）——"该通知，但只发一次" |
| 幂等 | 已是公开单或已终态一律拒绝放开，故补发在单生命周期内**最多发生一次** |

> 实现要点：`SourcingDemandPublishedEvent` 本就携带"最终收件人集合"（见 2.3），订阅者按集合投递、不自行匹配，因此差集补发只需构造集合即可复用同一条订阅链。
> 配套：《寻货功能设计 v1.8.2》7.2、《API 端点说明 v1.56.0》本版增量。
