## 1. 核心概念

### 1.1 两种数据来源，共存方案

| 来源 | 含义 | 管理方 | 可信度 |
|------|------|--------|--------|
| 爬虫（Crawler） | ETL 从 CBIA 等互联网站点抓取 | Sync 服务自动维护 | 低，用于冷启动填充 |
| 商户自管（Manual） | 认证商户自行上传/维护 | 商户管理员/员工 | 高，商户自行负责 |

**原则：** 爬虫数据作为基础填充。商户认证后，L 阶段在写入 MerchantBearing 前检查商户 `IsVerified=true`，已认证商户的关联数据直接被跳过（不创建也不更新）。爬虫数据中已认证商户未触碰的轴承记录继续保留，显示"信息来源于互联网"。商户上传同款轴承时通过 `DataSourceType=Manual` 与爬虫记录区分。

### 1.2 三种用户类型

| 类型 | 认证方式 | 入口 | 职能 |
|------|----------|------|------|
| 普通用户 | 手机号 + 短信验证码 | Mobile APP | 搜索轴承、浏览商户、关注收藏 |
| 商户管理员 | 普通用户 -> 申请入驻 -> 审核通过 | Mobile APP + Admin | 管理店铺、维护库存、邀请员工 |
| 商户员工 | 被管理员邀请 -> 注册/确认 | Mobile APP | 协助维护库存 |

## 2. 业务流程图

### 2.1 全链路

```
                        普通用户注册（手机号 + 验证码）
                                    |
                           ↓ 想卖货了 ↓
                          申请入驻
                      /               \
                 认领爬虫商户         新建商户
                 （自动填充信息）     （全部手工填写）
                      \               /
                          上传营业执照
                          提交申请
                              |
                          等待审核（PendingReview）
                              |
                     ┌────────┴────────┐
                     ▼                 ▼
              审核通过              审核拒绝
              Merchant.Verify()     已拒绝状态
              标记已认证            可重新申请
              商户管理员可登录
                     |
              ┌──────┴──────┐
              ▼             ▼
        维护库存         邀请员工
        增加/删除/批量   手机号 -> 邀请码
        上架/下架          -> 员工注册/确认
```

**审核通过时的操作：**

1. `Merchant.Verify(verifiedBy)` —— 标记已认证，记录审核人
2. 用户关联：`Merchant.AddStaff(user)`
3. Sync L 阶段自动跳过该商户的 MerchantBearing

## 4. 商户入驻体系

### 4.1 入驻申请（API 项目）

`POST /api/merchant/apply`

**请求参数：**

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `claimMerchantId` | Guid? | 否 | 认领已有商户 ID，不填则为新建 |
| `name` | string | 认领时否，新建时是 | 商户名称 |
| `contactPerson` | string | 否 | 联系人 |
| `phone` | string | 否 | 联系电话 |
| `address` | string | 否 | 地址 |
| `businessLicenseImage` | string | 是 | 营业执照图片（base64 或文件上传 URL） |

**认领 vs 新建：**

| 方式 | 操作 |
|------|------|
| 认领 | MAUI 搜索爬虫商户名 -> 选中 -> 自动填充名称/地址/联系人 -> 用户确认补充 -> 提交 |
| 新建 | 全部由用户填写 -> 提交 |

**状态机：**

```
Draft（编辑中，未提交）
  -> PendingReview（已提交，等待审核）
    -> Verified（审核通过，成为认证商户）
    -> Rejected（审核拒绝，附拒绝原因，可重新提交申请）
```

### 4.2 审核管理（Admin 项目）

Admin 审核页功能：

| 功能 | 说明 |
|------|------|
| 待审核列表 | 按提交时间排序，显示商户名+申请人+提交时间 |
| 详情查看 | 商户信息 + 营业执照图片预览 |
| 审核通过 | 调用 `POST /api/admin/merchants/{id}/verify` |
| 审核拒绝 | 调用 `POST /api/admin/merchants/{id}/reject`，附带原因 |
| 历史记录 | 显示该商户的审核流水 |

### 4.3 已认证商户数据保护

审核通过后不删除已有 MerchantBearing 数据。后续 Sync L 阶段 `LoadRelationsAsync` 在发送请求前检查目标商户是否已认证：

```
LoadRelationsAsync 每批：
  ├── 收集本批所有唯一 MerchantId
  ├── POST /api/merchants/batch-check-verified  → 返回已认证商户 ID 列表
  └── 已认证商户的关联记录 → MarkAsSyncFailed("商户已入驻，跳过爬虫关联数据")
      未认证商户的关联记录 → 正常同步（DataSourceType = Crawler）
```

## 6. 商户库存管理

### 6.1 MerchantBearing 现有字段

`MerchantBearing` 实体已有丰富的生命周期管理模型，不重新设计，直接复用：

| 字段 | 类型 | 说明 |
|------|------|------|
| `MerchantId` | Guid | 商户ID |
| `BearingId` | Guid | 轴承ID |
| `PriceDescription` | string? | 价格描述（"55-60元"、"电议"） |
| `NumericPrice` | decimal? | 数值化价格（用于排序筛选） |
| `PriceVisibility` | enum | Public / LoginRequired |
| `StockDescription` | string? | 库存描述（"现货"、"期货"） |
| `MinOrderDescription` | string? | 起订量描述 |
| `Remarks` | string? | 商家备注 |
| `IsOnSale` | bool | 是否在售（商户控制上架/下架） |
| `IsPendingApproval` | bool | 是否需要管理员审核 |
| `IsFeatured` | bool | 是否推荐 |
| `ViewCount` | int | 浏览次数 |

### 6.2 MerchantBearing 新增字段

| 字段 | 类型 | 说明 |
|------|------|------|
| `DataSourceType` | 枚举（Crawler / Manual） | 区分爬虫数据和商户自管数据 |

`MerchantBearingConfiguration` 中使用简单枚举映射（非 `OwnsOne`），因为仅需要一个枚举字段，不需要完整的 Value Object。

### 6.3 爬虫库存标记

Sync L 阶段创建 MerchantBearing 时需要标记 `DataSourceType = Crawler`。涉及位置：

| 位置 | 改动 |
|------|------|
| `BatchCreateMerchantBearingsCommandHandler.cs` | 创建时 `DataSourceType = Crawler` |

商户自管库存通过 `MerchantEndpoints` 创建时默认 `DataSourceType = Manual`。

### 6.4 爬虫库存 vs 商户库存搜索

```
用户搜索轴承 -> 返回结果
  ├─ 认证商户的 MerchantBearing（Source = Manual） -> 优先展示
  └─ 非认证商户的 MerchantBearing（Source = Crawler） -> 标注"信息来源于互联网"展示
```

已认证商户的爬虫 MerchantBearing 在 L 阶段被跳过写入，所以搜索结果中认证商户仅展示自管数据。认证商户入驻前存在的 Crawler 记录继续保持（已被标记为 Crawler，不受 L 阶段影响）。

### 6.5 API 端点

| 端点 | 说明 | 认证 |
|------|------|------|
| `POST /api/merchants/batch-check-verified` | 批量查询商户是否已认证 | Bearer（SyncClient） |
| `GET /api/merchant/bearings` | 查看自己库存 | Bearer（商户管理员/员工） |
| `POST /api/merchant/bearings` | 添加在售轴承（单条） | Bearer（商户管理员/员工） |
| `DELETE /api/merchant/bearings/{id}` | 下架 | Bearer（商户管理员/员工） |
| `POST /api/merchant/bearings/batch` | Excel 批量导入 | Bearer（商户管理员） |

## 8. 已确认的设计决策

### 8.1 ETL 与商户认证的交互策略

**决策：** 采用方案 A（L 阶段跳过认证商户）。

**理由：** 认证商户数据由商户自管，Sync 不再维护其库存数据。

**实现方式：** `LoadRelationsAsync` 每次处理前调用 `POST /api/merchants/batch-check-verified` 获取已认证商户列表。

### 8.2 其他讨论（同 v1.0.0）

- 商户认领冲突：一个爬虫商户只能被一个申请认领
- 验证码有效期：5分钟，发送间隔60秒，日上限10次，开发环境固定 123456
- 营业执照图片：开发环境存 base64，生产环境使用 OSS
- 商户员工角色：管理员可管理全部，员工仅库存 CRUD
- MAUI 极简版：5 个页面按 Step 顺序实现

## 9. 实施顺序

| Step | 内容 | 涉及项目 | 后端 | MAUI 页面 |
|------|------|----------|------|-----------|
| 1 | SMS 授权流程 | Identity | send-code + grant_type=sms + signup | 注册/登录页 |
| 2 | 商户入驻 | API + Identity | apply + 认领 + 新建 | 入驻申请页 + 状态页 |
| 3 | Admin 审核页 | Admin | reject + license preview + search | 无 |
| 4 | 员工邀请 | API + Identity | invite + invite_code 消费 | 员工邀请页 |
| 5 | 库存管理 + 爬虫数据保护 | API + Sync | bearing CRUD + DataSource 标记 + 认证商户跳过 | 库存管理页 |
| 6 | ETL 重跑验证 | Sync | 确认爬虫数据不再同步给已认证商户 | 无 |
