## 1. 核心概念

### 1.1 两种数据来源，共存方案

| 来源 | 含义 | 管理方 | 可信度 |
|------|------|--------|--------|
| 爬虫（Crawler） | ETL 从 CBIA 等互联网站点抓取 | Sync 服务自动维护 | 低，用于冷启动填充 |
| 商户自管（Manual） | 认证商户自行上传/维护 | 商户管理员/员工 | 高，商户自行负责 |

**原则：** 爬虫数据作为基础填充，与商户自管数据通过 `DataSourceType` 字段共存。商户认证审核通过时不再清除爬虫数据，数据保留在库中。公共端点 `GET /api/merchants/{id}/bearings` 默认按 Manual 优先展示（可通过 `dataSource` 参数切换），Admin 页面提供"同步数据"弹窗查看爬虫来源记录。Sync L 阶段全量导入所有 MerchantBearing（不跳过已认证商户），`DataSource` 字段显式传入 `"cbia"`。

**覆盖保护：** 任何实体被人工维护过（DataSource 非 Crawler）后，爬虫不得覆盖（约束同时应用于 Bearing/Brand/BearingType/Merchant/MerchantBearing 的 Sync 批量写入路径）。

### 1.2 三种用户类型

| 类型 | 认证方式 | 入口 | 职能 |
|------|----------|------|------|
| 普通用户 | 手机号 + 短信验证码 | Mobile APP | 搜索轴承、浏览商户、关注收藏 |
| 商户管理员 | 普通用户 -> 申请入驻 -> 审核通过 | Mobile APP + Admin | 管理店铺、维护库存、邀请员工 |
| 商户员工 | 被管理员邀请 -> 注册/确认 | Mobile APP | 协助维护库存 |

### 1.3 商户成员模型（一人多商户）

- 成员关系存 `MerchantMember` 表（(UserId, MerchantId) 唯一约束），取代 `User.MerchantId` 单值列的"一人一商户"硬约束。
- 商户域角色（MerchantAdmin / MerchantStaff）存于成员行；平台级角色（Individual/Admin/SuperAdmin）仍走全局 RBAC。
- 成员状态机：Active（在职）/ Removed（已移除，可被重新邀请复用 Removed 行）/ Suspended（停用，保留关系但无操作权限，可恢复）。
- 一个商户须始终保持 >= 1 个 Active MerchantAdmin；移除/停用最后一个管理员时拦截（守卫与移除能力同批交付）。

## 2. 业务流程图

### 2.1 全链路

```
                        普通用户注册（手机号 + 验证码）
                                    |
                           ↓ 想卖货了 ↓
                          商户入驻（三种模式见 4.1）
                      /         |          \
                  模式A 自助   模式B 提名    模式C 认领
                 (self 新建)  (此他人当   (claim 认领
                             管理员)     爬虫商户)
                      \         |          /
                          上传/补全资料
                              |
                   ┌──────────┴──────────┐
                   │   等待审核(Pending)    │
                   └──────────┬──────────┘
                      ┌───────┴───────┐
                      ▼               ▼
               审核通过(approve)     审核拒绝(reject)
              Pending->Active       Suspended + 原因
              (可选 verify 认证)      可重新申请
                     |
         ┌───────────┴────────────┐
         ▼                        ▼
   商户管理员可登录              成员行按模式生成
   （发起人=Admin / 被提名人=Admin/
     发起人=Staff(可选) / 认领人=Admin）
```

**审核通过时的操作（ApproveMerchantCommandHandler）：**

1. `Merchant.Approve()` —— Pending → Active，商户生效（补齐原缺失的审核门）
2. 提名模式商户：建被提名人 MerchantAdmin 成员行 + 发起人 MerchantStaff 成员行（InitiatorJoins=true 时）
3. 爬虫数据保留在库中（与 v1.3.0 一致），不因审核清除

**认证（verify）与审核（approve）分离：**
- `approve` 决定商户是否生效（Pending→Active），是 C 端可见的前提
- `verify` 仅标记认证等级（IsVerified/Grade），不再清除爬虫数据

## 3. 身份认证体系

- 认证事实源在 Identity（手机号/微信 OpenId/密码），业务事实源在 API，单向同步。
- 业务鉴权不信 JWT role claim：**MerchantAdmin/MerchantStaff 一律查 API 自己的成员表动态判定**（详见 7.2）。
- 一人多商户：请求头 `X-Merchant-Id` 指定当前操作商户（缺省 = 首个在职成员商户），由 `UserContextMiddleware` 解析并校验"该用户是该商户的 Active 成员"后写入 `context.Items["CurrentMerchantId"]`。

## 4. 商户入驻体系

### 4.1 入驻申请（API 项目，`MerchantApplicationEndpoints`）

**端点：**

| 方法 | 路由 | 说明 |
|------|------|------|
| POST | `/api/merchant/apply` | 提交入驻申请（mode=self / claim） |
| GET | `/api/merchant/application` | 查询当前用户在各商户的入驻状态 |
| POST | `/api/merchant/nominate` | 提名他人为管理员（模式 B） |
| POST | `/api/merchant/nominate/{code}/accept` | 被提名人接受提名并补全资料 |
| GET | `/api/merchant/claimable` | 搜索可认领的爬虫来源商家 |
| GET | `/api/merchant/nominations/pending` | 按当前登录手机号查询待我接受的提名 |

组授权：`RequireAuthorization()`（任意已认证用户，非 Merchant 策略）。

**模式 A 自助当管理员（mode=self，默认）：**
登录用户填商户资料+资质 → 建 Pending 商户 + 发起人 MerchantAdmin 成员行 → Admin approve → 商户生效。

`POST /api/merchant/apply` 请求体字段：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `mode` | string | 否 | 默认 `self`；`claim` 为认领 |
| `claimMerchantId` | Guid? | claim 时是 | 认领的爬虫商家 ID |
| `name` | string | self 时是 | 商户名称 |
| `type` | int? | self 时是 | MerchantType 枚举值 |
| `contactPerson` / `phone` / `mobile` / `email` / `address` | string? | 否 | 联系方式 |
| `companyName` | string? | 否 | 公司全称 |
| `unifiedSocialCreditCode` | string? | 否 | 统一社会信用代码 |
| `description` | string? | 否 | 商家简介 |
| `licenseUrl` | string? | 否 | 营业执照图片 URL（可选，用于认证） |

**模式 B 提名他人当管理员（mode=nominate）：**
1. 发起人填被提名人手机号/邮箱 + 商户草稿信息 → 建 **Draft 商户** + 一条 `Type=Nomination, Role=MerchantAdmin` 的 StaffInvitation（发起人 `InitiatorJoins` 默认 true）。
2. 被提名人（注册/登录后）经 `/api/merchant/nominate/{code}/accept` 补全资料 → **Draft → Pending**。
   - 安全强化：被提名人手机号取自 JWT `phone_number` claim（不接收户参数），handler 校验与邀请手机号一致，防邀请码泄露被冒领。
   - 补资料为字段级合并（`??` 原值），未填字段不清空 Draft 阶段已填值。
3. Admin approve → 商户 Active，建双方成员行：被提名人 = MerchantAdmin，发起人 = MerchantStaff（InitiatorJoins=true 时）。
4. 拒绝/超时 → 提名 Status=Declined/Expired，Draft 商户失效。
5. 认证审查：被拒绝的爬虫商家再次被认领时，`ReopenForClaim()` 清除拒绝标记恢复为待审核。

**模式 C 认领存量商户（mode=claim）：**
- 场景：Sync 持续灌入爬虫商户，自助入驻只新建会与爬虫数据重复。
- 入口搜索：`GET /api/merchant/claimable?keyword=&page=&pageSize=`（返回未被认领的爬虫来源商家）。
- `POST /api/merchant/apply`（mode=claim, claimMerchantId）认领后申请人成为该商户 MerchantAdmin（审核通过后）。

**状态机：**

```
MerchantStatus.Draft（提名草稿，不可被C端检索/不被Sync合并；仅模式B）
  -> PendingReview（已提交，等待审核）
    -> Active（approve 审核通过，商户生效）
    -> Suspended（reject 审核拒绝，附原因，可重新申请）
```

### 4.2 审核管理（Admin 项目）

Admin 审核页功能：

| 功能 | 说明 |
|------|------|
| 待审核列表 | 按提交时间排序，显示商户名+申请人+提交时间 |
| 详情查看 | 商户信息 + 营业执照图片预览 |
| 审核通过 | 调用 `POST /api/admin/merchants/{id}/approve`（Pending→Active，商户生效） |
| 认证 | 调用 `POST /api/admin/merchants/{id}/verify`（仅标记认证等级，不再清除爬虫数据） |
| 审核拒绝 | 调用 `POST /api/admin/merchants/{id}/reject`，附带原因 |
| 历史记录 | 显示该商户的审核流水 |
| 同步数据 | 弹窗查看爬虫来源的 MerchantBearing 记录，支持"显示全部"切换 |
| 平台指定成员 | 调用 `POST /api/admin/merchants/{id}/members`（商户无在职管理员等异常时兜底指定/恢复成员） |

### 4.3 已认证商户数据保护

商户认证审核通过后，爬虫数据保留在库中，不再清除。公共端点默认展示 Manual 数据（商户自管），通过 `dataSource` 查询参数可切换到 Crawler 数据视图。Admin 审核页提供"同步数据"弹窗供运营人员查看爬虫来源记录。

**数据展示策略：**

```
GET /api/merchants/{id}/bearings?dataSource=Manual（默认，商户自管）
GET /api/merchants/{id}/bearings?dataSource=Crawler（爬虫数据）
GET /api/merchants/{id}/bearings?onlyOnSale=true（仅展示在售）
```

**Sync L 阶段导入策略：**

```
LoadRelationsAsync 每批：
  └── 全量发送到 API（不跳过已认证商户）
      └── DataSource = "cbia"，对应 MerchantBearing.DataSourceType = Crawler
```

## 5. 成员管理（商户团队）

### 5.1 商户管理员可用的成员操作（`MerchantEndpoints`，RequireAuthorization("Merchant")）

| 方法 | 路由 | 说明 |
|------|------|------|
| GET | `/api/merchant/staff` | 获取成员列表 |
| POST | `/api/merchant/staff` | 添加员工（AddStaffCommand） |
| DELETE | `/api/merchant/staff/{userId:guid}` | 移除员工 |
| POST | `/api/merchant/members/{userId:guid}/suspend` | 停用成员（离职/异常处置，可恢复） |
| POST | `/api/merchant/members/{userId:guid}/activate` | 恢复被停用成员 |
| PUT | `/api/merchant/members/{userId:guid}/role` | 变更成员角色（MerchantAdmin/MerchantStaff） |

- 以上操作均需 `permissionService.IsMerchantAdmin()`（按成员表 + 当前商户上下文判定，非 JWT role claim）。
- 移除/停用最后一个 Active 管理员时由仓库层守卫拦截（须先转让/指定新管理员）。

### 5.2 平台兜底（Admin）

`POST /api/admin/merchants/{id}/members`（RequirePermission("merchant.verify")）：商户无任何在职管理员等异常时，平台直接指定/恢复成员（已存在成员行则恢复/改角色，否则新建），避免"0 管理员"僵局。

### 6.3 DataSourceType 写入策略

### 6.4 库存操作端点（`MerchantEndpoints`）

| 方法 | 路由 | 管理员 | 员工 |
|------|------|--------|------|
| GET | `/api/merchant/bearings` | 可查看 | 可查看 |
| POST | `/api/merchant/bearings` | 可操作 | 可操作 |

| PUT | `/api/merchant/bearings/{id:guid}/price-visibility` | 可操作 | 可操作 |
| POST | `/api/merchant/bearings/{id:guid}/onshelf` | 可操作 | 可操作 |
| POST | `/api/merchant/bearings/{id:guid}/offshelf` | 可操作 | 可操作 |
| POST | `/api/merchant/inventory/import` | 可操作 | 拒绝 |

**Excel 批量导入库存（P7，SyncInventoryService）：**
- 端点 `POST /api/merchant/inventory/import`（仅商户管理员，`.DisableAntiforgery()`）。
- 流程：API 用 `sync-client` 客户端凭据换 `api:sync` token → 转发 Excel 到 Sync `POST /api/inventory/import?merchantId={id}` → Sync 完成 Excel 解析与型号解析 → 写库 `DataSourceType=Manual`（不被爬虫覆盖）。
- 配置项（appsettings.json `Sync` 节，ClientSecret 生产用 K8s Secret 覆盖）：

```json
"Sync": {
  "BaseUrl": "http://openfindbearings-sync:80",
  "ClientId": "sync-client",
  "ClientSecret": "REPLACE_ME",
  "Scope": "api:sync"
}
```

### 6.5 爬虫库存 vs 商户库存搜索

```
用户搜索轴承 -> 返回结果
  ├─ 认证商户的 MerchantBearing（Source = Manual） -> 优先展示
  └─ 非认证商户的 MerchantBearing（Source = Crawler） -> 标注"信息来源于互联网"展示
```

认证商户爬虫数据保留在库中，但公共端点默认仅展示 Manual 数据。通过 `dataSource=Crawler` 查询参数可查看爬虫数据。

| 端点 | 说明 | 认证 |
|------|------|------|
| `GET /api/merchants/{id}/bearings` | 查询商户轴承（支持 dataSource、onlyOnSale 参数） | 匿名 |

| L 阶段 `BatchCreateMerchantBearingsCommandHandler` | MerchantBearing 写入时 `DataSourceType = Crawler`，`DataSource = "cbia"` |
| 库存导入 | `POST /api/inventory/import`（Excel 解析能力被 API 的 SyncInventoryService 复用） |

## 8. 已确认的设计决策

### 8.1 ETL 与商户认证的交互策略

**决策：** 爬虫数据保留，通过 DataSourceType 字段区分，认证审核不再清除数据。

**理由：** 认证商户需要查看爬虫导入的初始库存数据作为参考。Admin 运营人员通过"同步数据"弹窗查看爬虫来源记录，便于数据核对。公共端点通过 `dataSource` 参数控制展示范围，Manual 数据优先。

**实现方式：**
1. 审核通过时不再调用 `DeleteByMerchantAndSourceAsync`，数据保留
2. L 阶段全量导入所有 MerchantBearing（不跳过已认证商户），`DataSource` 显式传入 `"cbia"`
3. `GET /api/merchants/{id}/bearings` 新增 `dataSource`（枚举：Manual/Crawler）和 `onlyOnSale`（bool）查询参数
4. Admin 审核页新增"同步数据"弹窗，支持"显示全部"切换

### 8.2 商户成员模型与审核门（v2.0.0 新增）

- **成员表取代单值列**：`MerchantMember` 是"谁属于哪个商户、什么角色"的唯一事实源；业务鉴权（IsMerchantAdmin/IsMerchantStaff）查成员表，不信 JWT role claim。
- **一人多商户**：请求带 `X-Merchant-Id`（缺省 = 首个在职成员商户），UserContextMiddleware 校验成员身份。
- **审核门**：全代码原先无处调 `Merchant.Approve()`（P3 修复前审批通过仍 Pending、C 端不可见）。现 `approve`（Pending→Active）与 `verify`（认证等级）分离。
- **多管理员 + 守卫**：商户须 >= 1 Active MerchantAdmin；移除能力与守卫同批交付；异常致 0 管理员时平台经 `POST /api/admin/merchants/{id}/members` 兜底。
- **提名入伙**：被提名人=MerchantAdmin、发起人=MerchantStaff（InitiatorJoins=true 时），审核通过时建成员行。

### 8.3 其他讨论（同 v1.0.0）

- 商户认领冲突：一个爬虫商户只能被一个申请认领
- 验证码有效期：5分钟，发送间隔60秒，日上限10次，开发环境固定 123456
- 营业执照图片：开发环境存 base64，生产环境使用 OSS
- 商户员工角色：管理员可管理全部，员工仅库存 CRUD
- MAUI 极简版：5 个页面按 Step 顺序实现
