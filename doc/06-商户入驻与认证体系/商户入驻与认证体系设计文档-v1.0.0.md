## 1. 核心概念

### 1.1 两种数据来源

| 来源 | 含义 | 管理方 | 可信度 |
|------|------|--------|--------|
| 爬虫（Crawler） | ETL 从 CBIA 等互联网站点抓取 | Sync 服务自动维护 | 低，用于冷启动填充 |
| 商户自管（Manual） | 认证商户自行上传/维护 | 商户管理员/员工 | 高，商户自行负责 |

**原则：** 爬虫数据只是"冷启动种子"。真实商户入驻认证后，爬虫库存清空，改为商户自管库存。无双源共存，无备选回退。

### 1.2 三种用户类型

| 类型 | 认证方式 | 入口 | 职能 |
|------|----------|------|------|
| 普通用户 | 手机号 + 短信验证码 | Mobile APP | 搜索轴承、浏览商户、关注收藏 |
| 商户管理员 | 普通用户 -> 申请入驻 -> 审核通过 | Mobile APP + Admin | 管理店铺、维护库存、邀请员工 |
| 商户员工 | 被管理员邀请 -> 注册/确认 | Mobile APP | 协助维护库存 |

## 2. 业务流程图

### 2.1 全链路

```
                        普通用户注册（手机号 + 验证码）
                                    |
                           ↓ 想卖货了 ↓
                          申请入驻
                      /               \
                 认领爬虫商户         新建商户
                 （自动填充信息）     （全部手工填写）
                      \               /
                          上传营业执照
                          提交申请
                              |
                          等待审核（PendingReview）
                              |
                     ┌────────┴────────┐
                     ▼                 ▼
              审核通过              审核拒绝
              Merchant.Verify()     已拒绝状态
              清空爬虫库存           可重新申请
              商户管理员可登录
                     |
              ┌──────┴──────┐
              ▼             ▼
        维护库存         邀请员工
       增加/删除/批量   手机号 -> 邀请码
                        -> 员工注册/确认
```

## 3. 身份认证体系

### 3.1 OpenIddict 自定义授权流程

在现有 OpenIddict 注册中启用以下 grant type：

| Grant Type | 用途 | 当前状态 |
|---|---|---|
| `authorization_code` | Admin 后台登录 | 已启用 |
| `client_credentials` | Sync M2M 通信 | 已启用 |
| `password` | 预留（密码登录） | 已启用但未开放 |
| `refresh_token` | Token 刷新 | 已启用 |
| **`sms`** | 手机号 + 短信验证码登录 | **本次新增** |
| `wechat` | 微信登录 | 预留（mock） |
| `alipay` | 支付宝登录 | 预留（mock） |

### 3.2 SMS 授权流程

```
Mobile APP                    Identity
    |                            |
    |--- POST /api/account/send-code --->|
    |                            | 生成6位验证码
    |                            | 存入 SmsVerificationCode 表
    |  <--- 返回 ok / 打印日志 ---|
    |                            |
    |--- POST /connect/token --->|
    |    grant_type=sms          |
    |    phone=138xxxx           |
    |    code=123456             |
    |                            | 校验验证码
    |                            | 查询/创建 OIDC 用户（phone 为 username）
    |                            | 标记验证码已使用
    |  <--- 返回 tokens ---------|
    |                            |
    |--- 后续请求带 Bearer token->|
```

**验证码表结构（SmsVerificationCode）：**

| 字段 | 类型 | 说明 |
|------|------|------|
| Id | Guid | PK |
| Phone | string(20) | 手机号 |
| Code | string(6) | 6位数字验证码 |
| ExpiresAt | DateTime | 过期时间（创建后5分钟） |
| IsUsed | bool | 是否已使用 |
| CreatedAt | DateTime | 创建时间 |

### 3.3 手机号注册

有两种设计路径：

**路径 A：扩展 SignUp（推荐）**

`POST /api/account/signup` 目前 `Password` 字段 `[Required]`，需要改为条件必填——当提供 `code`（短信验证码）时可以无密码注册；否则仍需要密码（保留邮箱/用户名注册能力）。

```json
// 以手机号 + 验证码注册（不需要密码）
{
  "account": "13800138000",
  "code": "123456",       // 验证码，code 与 password 二选一
  "realm": "openfindbearings"
}
```

**路径 B：独立手机号注册端点**

`POST /api/account/register-phone` 专门处理手机号+验证码注册，不修改原有 SignUp。

```
路径 A 修改一处，逻辑统一，但需要改 SignUpRequest 校验。
路径 B 隔离性更好，不破坏现有 SignUp 逻辑。
```

注册成功后返回 access_token + refresh_token，用户可直接开始使用，无需额外登录。

## 4. 商户入驻体系

### 4.1 入驻申请（API 项目）

`POST /api/merchant/apply`

**请求参数：**

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `claimMerchantId` | Guid? | 否 | 认领已有商户 ID，不填则为新建 |
| `name` | string | 认领时否，新建时是 | 商户名称 |
| `contactPerson` | string | 否 | 联系人 |
| `phone` | string | 否 | 联系电话 |
| `address` | string | 否 | 地址 |
| `businessLicenseImage` | string | 是 | 营业执照图片（base64 或文件上传 URL） |

**认领 vs 新建：**

| 方式 | 操作 |
|------|------|
| 认领 | MAUI 搜索爬虫商户名 -> 选中 -> 自动填充名称/地址/联系人 -> 用户确认补充 -> 提交 |
| 新建 | 全部由用户填写 -> 提交 |

**状态机：**

```
Draft（编辑中，未提交）
  -> PendingReview（已提交，等待审核）
    -> Verified（审核通过，成为认证商户）
    -> Rejected（审核拒绝，附拒绝原因，可重新提交申请）
```

### 4.2 审核管理（Admin 项目）

Admin 审核页功能：

| 功能 | 说明 |
|------|------|
| 待审核列表 | 按提交时间排序，显示商户名+申请人+提交时间 |
| 详情查看 | 商户信息 + 营业执照图片预览 |
| 审核通过 | 调用 `POST /api/admin/merchants/{id}/verify` |
| 审核拒绝 | 调用 `POST /api/admin/merchants/{id}/reject`，附带原因 |
| 历史记录 | 显示该商户的审核流水 |

**审核通过时的附加操作：**

1. `Merchant.Verify(verifiedBy)` —— 标记已认证，记录审核人（当前 `Verify()` 无参数，需改为 `Verify(string verifiedBy)`）
2. `DELETE FROM MerchantBearings WHERE MerchantId = :id AND DataSourceType = 'Crawler'` —— 清空爬虫库存
3. 用户关联：保证申请用户已绑定到该商户（`Merchant.AddStaff(user)`）

### 4.3 爬虫库存清空时机

| 触发点 | 操作 |
|--------|------|
| 审核通过 | 立即清空该商户所有爬虫 MerchantBearing |
| 商户入驻后 ETL 再次运行 | **？？？详见第 8 节待讨论** |

## 5. 员工邀请体系

### 5.1 邀请流程

```
商户管理员（已认证）
    |
    |--- POST /api/merchant/staff/invite --->|
    |    { "phone": "13900139000" }           |
    | <--- { "inviteCode": "ABC123" } --------|
    |
    | 通过短信/链接/当面 发送邀请码给员工
    |
员工
    |--- POST /api/account/signup ----------->|
    |    { "account": "13900139000",          |
    |      "code": "654321",                  |
    |      "inviteCode": "ABC123",            |
    |      "realm": "openfindbearings" }      |
    | <--- tokens ----------------------------|
    |
    |--- 首次调用 API（JIT） ---------------->|
    |    CreateUserFromAuthCommandHandler     |
    |    读取 inviteCode -> 关联 merchant    |
    |    User.AssignToMerchant(merchantId)    |
```

### 5.2 InviteCode 生命周期

| 属性 | 值 |
|------|-----|
| 格式 | 6位字母+数字组合 |
| 有效期 | 72小时（从生成起） |
| 使用次数 | 一次性，使用后标记已消费 |
| 关联信息 | 记录邀请方 MerchantId + 被邀请人手机号 |

### 5.3 InviteCode 跨服务流程

```
API 项目：POST /api/merchant/staff/invite → 生成邀请码，存入 Invitation 表
                                ↓
Identity：SignUp 时校验 InviteCode（HTTP 调 API 校验或本地缓存校验）
                                ↓
Identity：校验通过后 InviteCode 存入 OidcUser.CustomClaims（Key="invite_code"）
                                ↓
API：CreateUserFromAuthCommandHandler 读取 AuthUserId + 自定义声明
  → 通过 AuthUserId 找到 OIDC 用户 → 读取 invite_code claim
  → 从 Invitation 表解析 MerchantId
  → user.AssignToMerchant(merchantId)
  → merchant.AddStaff(user)
  → 标记邀请码已使用
```

**注意：** `Invitation` 表放在 API 项目（业务数据由 API 负责）。Identity 不直接读 Invitation 表——Identity SignUp 校验邀请码时通过 HTTP 调用 API 校验端点 `/api/invite/validate`，或简单地在 Identity 本地校验格式后信任 API 最终校验。

**三种送达方式：**

| 方式 | 说明 | 开发阶段 |
|------|------|----------|
| 短信发送 | 通过真实 SMS 服务商发短信 | mock（打印日志） |
| 邀请链接 | 生成 deeplink，员工点开自动填入邀请码 | 需 MAUI 支持深度链接 |
| 当面告知 | 管理员直接告诉员工邀请码，员工在 APP 手动输入 | APP 输入框 |

### 5.3 InviteCode 表结构

| 字段 | 类型 | 说明 |
|------|------|------|
| Id | Guid | PK |
| MerchantId | Guid | 关联商户 |
| Phone | string(20) | 被邀请人手机号 |
| Code | string(20) | 邀请码 |
| ExpiresAt | DateTime | 过期时间 |
| IsUsed | bool | 是否已使用 |
| UsedByUserId | Guid? | 使用人（Identity UserId） |
| UsedAt | DateTime? | 使用时间 |
| CreatedAt | DateTime | 创建时间 |

### 6.1 MerchantBearing 现有字段

| 字段 | 类型 | 说明 |
|------|------|------|

| `BearingId` | Guid | 轴承ID |
| `PriceDescription` | string? | 价格描述（"55-60元"、"电议"） |
| `NumericPrice` | decimal? | 数值化价格（用于排序筛选） |
| `PriceVisibility` | enum | Public / LoginRequired |

| `MinOrderDescription` | string? | 起订量描述 |
| `Remarks` | string? | 商家备注 |
| `IsOnSale` | bool | 是否在售（商户控制上架/下架） |
| `IsPendingApproval` | bool | 是否需要管理员审核 |
| `IsFeatured` | bool | 是否推荐 |
| `ViewCount` | int | 浏览次数 |

### 6.2 MerchantBearing 新增字段

| 字段 | 类型 | 说明 |
|------|------|------|
| `DataSourceType` | 枚举（Crawler / Manual） | 区分爬虫数据和商户自管数据 |

`MerchantBearingConfiguration` 中使用简单枚举映射（非 `OwnsOne`），因为仅需要一个枚举字段，不需要完整的 Value Object。

### 6.3 爬虫库存标记

Sync L 阶段创建 MerchantBearing 时需要标记 `DataSourceType = Crawler`。涉及两处：

| 位置 | 改动 |
|------|------|
| `BatchCreateMerchantBearingsCommandHandler.cs` | 创建时 `DataSourceType = Crawler` |
| `BatchCreateBearingsCommandHandler.cs` | 如果有连带创建 MerchantBearing 的代码，同步标记 Crawler |

商户自管库存通过 `MerchantEndpoints` 创建时默认 `DataSourceType = Manual`。

### 6.2 API 端点

| 端点 | 说明 | 认证 |
|------|------|------|
| `GET /api/merchant/bearings` | 查看自己库存 | Bearer（商户管理员/员工） |
| `POST /api/merchant/bearings` | 添加在售轴承（单条） | Bearer（商户管理员/员工） |
| `DELETE /api/merchant/bearings/{id}` | 下架 | Bearer（商户管理员/员工） |
| `POST /api/merchant/bearings/batch` | Excel 批量导入 | Bearer（商户管理员） |

### 6.3 爬虫库存 vs 商户库存搜索

```
用户搜索轴承 -> 返回结果
  ├─ 认证商户的 MerchantBearing（Source = Manual） -> 优先展示
  └─ 非认证商户的 MerchantBearing（Source = Crawler） -> 正常展示
```

认证商户的爬虫库存已清空，所以搜索结果中认证商户展示的都是自管数据。

## 8. 待讨论确认的问题

### 8.1 ETL 再次运行时爬虫数据是否会重新覆盖

**问题：** 商户认证后爬虫库存被清空。但 ETL 每晚运行，下一次 L 阶段是否又会重新给该商户创建爬虫 MerchantBearing？

**分析：** 目前 L 阶段 `BatchCreateMerchantBearingsCommandHandler` 不做商户认证状态的检查，只要是 staging 来的数据就写入。认证商户的爬虫数据被清空后，下一次 ETL 运行时又会重新创建。

**可能的解决方案：**

| 方案 | 操作 | 复杂度 |
|------|------|--------|
| A. L 阶段跳过认证商户 | LoadService 创建关系前检查 Merchant.IsVerified，跳过 | 低，同步后爬虫不再更新 |
| B. 不做特殊处理，依赖幂等 | 爬虫数据覆盖不了自管数据（需 DataSource 保护逻辑） | 中，需要 MerchantBearing 级别保护 |
| C. ETL 不再处理认证商户 | Extract 阶段直接跳过认证商户的关系抽取 | 中，但商户添加新轴承后 ETL 无法补全外部定价参考 |

**初步推荐方案 A**：L 阶段检查目标商户是否为认证商户（`Merchant.IsVerified == true`），是则跳过爬虫 MerchantBearing 写入。这样做最简单，且符合"认证商户数据由商户自管"的原则。

### 8.2 商户认领冲突

**问题：** 如果商户 A 先申请认领了"上海天马轴承有限公司"，在审核通过前，商户 B 又申请认领同一家，怎么处理？

**建议：** 一个爬虫商户只能被一个申请认领。当存在 `PendingReview` 状态的申请时，其他用户不能再认领该商户。审核拒绝后可以重新被其他人认领。

### 8.3 验证码有效期与频率限制

**问题：** 短信验证码的有效期和发送频率策略？

**建议：**

| 策略 | 值 |
|------|-----|
| 验证码有效期 | 5分钟 |
| 同一手机号发送间隔 | 60秒 |
| 同一手机号每日上限 | 10次 |
| 验证码长度 | 6位数字 |

开发环境下固定验证码 `123456` 绕过上述限制，方便测试。

### 8.4 营业执照图片存储

**问题：** 商户上传的营业执照图片存在哪里？目前系统无 OSS 或文件存储服务。

**建议：**

| 选项 | 说明 |
|------|------|
| 本地文件系统 | 开发环境可用，生产环境需要挂载持久卷 |
| 数据库 base64 | 简化开发，但图片体积大时影响性能 |
| 对象存储 OSS | 生产环境推荐（阿里云OSS、MinIO等） |

**初期方案：** 开发环境存数据库 base64 字段（`Merchant.BusinessLicenseImage`），生产环境切换到 OSS。`Merchant` 实体新增 `BusinessLicenseUrl` 字段（OSS URL）和 `BusinessLicenseData` 字段（base64，仅开发用）。

### 8.5 商户员工的角色和权限

**问题：** 员工被邀请加入商户后，能做什么？与商户管理员权限如何区分？

**建议：**

| 角色 | 权限 |
|------|------|
| **商户管理员** | 全部权限：库存 CRUD + 员工管理 + 编辑商户信息 |
| **商户员工** | 仅库存 CRUD，不能管理员工或编辑商户信息 |

API 中通过 `User.MerchantId` + 业务层角色判断。员工在 `admin_user_roles` 中记录 `role_name = "MerchantStaff"`。
