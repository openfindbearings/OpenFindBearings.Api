## 1. 核心概念

### 1.1 两种数据来源，共存方案

| 来源 | 含义 | 管理方 | 可信度 |
|------|------|--------|--------|
| 爬虫（Crawler） | ETL 从 CBIA 等互联网站点抓取 | Sync 服务自动维护 | 低，用于冷启动填充 |
| 商户自管（Manual） | 认证商户自行上传/维护 | 商户管理员/员工 | 高，商户自行负责 |

**原则：** 爬虫数据作为基础填充，与商户自管数据通过 `DataSourceType` 字段共存。商户认证审核通过时不再清除爬虫数据，数据保留在库中。公共端点 `GET /api/merchants/{id}/bearings` 默认按 Manual 优先展示（可通过 `dataSource` 参数切换），Admin 页面提供"同步数据"弹窗查看爬虫来源记录。Sync L 阶段全量导入所有 MerchantBearing（不跳过已认证商户），`DataSource` 字段显式传入 `"cbia"`。

**覆盖保护：** 任何实体被人工维护过（DataSource 非 Crawler）后，爬虫不得覆盖（约束同时应用于 Bearing/Brand/BearingType/Merchant/MerchantBearing 的 Sync 批量写入路径）。

### 1.2 三种用户类型

| 类型 | 认证方式 | 入口 | 职能 |
|------|----------|------|------|
| 普通用户 | 手机号 + 短信验证码 | Mobile APP | 搜索轴承、浏览商户、关注收藏 |
| 商户管理员 | 普通用户 -> 申请入驻 -> 审核通过 | Mobile APP + Admin | 管理店铺、维护库存、邀请员工、维护资料与 Logo |
| 商户员工 | 被管理员邀请 -> 注册/确认 | Mobile APP | 协助维护库存 |

### 1.3 商户成员模型（一人多商户）

- 成员关系存 `MerchantMember` 表（(UserId, MerchantId) 唯一约束），取代 `User.MerchantId` 单值列的"一人一商户"硬约束。
- 商户域角色（MerchantAdmin / MerchantStaff）存于成员行；平台级角色（Individual/Admin/SuperAdmin）仍走全局 RBAC。
- 成员状态机：Active（在职）/ Removed（已移除，可被重新邀请复用 Removed 行）/ Suspended（停用，保留关系但无操作权限，可恢复）。
- 一个商户须始终保持 >= 1 个 Active MerchantAdmin；移除/停用最后一个管理员时拦截（守卫与移除能力同批交付）。
- **当前商户上下文（v2.2.0 收口）**：商户资料维护的读写（`GET/PUT /api/merchant/profile`）一律以 `X-Merchant-Id` 定位当前商户，与商品/成员管理同源，杜绝"看 A 改 B"。

### 1.4 两轴解耦模型（v2.1.0 新增，权威收口）

商户的"覆盖"与"认领"是**两根相互独立的轴**，各由不同字段决定，不再互相绑定：

| 轴 | 决定字段 | 判定 | 生效位置 |
|----|----------|------|----------|
| 是否会被爬虫覆盖 | `DataSource` | `!= Crawler`（即 Manual）→ 跳过覆盖 | Sync `BatchCreateMerchants`（仅当 `DataSource != null && SourceType != Crawler` 时跳过） |
| 是否可被认领 | `IsVerified` | `== false`（未认证）→ 开放认领 | `MerchantRepository.GetClaimableAsync` |

**覆盖轴规则：** 凡是"真人之手"产生或确认的商户，一律 `SetDataSource(Manual)`，此后永不被爬虫刷掉。写入 Manual 的全部路径：

| 动作 | 处理器 | 是否置 Manual |
|------|--------|----------------|
| 自助新建入驻（self） | `ApplyMerchantCommandHandler.ApplySelfAsync` | 是（新建时；此前留 null 是被夺走的漏洞，已修） |
| 认领已有商家（claim） | `ApplyMerchantCommandHandler.ApplyClaimAsync` | 是（认领即接管，并应用第三步核对的资料） |
| 接受提名（新建/已有两路） | `AcceptNominationCommandHandler` | 是 |
| 管理员编辑商户资料 | `UpdateMerchantCommandHandler` | 是（已有；v2.2.0 起维护页写入即走此路径） |
| 认证通过 | `VerifyMerchantCommandHandler` / `ApproveLicenseCommandHandler` | 是（人工核实即人工维护） |
| 纠错审核通过 | `ApproveCorrectionCommandHandler` | 是（已有） |

> 关键坑：`DataSource == null` 比 `Crawler` 更危险——`BatchCreateMerchants` 的跳过条件要求 `DataSource != null`，null 不会被跳过，反而会经同名匹配被回填为 Crawler 并覆盖。因此**所有创建路径必须显式置 Manual，绝不能留 null**。

**认领轴规则：** 商户被认证（`IsVerified=true`）即退出认领池；认证↔解除认证即开关认领。已认领（有在职成员）或进行中提名锁定的商家也不在池内。见 4.1 认领门。

> 两轴解耦后，"认证"不再顺带管覆盖，"覆盖"也不再顺带管认领。爬虫无主商家（Crawler + 未认证 + 无成员 + 无提名）既在认领池、也会被爬虫刷新（正常）；一旦被真人认领/新建/认证即置 Manual 出覆盖面，认领/成员态决定其出认领面。

**解除认证（Unverify）：** `Merchant.Unverify()` 方法存在但当前**无端点/调用方**，属未接线的独立管理功能。设计原则：解除认证时 `IsVerified=false`（回到可被认领），且**仅当无在职成员时**才把来源退回 `Crawler`（重新可被爬虫刷）；若仍有在职管理员则保持 `Manual`（有人维护的不被覆盖）。待有产品需求再接线。

**审核通过时的操作（ApproveMerchantCommandHandler）：**

1. `Merchant.Approve()` —— Pending → Active，商户生效（补齐原缺失的审核门）
2. 提名模式商户：建被提名人 MerchantAdmin 成员行 + 发起人 MerchantStaff 成员行（InitiatorJoins=true 时）
3. 爬虫数据保留在库中（与 v1.3.0 一致），不因审核清除

**认证（verify）与审核（approve）分离：**
- `approve` 决定商户是否生效（Pending→Active），是 C 端可见的前提
- `verify` 标记认证等级（`IsVerified=true`/Grade），不再清除爬虫数据；v2.1.0 起 verify 同时 `SetDataSource(Manual)`（人工核实即人工维护，护住不被覆盖）

## 3. 身份认证体系

- 认证事实源在 Identity（手机号/微信 OpenId/密码），业务事实源在 API，单向同步。
- 业务鉴权不信 JWT role claim：**MerchantAdmin/MerchantStaff 一律查 API 自己的成员表动态判定**（详见 7.2）。
- 一人多商户：请求头 `X-Merchant-Id` 指定当前操作商户（缺省 = 首个在职成员商户），由 `UserContextMiddleware` 解析并校验"该用户是该商户的 Active 成员"后写入 `context.Items["CurrentMerchantId"]`。

**移动端向导（Taro `pages/merchant/apply`，v2.1.0/v2.2.0）：** 三步单页——
1. 查找：关键词联想 `GET /api/merchant/claimable`，可"选中已有商家"或"没找到？新建商户"。
2. 操作方式：**选中已有** 与 **新建** 两条路径都给两卡——"我当管理员经营"（self/claim）、"邀请别人当管理员"（nominate）。多管理员/员工不在向导内配置，走入驻成功后的成员管理（§5）。
3. 提交表单：`self`=空白可编辑；`claim`=用 `getMerchantDetail` 预填后逐项核对可编辑（互联网信息不可信）；`nominate`=填被提名人手机号（指向已有商家时展示所选商家，无需再填名称）。**"客服电话"= 商户对外公开电话（可为 400/座机/手机），普通可编辑、self 留空 / claim 预填爬虫值，不预填申请人手机**；联系人（对外联系人姓名）默认取登录昵称、可编辑（见 8.5 与 4.4）。

#### 认领门（`GetClaimableAsync`，v2.1.0 收口）

可认领池谓词（两根轴解耦后的完整条件）：

```
!IsVerified                                   // 认领轴：已认证不出池
&& Status != MerchantStatus.Draft             // 排除提名草稿
&& !MerchantMembers.Any(m => m.Status==Active)  // 已被真人认领(有在职成员)不出池
&& !StaffInvitations.Any(si => si.Type==Nomination
      && si.Status in {Pending, Accepted}
      && si.CreatedAt.AddDays(7) >= now)       // 进行中提名锁定，不出池
```

- v2.0.0 及以前"来源必须=Crawler"这一条件**已移除**：来源管的是覆盖、不是认领（见 1.4）。
- "无在职成员"防二次抢领；"无进行中提名"补住"提名发出到审核生效"这段窗口（成员在审核通过才建，此前无在职成员，需靠邀请状态排除）。
- 提交时 `ApplyClaimAsync` / `NominateMerchant(已有)` 再做一次并发校验（`GetActiveByMerchantAsync` + 状态校验），防瞬间双领。

#### 4.1.1 新建撞名引导认领（v2.2.0 新增）

**背景：** v2.1.0 前 `ApplySelfAsync` 只校验"名称非空"即 `new Merchant` 落库，而 `Merchants.Name`/`UnifiedSocialCreditCode` 索引**均非唯一**，真人自助新建撞名会直接产生**重复商户行**（与爬虫 Pending 或他人 Manual 商户同名/同代码），造成数据分裂。

**查重规则（`EnsureNoSelfDuplicateAsync`，仅 self 模式）：**
- 匹配键：**填了统一社会信用代码就按代码精确匹配，否则按商户名精确匹配**（`GetByCreditCodeAsync` / `GetByNameAsync`，均排除 Draft）。
- 命中后按可认领性分流：

| 命中商户 | 判定 | 行为 |
|----------|------|------|
| 可认领（`!IsVerified` 且无在职成员） | 引导改认领 | 抛 `MerchantClaimableConflictException` → HTTP 409 + `code=MERCHANT_CLAIMABLE_EXISTS` + `existingMerchantId/existingName` |
| 已认证 或 已被认领（有在职成员） | 拒绝 | 抛 `InvalidOperationException` → 400（"该商户已存在…已认证或已被认领"） |
| 无命中 | 正常新建 | 建 Pending 商户 + MerchantAdmin 成员 + `SetDataSource(Manual)` |

**前端引导（Taro）：** self 提交捕获 409 + `code==='MERCHANT_CLAIMABLE_EXISTS'` → 弹窗"「X」已存在但尚未被认领，是否改为认领？"→ 选"改为认领"则**保留已填表单**、切 `flow=claim` + `selected=existing`，再点提交即走认领（数据合流，不新建）；选"改名新建"则留在表单改名称。**错误透传依赖 §8.6 的 BFF 修复。**

> 无唯一索引硬约束：撞名判断为应用层精确匹配 + 认领引导；同名通用词仍可经"改名新建"或精确匹配不命中而各自独立存在（用户为不同实体新建是合理的）。如需 DB 级唯一性，另立需求（涉及迁移 + 历史重复数据清洗）。

**模式 A 自助当管理员（mode=self，默认）：**
登录用户填商户资料+资质 → 建 Pending 商户 + 发起人 MerchantAdmin 成员行 + `SetDataSource(Manual)` → Admin approve → 商户生效。

`POST /api/merchant/apply` 请求体字段：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `mode` | string | 否 | 默认 `self`；`claim` 为认领 |
| `claimMerchantId` | Guid? | claim 时是 | 认领的目标商家 ID（须通过认领门） |
| `name` | string | self 时是 | 商户名称 |
| `type` | int? | 否 | MerchantType 枚举值 |
| `contactPerson` / `phone` / `mobile` / `email` / `address` | string? | 否 | 联系方式 |
| `companyName` | string? | 否 | 公司全称 |
| `unifiedSocialCreditCode` | string? | 否 | 统一社会信用代码 |
| `description` | string? | 否 | 商家简介 |
| `licenseUrl` | string? | 否 | 营业执照图片 URL（可选，用于认证） |

**模式 B 提名他人当管理员（`POST /api/merchant/nominate`）：**
请求体在 v2.1.0 新增 `targetMerchantId`（Guid?，可选）：
- **为空 = 提名新建**：发起人填被提名人手机号/邮箱 + 商户草稿信息 → 建 **Draft 商户** + 一条 `Type=Nomination, Role=MerchantAdmin` 的 StaffInvitation（发起人 `InitiatorJoins` 默认 true）。
- **非空 = 提名认领已有商家**：不新建、不改来源，仅对该商家登记 Nomination 邀请；后端校验目标 `!IsVerified && Status!=Draft && 无在职成员`。
- 两种情况都做**防重复提名**：同一商家若已有未过期的 Pending Nomination，拒绝再次发出。
- 被提名人经 `/api/merchant/nominate/{code}/accept` 接受（见下）。Admin approve → 商户 Active，建成员行：被提名人 = MerchantAdmin，发起人 = MerchantStaff（InitiatorJoins=true 时）。
- 被提名人手机号取自 JWT `phone_number` claim（不接收户参数），accept 校验与邀请手机号一致，防邀请码泄露被冒领。

**模式 C 认领存量商户（mode=claim）：**
- 场景：Sync 持续灌入爬虫商户，未认证的开放商家可被真人认领接管。
- 入口搜索：`GET /api/merchant/claimable?keyword=&page=&pageSize=`（返回通过认领门的商家）。
- 向导第三步预填可编辑，提交 `POST /api/merchant/apply`（mode=claim, claimMerchantId + 核对后的资料）：`ApplyClaimAsync` 应用编辑（字段级 `??` 合并，不冲 logo/website/businessScope）并 `SetDataSource(Manual)`，申请人成为该商户 MerchantAdmin（审核通过后生效）。
- 曾被拒绝的商家再次被认领时，`ReopenForClaim()` 解除旧成员、恢复 Pending 重走审核（B7）。

#### 4.1.2 申请人自助撤回入驻申请（v2.3.0 新增）

**背景：** 用户在提交入驻申请后、平台审核前，可能发现资料填错、撞名引导后想改名重填、或不再需要入驻。此前 Pending 申请只能等 Admin approve/reject，用户无自助撤销通道；且"新建"与"认领"两种渠道的商户本体归属完全不同（自建商户是本次申请新造的、认领商户本就是爬虫/平台的），撤回清理策略必须区分。

**端点：** `POST /api/merchant/{merchantId:guid}/withdraw`（入驻组，`RequireAuthorization()` 任意登录用户，具体权限在 handler 内校验）。

**守卫（`WithdrawApplicationCommandHandler`）：**
1. 商户须存在，否则抛"要撤回的申请不存在"；
2. `Status == Pending` —— 审核通过后是正式商户（走正常管理，不属"撤回"语义），拒绝；
3. 调用者须为该商户**当前在职 MerchantAdmin 成员**（`GetActiveByUserAndMerchantAsync` + `IsAdmin`）——申请提交时唯一的管理员即申请人，防越权撤他人申请；
4. 失败均以 `InvalidOperationException` → HTTP 400 返回。

**渠道打标（`Merchant.ApplicationMode` 枚举，v2.3.0 新增）：**

| 值 | 含义 | 打标位置 |
|----|------|----------|
| `None`(0) | 非入驻流程产生（爬虫/导入/种子/历史/撤回后的认领商户） | 默认值 |
| `Self`(1) | 自助新建 | `ApplySelfAsync` 建商户时 |
| `Claim`(2) | 认领既有商家 | `ApplyClaimAsync` 认领时 |
| `Nomination`(3) | 提名草稿 | `NominateMerchantCommandHandler` 提名新建 Draft 时 |

**分支清理策略：**

| 渠道 | 清理动作 | 理由 |
|------|----------|------|
| Self | 硬删除商户本体 + 其全部成员行（外键 Restrict 须先删成员；营业执照/商品等子表由 MerchantId 外键级联随商户删除） | 未公示的草稿式 Pending 商户撤回后彻底清除，避免残留同名/同代码记录干扰 4.1.1 新建查重 |
| Claim | 不删商户（本就属于爬虫/平台）：认领人成员行软移除（`Remove()` → Removed）；`RevertClaimedToCrawler("apply-revert")` 把来源退回 Crawler、渠道归 None | 撤回后该商家重新满足认领门（无在职成员 + 来源回爬 + 未认证），回到公共认领池，且重新可被 Sync 刷写（认领时置 Manual 的保护随认领关系一并解除） |
| Nomination / None | 抛"该申请暂不支持自助撤回"（400） | 提名草稿的发起人本就不是商户成员（成员审核通过才建），不满足守卫 3；且提名取消涉及邀请作废，语义不同，不并入此入口。None 为历史/爬虫数据，不应出现在申请列表 |

**幂等与竞态：** 守卫均在同一命令内校验（Pending + 在职管理员），若审核已抢先处理（状态非 Pending）撤回即被拒；撤回成功后 Self 商户消失、Claim 商户出成员表，`GET /api/merchant/application` 自然不再返回该卡片，移动端刷新列表即可（见 8.8）。

**状态机（更新）：**

```
MerchantStatus.Draft（提名草稿，不可被C端检索/不被Sync合并；仅"提名新建"路径）
  -> PendingReview（已提交，等待审核）
    -> Active（approve 审核通过，商户生效）
    -> Suspended（reject 审核拒绝，附原因，可重新申请）
    -> 撤回（withdraw，v2.3.0）：Self 商户行删除 / Claim 退回 Pending 无主状态并入认领池
  Suspended（v2.6.0 自助通道，见 4.1.3）：
    -> resubmit 修改重提：回 PendingReview 重走审核（原单保留，成员不动）
    -> delete-application 删除：Self 商户行删除 / Claim 退回认领池（与撤回同构）
"提名认领已有商家" 保持其原状态（本就非 Draft），accept 仅预认领 + 置 Manual，成员审核时建。
```

#### 4.1.3 被拒申请修改重提与删除（v2.6.0 新增）

**背景：** 申请被驳回后，申请人此前的唯一出口是点击卡片跳**空白**向导重填——且 self 渠道换不了结局：原被拒商户行仍在库（同名/同信用代码查重会命中它且申请人仍是其在职管理员），再提交必吃 400"无法重复新建"，**永久卡死**（claim 渠道有"重认领 reopen"隐式路径幸免）。主流平台（美团/淘宝/抖音门店入驻）被拒后的标准二件套是"修改资料重新提交（原单保留）"+"删除申请记录"。移动端交互与撤回同构：**点击=主操作（编辑重提）、左滑=销毁操作（删除）**。

**三端点（入驻组，登录即可 + handler 内成员表校验）：**

| 端点 | 守卫 | 行为 |
|------|------|------|
| `GET /{merchantId}/application` | 调用者为在职成员（否则 404，不泄露存在性） | 返回全量可编辑资料 + status/rejectReason/applicationMode（重提表单预填源） |
| `POST /{merchantId}/resubmit` | `Suspended` + 在职 MerchantAdmin + 渠道 Self/Claim；`name`/`companyName` 必填 | 查重排除自身后字段级合并更新（含改名/改类型，`UpdateName`/`UpdateType`）+ `Resubmit()`：清驳回原因、`Activate()`、回 Pending 重走审核；原单保留、成员关系不动 |
| `POST /{merchantId}/delete-application` | `Suspended` + 在职 MerchantAdmin | 按渠道分支清理，**与撤回同构**（v2.6.0 提取 `ApplicantApplicationCleanup` 共用：Self 硬删商户+成员 / Claim 解除认领人+退回爬虫认领池 / Nomination、None 拒绝） |

**与撤回（4.1.2）的分工：** 清理逻辑完全同构，差异仅在状态守卫——Pending 用"撤回"、Suspended 用"删除"，三态语义（审核后=正式商户管理）不混用。

**不做：** 提名（Nomination）被拒单的自助重提/删除仍不开放——被提名人重提走"接受提名"原通道（Draft 未变），发起方取消属提名专项；`None` 为历史/爬虫数据无申请人。

**移动端（Taro）：** `apply.tsx` 路由参数 `merchantId` 进入**编辑模式**——直达表单相位（无步骤条、无"返回上一步"）、拉详情预填、非 Suspended/非 self/claim 自动退页、提交走 resubmit；`pages/merchant/index` Suspended 卡外包 SwipeCell 左滑红色"删除"（二次确认），副标题改操作指引"点击修改重新提交，左滑可删除"。BFF 三条同名代理（`/mobile/merchants/{id}/application|resubmit|delete-application`）。

### 4.4 商户信息维护与 Logo（v2.2.0 新增）

入驻生效后，商户管理员在移动端"商户页 → 信息维护"编辑本商户资料与 Logo，是 `UpdateMerchantCommandHandler`（置 Manual，见 1.4）的前端入口。

**端点（`MerchantEndpoints`，组 `RequireAuthorization("Merchant")`）：**

| 方法 | 路由 | 说明 | 权限 |
|------|------|------|------|
| GET | `/api/merchant/profile` | 读当前商户上下文资料（维护页回填） | 商户成员（只读） |
| PUT | `/api/merchant/profile` | 更新资料（名称/类型/公司名/信用代码/联系方式/官网/简介/经营范围/Logo） | **MerchantAdmin** |
| POST | `/api/merchant/logo` | 上传 Logo 图片，仅返回相对 URL | **MerchantAdmin** |

- **读写均按 `X-Merchant-Id` 当前商户上下文定位**：`GET` 由 `GetMerchantByUserIdQuery`（首个成员）改为 `GetCurrentMerchantAsync`（当前上下文），与 `PUT` 对齐（修复 v2.2.0 前多商户"GET 载 A、PUT 存 B"错位）。
- **PUT / logo 锁 MerchantAdmin**：`permissionService.IsMerchantAdmin()` 校验（对齐成员管理/Excel 导入端点）；此前仅"成员即可"，已收紧。
- **Logo 落盘约定**：`uploads/merchants/logo/{userId:N}_{UTC时间戳}{ext}`（jpg/png/webp，≤2MB），与用户头像/证照材料同走 `IObjectStorageService` 抽象（v2.8.0：生产 MinIO bucket=media，开发本地盘），与爬虫 logo（Sync 写 `images/merchants/logo/{sha256}`）两前缀并存；两棵树均由独立 nginx 媒体服务反代 MinIO 在 `bff.515813.xyz/media/**` 直出，前端 `usableImage` 拼媒体源 base 渲染（库内只存相对键 `/uploads/...`、`/images/...`）。
- **上传只回 URL，不即时落库**：`POST /api/merchant/logo` 返回 `{ url }`，维护页把它填入表单 `logoUrl`，点保存时随 `PUT /profile` 写入（`UpdateMerchantCommandHandler`：`logoUrl` 为 `null` 保留原值、非空覆盖，与"留空不改"一致）。
- **`ToDetailDto` 补齐映射**：v2.2.0 前 `MerchantExtensions.ToDetailDto`（两个重载）均未映射 `LogoUrl`（及 `Website`/`UnifiedSocialCreditCode`），导致商户详情页与维护页永远读不到 logo，已在两个重载补齐。

### 4.5 移动端商户切换器（v2.2.0 新增）

### 4.6 站内信通知系统（v2.5.0 新增）

审核结果与提名进展通过站内信触达申请人，架构为"领域事件 → 订阅者落库 → 收件箱读取"三段：

**数据模型**：`Notification` 实体（`Notifications` 表，迁移 `AddNotifications`），写扩散 1 对 1（每收件人一行）：
`UserId / Type(merchant_approved|merchant_rejected|nomination_accepted|system) / Title / Body / BizType(merchant|nomination) / BizId / IsRead / ReadAt`，
索引 `(UserId,CreatedAt)`（列表）与 `(UserId,IsRead)`（角标）。

**产生链路**（订阅发生在 `UnitOfWorkBehavior` 提交之后，通知写入失败仅记日志、不回滚已成功的业务命令）：

| 触发点 | 事件 | 收件人 | 正文要点 |
|--------|------|--------|----------|
| Admin 审核通过 | `MerchantApprovedEvent`（`Merchant.Approve()` 发布） | 该商户全部在职 MerchantAdmin | 恭喜生效，可开始经营 |
| Admin 审核拒绝 | `MerchantRejectedEvent`（`Merchant.Reject()` 发布） | 同上 | 含"分类：说明"格式的拒绝原因 |
| 被提名人接受提名 | `NominationAcceptedEvent`（命令处理器直接 Publish） | 发起人（`invitation.OperatorId`） | 资料已提交审核，你以员工入伙 |

**边界决策**：不设"提名已发出"事件——被提名人手机号到 API 用户的解析在 Identity 侧（API `User` 实体无手机号列），未注册用户站内信不可达；发出环节的触达由邀请链接（H5 注册页带 inviteCode）与 `GET /api/merchant/nominations/pending` 待办查询承担。

**读取端**：`/api/notifications` 6 端点（见 API《02 v1.27.0》第 6 组）→ BFF `/mobile/notifications/*` 透传 token → Taro `pages/notifications/index` 消息中心 + `CustomTabBar`"我的"tab 未读角标（`stores/notification` zustand 共享；TabBar 随页面切换重挂载即刷新，无轮询）。

**v2.12.0 消息管理增强**（对标主流消息中心）：
- **删除单条**：`DELETE /api/notifications/{id:guid}` 硬删（收件人即唯一读者，无保留价值；`UserId` 条件天然防越权）。前端已读行左滑出红色"删除"（SwipeCell 复用），**未读行不可滑删**（防误删漏看）。
- **清空已读**：`DELETE /api/notifications/read` 批量删本人全部已读、未读保留，返回 `{ affected }`。前端顶部"清空已读"+确认框。
- **全部已读常驻**：Taro 端"全部已读"从"有未读才渲染"改常驻、无未读置灰（原条件渲染让用户找不到入口）。
- **详情面板**：点消息行不再直接跳转，弹底部详情面板（标题/全文/时间 +〔知道了〕〔去处理〕），打开即标已读；〔去处理〕才按 BizType 跳商户页/申请页。
- **邀请站内信核销**：员工邀请被接受/拒绝时服务端 `MarkReadByTypeAsync` 自动把对应邀请通知置已读（v2.11.0），角标不残留已处理邀请。

### 4.7 入驻材料按类型分层，随申请单一次审结（v2.7.0 新增）

**背景：** 本平台是"轴承门店点对点找货"的信息聚合平台（非交易撮合），审核要保护的核心资产是**供给数据可信度**。旧模型只承载营业执照一种材料、且"先入驻后补照"独立排队——审核人面对"名称+电话"盲审；轴承行业真正的信任轴（授权经销商身份真伪）完全无证据可审。对照主流（企业店入驻=资质随单审 + 按经营范围分层要材料）改造为"申请单一次审结、材料按商家类型分层"。

**材料矩阵（`Application.DTOs.DocumentRequirements`，apply/resubmit/accept 三入口共用）：**

| 商家类型 | 必备材料 | 选传 |
|---|---|---|
| 生产厂家 Manufacturer | 营业执照 | 厂房照片（认证加分展示） |
| 授权经销商 AuthorizedDealer | 营业执照 + **品牌授权书** | — |
| 分销商 / 贸易商 | 营业执照 | — |

- **商家类型升必填**（此前 self 缺省 Trader，可钻"贸易商只要执照"的空子冒充授权渠道）。
- **随单提交**：前端先 `POST /api/merchant/documents/upload` 预上传拿 URL，材料以 `documents:[{type,fileUrl}]` 随 apply/resubmit/accept 一次提交，落 Pending 记录。
- **审结级联**：`approve` 把该商户 Pending 材料批量置 Approved；`reject` 批量置 Rejected（带原因）。**不再有"材料单独排队"**——原独立队列 `DocumentController`（Admin"证照材料审核"）降级为入驻后换证/补材料的变更通道。
- **认证口径**：`verify`（点认证标）校验该类型必备材料全部 Approved，缺则 400 列缺项；移除旧 `ApproveDocument`"通过即自动认证"耦合（认证成为独立、有据的判定）。
- **重提合并判定**：被拒重提按"存量已批准 + 本次新补"合并跑矩阵——历史批过的沿用、驳回过的缺什么补什么（`GetApplicationDetail` 返回 `documents[]` 含状态供前端回显）。
- **安全**：材料 URL 不进 C 端商家详情 DTO（授权书属敏感经营信息），仅商户本人（成员）与 admin 审批侧可见。

**数据迁移：** `AddMerchantDocuments` 手写 RenameTable/RenameColumn/RenameIndex + AddColumn `Type`（一次性 defaultValue=1 回填存量），无数据丢失；Sync/Crawler 不触碰该表，零影响。

### 4.8 商户主动申请认证闭环（v2.9.0 新增）

**背景：** 认证（资质等级）此前是 Admin 单向动作——商户补全材料后只能等待平台发现，缺少"我准备好了"的表达通道，审核侧也无优先级信号。

**设计（对标 1688/京东店铺认证申请制）：**

1. **申请端点** `POST /api/merchant/{merchantId}/verify-request`（`RequestVerifyMerchantCommand`）：
   - 权限：该商户在职 MerchantAdmin（成员表校验，防越权替他人商户申请）
   - 前置：商户 `Active`（Pending 走入驻审批通道）且未认证
   - 资格校验：`DocumentRequirements.RequiredTypes(类型)` 全部 `Approved`——**与 Admin verify 完全同口径**，杜绝"申请了但审不了"的空转；不齐时 400 透传缺项清单（"缺少已审核通过的必备材料：营业执照、品牌授权书，请先在信息维护补传"），Taro toast 直接展示引导
   - 幂等：已申请再次提交静默成功
2. **状态标记：** `Merchant.VerifyRequested`（bool，迁移 `AddMerchantVerifyRequested`）；`Verify()` 认证通过自动清除。标记**仅作意向信号**，不改变认证判定逻辑。
3. **消费方：**
   - Admin 入驻审批页：Active 未认证且已申请的行显黄色"申请认证"徽标（列表+抽屉状态行），审核队列优先处理
   - Taro 商户卡："申请认证"按钮调本端点；`verifyRequested=true` 时按钮转"已申请认证"置灰（数据经 `MerchantApplicationDto.verifyRequested` → BFF → store 透传）

**边界决策：** 未做"申请撤回"（Admin 未处理时标记无副作用，再认证时自动清）；未做站内信通知 Admin（Admin 徽标即队列信号，通知留给未来工单化）；认证被拒不清除申请标记的场景不存在（verify 只有成功路径，拒绝走驳回通道）。

### 4.9 入驻主体字段锁定与全量发现搜索（v2.10.0 新增）

**字段锁定：** Active 商户 `PUT /api/merchant/{id}`（UpdateMerchant）拒绝变更 `CompanyName`/`UnifiedSocialCreditCode`——两者与营业执照绑定、是平台认证依据，自助改动等于换主体却免审（换主体须重新入驻/联系平台）。守卫只在"请求值≠存量值"时 400，未传/同值放行（兼容部分字段更新）。Taro 信息维护页对应字段改只读展示 + 联系平台提示。可编辑：商户名称（展示名）、联系人、电话、地址、简介、Logo、官网。

**全量发现搜索：** `GET /api/merchant/claimable`（入驻向导第一步）由"仅可认领池"升级：

- 仓储 `GetClaimableAsync`→`GetDiscoverableAsync`：只排除草稿，返回关键词命中的全部商户。
- 认领可行性从查询条件移到处理器标记计算：`isClaimable`（未认证 && 无在职成员 && 无进行中提名锁定）、`isMine`（当前用户在职成员）、`statusText`（可认领/我的商户/已入驻/审核中/已认证）。批量集合查询防 N+1（成员 `GetActiveByMerchantIdsAsync` + 提名锁定 `GetNominationLockedMerchantIdsAsync`）。
- Taro：搜索结果行显状态徽标；点"我的商户"引导返回商户页管理；点不可认领项 toast 提示——**在搜索阶段阻断重复新建**，不再只靠提交时 409 撞名兜底（409 通道保留）。

### 5.3 员工邀请确认制（v2.10.0 新增，替代静默拉入）

**背景：** 原"添加成员"对已注册用户直接写成员行——被邀人无感知、列表却凭空多出成员，与主流协作产品（钉钉/飞书/千牛：邀请需本人同意）不符；且 Identity 侧 `/api/users/by-phone|by-email` 端点从未实现（UsersController 是 MVC 管理面板），API 查询恒 404，实际所有添加都静默走了"未注册→邀请码"分支。

**设计：**

1. **Identity 补齐服务间查询面**：新增 `UsersApiController`（`api/users`，AllowAnonymous + 集群内网隔离，与 SmsController 同款先例）：`GET by-phone` / `GET by-email`，返回 OIDC 形状 UserDto（禁用用户按 404）。不触碰 OpenIddict/OAuth。
2. **已注册用户 → 待确认邀请**：`AddStaff` 命中注册用户后 JIT 业务库 User 行，创建 `StaffInvitation(Type=Staff, Phone=Identity档案手机号优先, Role, OperatorId)`，**不建成员行**；发站内信 `staff_join_invited` 给被邀人。已是 Active 成员返回幂等提示（`AlreadyMember`）。
3. **未注册用户 → 原邀请码通道**：记录邀请 + 短信/邮件（mock 发送，链接带 code 注册时 `CompleteInvitationAsync` 兑换）。
4. **被邀人侧**：`GET staff/invitations/pending` 按 JWT `phone_number`/`email` claim 匹配（服务端权威，不接受自报联系方式）；accept → 守卫（Type=Staff + Pending + 7 天有效期 + 联系方式"非空且相等"命中，排除 null==null 穿透；已是成员拒绝）→ 建成员行（复用 Removed 行 Rejoin）+ `Complete(sub)` + 通知发起人 `staff_join_accepted`；decline → `Declined`。
5. **管理员侧**：成员列表合并 `Status=Invited` 行（Nickname 位展示被邀联系方式，管理员自填不属泄露）；revoke 需在职管理员 → `Revoked`。
6. **Taro 消费**：商户页 `useDidShow` 拉待确认邀请 → 卡片横幅（接受/拒绝）；成员页邀请行点击仅可"撤销邀请"。

**幂等与防重：** 同商户重复添加同一在职成员 → AlreadyMember 提示；重复发邀请不撤销旧邀请（多条 Pending 并存，接受一条其余仍 Pending 至过期/撤销——可接受，成员行唯一键兜底）。

### 5.2 平台兜底（Admin）

`POST /api/admin/merchants/{id}/members`（RequirePermission("merchant.verify")）：商户无任何在职管理员等异常时，平台直接指定/恢复成员（已存在成员行则恢复/改角色，否则新建），避免"0 管理员"僵局。

## 8. 已确认的设计决策

### 8.1 ETL 与商户认证的交互策略

**决策：** 爬虫数据保留，通过 DataSourceType 字段区分，认证审核不再清除数据。

**理由：** 认证商户需要查看爬虫导入的初始库存数据作为参考。Admin 运营人员通过"同步数据"弹窗查看爬虫来源记录，便于数据核对。公共端点通过 `dataSource` 参数控制展示范围，Manual 数据优先。

**实现方式：**
1. 审核通过时不再调用 `DeleteByMerchantAndSourceAsync`，数据保留
2. L 阶段全量导入所有 MerchantBearing（不跳过已认证商户），`DataSource` 显式传入 `"cbia"`
3. `GET /api/merchants/{id}/bearings` 新增 `dataSource`（枚举：Manual/Crawler）和 `onlyOnSale`（bool）查询参数
4. Admin 审核页新增"同步数据"弹窗，支持"显示全部"切换

### 8.2 商户成员模型与审核门（v2.0.0 新增）

- **成员表取代单值列**：`MerchantMember` 是"谁属于哪个商户、什么角色"的唯一事实源；业务鉴权（IsMerchantAdmin/IsMerchantStaff）查成员表，不信 JWT role claim。
- **一人多商户**：请求带 `X-Merchant-Id`（缺省 = 首个在职成员商户），UserContextMiddleware 校验成员身份。
- **审核门**：全代码原先无处调 `Merchant.Approve()`（P3 修复前审批通过仍 Pending、C 端不可见）。现 `approve`（Pending→Active）与 `verify`（认证等级）分离。
- **多管理员 + 守卫**：商户须 >= 1 Active MerchantAdmin；移除能力与守卫同批交付；异常致 0 管理员时平台经 `POST /api/admin/merchants/{id}/members` 兜底。
- **提名入伙**：被提名人=MerchantAdmin、发起人=MerchantStaff（InitiatorJoins=true 时），审核通过时建成员行。

### 8.3 两轴解耦：覆盖看 DataSource、认领看 IsVerified（v2.1.0 新增，权威收口）

**决策：** 彻底拆分"能否被爬虫覆盖"与"能否被认领"两根轴（详见 1.4）。
- 覆盖 = `DataSource==Manual` 才免覆盖；所有真人之手（新建/认领/接受提名/编辑/认证/纠错）统一置 Manual。
- 认领 = `!IsVerified && 非Draft && 无在职成员 && 无进行中提名`；认证开关认领池。

**理由：** v2.0.0 把"可认领"错挂在"来源=Crawler"上，既误伤人工新建、又与覆盖逻辑纠缠不清；且自助新建来源留 null，会被 `BatchCreateMerchants` 当未打标经同名匹配转 Crawler 并覆盖，导致用户新建的商户被爬虫"夺走"。两轴各自正交后，覆盖与认领互不干扰，语义清晰。

**实现方式：**
1. `GetClaimableAsync` 去掉来源条件，加 `无进行中提名` 条件。
2. `ApplySelfAsync` / `ApplyClaimAsync` / `AcceptNomination` / `Verify` / `ApproveLicense` 各加 `SetDataSource(FromManual)`。
3. `NominateMerchant` 加 `TargetMerchantId` + 防重复提名；`AcceptNomination` 放宽 Draft 分支。
4. Taro 向导：第二步双卡、第三步认领预填可编辑（`getMerchantDetail` 预填），提交按矩阵分发（self/claim/nominate-new/nominate-existing）。
5. Sync 无需改动——覆盖判断已在 `BatchCreateMerchants` 按 `DataSource` 生效，API 侧置 Manual 即落入跳过分支。

### 8.5 新建查重引导认领 + 联系方式字段语义拆分（v2.2.0 新增）

**决策：**
1. 自助新建撞名不产生重复：填了信用代码按代码、否则按名称精确查库；命中可认领→引导改认领（合流），命中已认证/已认领→拒绝（见 4.1.1）。
2. **拆字段而非加开关**（借鉴美团"门店电话 vs 经办人手机"、淘宝/拼多多"客服电话 vs 主体实名手机"）：`Merchant.Contact.*` 定位为**商户对外公开联系块**（详情页可见）。
   - **客服电话**（`Contact.Phone`）：店铺对外电话，可为 400/座机/手机，**普通可编辑**，self 留空、claim 预填爬虫值供核对；**不预填、不锁定申请人手机号**（避免把个人手机默认公示）。
   - **申请人/经办人手机**：**不在本字段**，它本就是登录账户手机（`User.PhoneNumber` + JWT `phone_number` + 由 `MerchantMember(UserId)` 关联可反查），认领/邀请核身走 JWT。
   - **联系人**（`Contact.ContactPerson`）：对外联系人姓名，默认取登录昵称（申请人常即首任联系人），仍可编辑。

**理由：** 早期把"账户手机"预填进"联系电话"并锁定，混淆了"身份手机"与"店铺对外电话"两个概念（店铺对外电话常是 400/门店号，且不应默认公示个人手机）；用复选框切换只是给错误字段打补丁。正解是**字段各司其职**：对外联系块归对外联系块，身份手机留在账户层。新建撞名不引导则产生重复商户行（名称/代码均无唯一索引）。

**实现方式：**
1. API：`MerchantClaimableConflictException` + 中间件 409 + `EnsureNoSelfDuplicateAsync`。
2. BFF：`PostWithResultAsync` + `/apply` 转发（见 8.6），否则 409 到不了前端。
3. Taro：`ApiError.data` 承载 `existingMerchantId/existingName`，向导捕获 `code==='MERCHANT_CLAIMABLE_EXISTS'` 弹引导；向导与维护页联系电话字段统一 label 为"客服电话"（对外），普通可编辑；申请人手机不进表单（身份在账户层）。

### 8.6 BFF 错误吞没修复（v2.2.0 新增）

**问题：** `ApiClient.PostAsync<T>` 对非 2xx 一律 `catch→return null`，且 `/mobile/merchants/apply` 忽略返回值固定 `Results.Ok(200,"申请已提交")`——导致 API 抛的所有业务错误（`该商家已被他人认领`/`已认证无法认领`/`新建撞名` 等）在 BFF 被双重吞掉，前端看到**虚假成功**。

**修复：** `ApiClient` 新增 `PostWithResultAsync<T>`（非 2xx 读取上游 ProblemDetails 的 status/title/detail/extensions，返回带状态码与错误码的结果），`/apply` 据此成功透传 `merchantId`、409 转发结构化冲突、其余 4xx/5xx 按码透传。旧 `PostAsync` 保留不动，零波及其它端点。

- Logo 落 `uploads/merchants/logo`（v2.8.0 起经 `IObjectStorageService` 写 MinIO/本地盘），与维护页 `logoUrl` 字段一并保存；上传端点仅回 URL。

### 8.8 申请人自助撤回：渠道打标 + 分支清理（v2.3.0 新增）

**决策：** 新增 `Merchant.ApplicationMode`（None/Self/Claim/Nomination）渠道打标列 + `POST /api/merchant/{merchantId}/withdraw` 自助撤回端点；撤回清理策略按渠道分支：**Self 硬删**（商户+成员行）、**Claim 软移除**（认领人成员 Removed + `RevertClaimedToCrawler` 退回认领池）、**Nomination/None 拒绝**（提名草稿不走此入口）。守卫 = `Pending` + 调用者为该商户在职 MerchantAdmin。

**理由：**
1. 待审核期间用户无自助撤销通道，只能等人工审核，填错资料/撞名引导后想改填的场景被卡死；
2. "撤回"对不同渠道的数据后果完全不同：Self 商户是本次申请新造的行，留着就是未公示的僵尸数据，还会干扰 4.1.1 新建查重（名称/信用代码精确匹配会命中它），故**硬删**；Claim 商户本就属于爬虫/平台，删除会毁掉既有数据，只能解除认领关系并把两轴状态还原（来源回 Crawler → 重新可被 Sync 覆盖 + 无在职成员 → 重新入认领池），故**软移除 + 回退**；
3. 渠道信息此前无处落库（Draft 状态仅提名新建有、Pending 无法区分 self/claim），故需新增打标列而非推断——历史/爬虫数据默认 None 即天然兼容，无需回填；
4. 提名（Nomination）撤回涉及邀请作废（StaffInvitation.Revoked/Expired 状态机）且发起人并非商户成员，语义与"申请人撤自己的入驻申请"不同，不并入此入口，拒绝处理留待提名取消专项。

**实现方式：**
1. Domain：`ApplicationMode` 枚举 + `Merchant.MarkApplicationMode()`/`RevertClaimedToCrawler()`；迁移 `AddMerchantApplicationMode`（integer 默认 0）。
2. Application：`WithdrawApplicationCommand/Handler`（守卫 + 分支清理）；apply self/claim 与 nominate 新建路径打标。
3. API：`MerchantApplicationEndpoints` 新增 `POST /{merchantId:guid}/withdraw`；失败均 400（中间件映射 `InvalidOperationException`）。
4. BFF/Taro：`/mobile/merchants/{id}/withdraw` 代理（`PostVoidAsync`）+ 商户页 Pending 卡左滑"撤回"操作条（SwipeCell，二次确认 → 刷新列表）。

### 8.9 审批主流化：详情抽屉 + 结构化拒绝 + 并发 409 + 站内信（v2.5.0 新增）

**决策：** 对齐主流平台入驻审批（淘宝/美团商家后台）：(1) Admin 审批页升级为**详情抽屉**（先看全资料再决策，爬虫历史比对内嵌），拒绝原因升级为**预设分类 + 补充说明**；(2) approve/reject 加**并发守卫**，后提交者收 409；(3) `companyName` 必填（self/claim/accept）；(4) 审核结果与提名进展经领域事件落**站内信**（写扩散），Taro 消息中心 + TabBar 角标消费；(5) 客服电话预填登录账号手机号（修订 v2.2.0"不预填"决策——主流平台默认填申请人手机，商户可改 400/座机）。

**理由：**
1. 原列表 7 字段无信用代码/执照/渠道信息，审核等于盲审；企业名称选填导致大量空值行（截图实证"公司全称 -"）；
2. 双管理员同开审批页时旧实现后提交者收 400"当前状态为 Active，无法审核"（领域守卫异常被中间件映射 400），冲突语义应为 409 且前端可自动刷新；
3. 审核结果此前无触达通道，申请人只能回页面轮询；`INotificationService` 早有占位接口，借领域事件设施（`BaseEntity.DomainEvents` + `UnitOfWorkBehavior` 提交后 Publish）落地，零新增依赖、不引入 MQ（单进程小流量，跨进程队列属过度设计）；
4. 通知写入在提交后发布且失败仅记日志——审核结果强一致优先，通知漏发可人工补，业务回滚不可接受；
5. 根因修复：Admin 审批按钮不显示并非镜像问题，是 `ToPublicDto` 漏映射 `Status`（徽标走兜底分支看似正常、按钮条件恒 false），补映射并加真实状态分支。

**实现方式：** 见 4.6（站内信链路）、4.2（抽屉/分类/409）、7 汇总表（实体/端点/DTO）。

### 8.10 被拒自助通道：点击重提 + 左滑删除（v2.6.0 新增）

**决策：** 被拒申请给申请人两条自助出路——**点击卡片=修改并重新提交**（原单预填、resubmit 回 Pending）、**左滑=删除记录**（与撤回同构清理）；不做"删掉再重新申请"的隐式路径替代。

**理由：**
1. 根因死角：self 被拒后跳空白向导再提交，会撞自身商户行的查重（申请人仍是其在职管理员）→ 恒 400 永久卡死；此前"可重新提交"文案与代码行为不符；
2. 原单保留重提（主流平台一致做法）：审核记录/站内信 bizId/认领关系连续，不产生重复商户行；"删了重建"会丢历史且 claim 渠道重建等于把商户退回公共池再抢一次，语义混乱；
3. 重提与撤回的清理完全同构（都发生在商户"未生效"期），差异只有状态守卫——提取 `ApplicantApplicationCleanup` 单一实现，避免两处分支随渠道扩展漂移；
4. 交互位复用 v2.3.0 已验证的 SwipeCell 与"Pending 左滑=撤回"心智：左滑恒为销毁类操作，点击恒为主操作，用户零学习成本。

**实现方式：** 见 4.1.3（三端点与守卫）、7 汇总表（领域方法/命令/端点/BFF/Taro 行）。

### 8.11 材料按类型分层随单审：审核"换弹药"不换骨架（v2.7.0 新增）

**决策：** 入驻审核从"名称+电话盲审、执照事后独立排队"升级为"申请单一次审结、材料按商家类型分层要证据"；实体泛化（一张 MerchantDocuments 表承载多类材料），而非新建材料表 + 保留旧执照表双轨。

**理由：**
1. 平台定位决定审核对象：找货信息平台保护的是**供给数据可信度**，轴承行业最大信任风险是"冒充授权经销商"（水货/假货经授权商名义流通）——授权书是唯一对症的证据，必须进申请单而非事后补；
2. 主流同构（企业店入驻=资质随单审 + 经营范围分层材料）；"空单先过再审材料"三段式让审核人第一轮无法判真伪，队列还割裂（执照批了认证点不了，两边口径不闭环）；
3. 泛化单表而非双轨：材料类型是枚举维度不是实体维度，新加"工厂视频/门头照"只是加枚举值零迁移；双表会复制状态机、级联与队列三套逻辑；
4. 骨架不动：三渠道状态机/撤回/重提/删除/成员表全保留，仅"审什么、凭什么审"变化——重提通道的"存量 Approved+新补"合并判定直接复用 v2.6.0 原单语义；
5. 授权书/厂房照属敏感经营材料，不进 C 端 DTO，泄露面收口在成员与审批侧。

**实现方式：** 见 4.7（矩阵与级联全貌）、7 汇总表（实体/命令/端点/三前端行）。

### 8.12 信息纠错闭环：结构化字段级 + 事件驱动通知 + 积分预留（v2.15.0 新增）

**背景：** 纠错是数据可信度平台的社区共建引擎，但后端（CorrectionRequest 实体/审批自动应用/覆盖保护）与前端（Taro 占位 toast）之间存在三处断链：BFF 无代理、Admin 页只读无审批 action、审批结果不通知提交人。

**决策：**
1. 字段级结构化纠错（对标高德报错）：表单为"选字段 → 核对当前值 → 填应改为"，字段清单由后端 fields 端点下发且与审批 Apply switch 严格同集合——用户能提交的每个字段，采纳后都真正生效；
2. 采纳即自动应用：Approve 按 FieldName 分发到实体 Update 方法并置 DataSource=Manual（人工纠错不被爬虫覆盖，纳入 8.7 总原则）；
3. 结果触达走领域事件：CorrectionProcessedEvent → 站内信订阅者；**积分奖励同事件扩展**——采纳加分的订阅者待 P8 积分体系落地时新增，审批链路零改动；
4. 去重守卫：同用户同实体同字段存在待审纠错时幂等拒绝（与邀请去重同思路），防刷审核队列。

### 8.13 认领接管重置经营性数据：商品/旧证照/待邀请三连清（v2.16.0 新增）

**背景：** "认领=真人接管"的语义此前只落到联系方式字段；商户名下的经营性数据（爬虫在售商品、上一任认领人的证照与邀请）原样继承，违背"互联网数据不可信"总原则且有隐私/越权隐患。

**决策：**
1. 接管即重置经营面：在售商品关联清空（认领人经"商品管理"从零自建，对标高德/美团认领后菜单自建）；旧认领人证照清空（个人申请资料不向新认领人泄露）；Pending 邀请一律 Revoke（防旧邀请人接受后混入新商户成员）；
2. 提名通道对齐：仅"提名已有商家"（预认领语义）同步重置；Draft 提名不清——发起人随单材料是本次申请的一部分，非前任遗留；
3. 关注关系不清：UserMerchantFollow 属买家用户自己的数据，店铺易主关注保留是主流行为；
4. 替代品不涉：BearingInterchange 是平台级"轴承↔轴承"映射，不随商户接管变动，其数据可信度走 DataSource 覆盖保护 + Sync 人工审核既有通道。

**实现方式：** ApplicantApplicationCleanup.ResetOperationalDataForTakeoverAsync 单一实现（与撤回清理同 helper 家族），ExecuteDelete 批量清商品/证照 + 逐条 Revoke 邀请保状态历史，UnitOfWork 统一提交。
