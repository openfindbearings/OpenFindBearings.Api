# 游戏中心设计 v1.0.0

> 版本：v1.0.0 | 日期：2026-09-27 | 上一版：无（首版）
> 定位：平台小游戏聚合入口（游戏中心）的架构决策、接口契约与合规口径留底。

---

## 一、定位与合规判断

- 游戏中心 = 个人"轴承币"的活跃奖励场景之一（签到/纠错同性质），不是收益渠道。
- 合规三红线沿用积分体系：不可充值、不可提现、不可转让；游戏发分**不进商家金 trickle 白名单**（娱乐被动收益与登录签到同类排除，防店铺农场刷金库）。
- 防刷口径：低额封顶（每局 5 币、日上限 10 币）+ 服务端幂等（bizId=minigame:{gameId}）+ 规则表日限截断。原型期客户端信任制（不验游戏过程，与签到可脚本化同风险等级，奖励小到无利可图）。
- 版权口径：连连看/数独/2048 均为公共玩法机制（思想/表达二分法，玩法不受版权保护）；全部 UI 自绘、题库用平台自有轴承数据与图片，零第三方素材。

## 二、架构决策：方案 A 进程内插件（微服务形状）

**决策**：不建独立微服务；API 内以 `IGameProvider` 插件接口 + 统一端点组实现"微服务形状"，将来可整组平移。

| 对比项 | 方案 A（现行） | 方案 B（微服务，暂缓） |
|---|---|---|
| 发分链路 | 进程内直调 PointsService（同库事务域，幂等/日限天然生效） | 需服务间认证调主 API 发分口（复用 sync-client 模式），多一条可断链路 |
| 基建 | 零新增 | 新项目+镜像+CI+K3s 资源（约一天且长期维护） |
| 资源隔离 | 端点全轻量（每局 1 次随机查询 + 1 次发分），不与主链路争抢 | 完全独立 |
| 拆分成本 | 低：接口+端点组+注册表即"平移单元"清单 | — |

**升级 B 的触发条件**（满足任一再拆）：游戏 ≥3 款且迭代频繁；出现重计算游戏（AI 对局/服务端权威状态）；实测游戏流量影响主 API P99。

## 三、接口契约

### API（OpenFindBearings.Api）

- `IGameProvider`（Application.Services）：`Key` / `DisplayName` / `GetBoardAsync(userId, size, ct)` / `ReportResultAsync(userId, payload, ct)→实发分`。实现纪律：轻量查询、发分必须走 PointsService 幂等+规则日限。
- 统一端点（Api.Endpoints.GameEndpoints，登录）：
  - `GET /api/games/{key}/board?size=` → 出题（未知 key 404）
  - `POST /api/games/{key}/result` → 结算发分 `{granted}`
- DI：每游戏一条 `AddScoped<IGameProvider, XxxProvider>()`，端点按 Key 路由——加游戏=加一个类+一条注册，不动主链路。
- 连连看 Provider（LinkupGameProvider）：题库 `IBearingRepository.GetRandomWithImageAsync`（有图+类型打散，防"照片脸盲"）；结算 payload={gameId}（客户端每局 uuid）。
- 规则种子（迁移 AddMinigame）：`minigame` 规则 5 币/局、日限 10，Admin 积分规则页可调。

### BFF（OpenFindBearings.Mobile）

- **通用代理**（GameEndpoints）：`GET/POST /mobile/games/{key}/board|result` JsonNode 原样透传——将来加游戏或游戏拆微服务，BFF 零改动。

### Taro

- 注册表 `services/games.ts` GAMES：key/name/desc/icon/route/status（available|comingSoon）。游戏中心页由注册表渲染，数独/2048 占位置灰。
- 游戏页 `pages/games/linkup.tsx`：6×6 棋盘 18 对、≤2 折路径消除（0/1/2 折三段式）、死局自动重排、120s 限时、提示高亮、胜利弹层显示实发分。
- 入口：我的页四宫格"游戏中心"（原"设置"位，设置仍在 NavBar 右上角）。

## 四、三端兼容口径

- 仅用 View/Text/Image + flex + absolute 弹层 + setInterval + 百分比宽度——weapp/RN/H5 原生支持；无 canvas/SVG 依赖（瓷片=图片+文字）。
- 图片瓷片加载失败 onError 降级为型号大字块（部分老数据无图不影响开局）。
- 已验证：build:h5 ✓、build:weapp ✓、build:rn（Metro bundle）✓；图标名 Grid3x3/Puzzle/Layers/Trophy/Timer 两端 lucide 0.378 均存在。
- 小程序上线前置（全 App 共性，非游戏特有）：request 合法域名配置 + Identity OAuth web-view 业务域名。

## 六、真机反馈修正（v1.0.0 同批增量）

- **题库图片口径**：3D 渲染图优先 → 不足用 2D 图纸补足 → **无任何图片一律不入选**。旧版过滤只判 null 未排空字符串，导致大量空瓷片（真机截图实锤），已修。
- **瓷片形态定案**：图+型号小字（用户曾提"纯图片"后收回——"玩着玩着就认识型号"是教育卖点）；脏数据漏网时防御分支退型号字块，不出空瓷片。
- **动态棋盘**：题数不足 18 对时按实际对数排行数（6 列定宽、尾行留空），3D 池小也能开局。
- **死局重排修复**：原实现整盘重建会复活已消除对，改为只重排剩余块放回原位。
- **路径算法澄清**（2000 局模拟背书）：满盘开局最多 8 对可连通（典型 3~5 对），"只能消少数对"是连连看标准规则非 bug；外圈可绕行（顶行隔格 2 折连通合法）。
- **商城目录 bug**：公开 /api/mall/items 输出漏 targetKind（只有 Admin 侧有），前端 ?? 1 兜底把寻货置顶卡误标"商家金"——已补透传。
