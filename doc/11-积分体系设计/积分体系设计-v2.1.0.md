## 1. 定位与合规红线

### 1.1 定位：生态货币与数据共创引擎

本平台无交易闭环、供给靠"数据清洗 + 商户自维护"，积分不是营销赠品，而是驱动整个生态飞轮的**生态货币 / 数据共创引擎**：

```
用户共创（纠错 / 维护数据 / 寻货应答）赚积分
    → 兑换平台权益（置顶、次数包、装扮）与商家挂礼（实物礼品）
        → 商家获得礼品页曝光与真实收货线索（B2B 获客）
            → 商家更愿意维护数据、挂出礼品、参与共创
                → 数据更好 → 用户更多 → 闭环加速
```

积分账本（PointTransactions）是这条飞轮唯一的价值计量单位：赚端记录"谁为平台贡献了什么"，花端记录"平台/商家回馈了什么"。

### 1.2 合规三禁（代码层写死，非文案承诺）

1. **不可充值**——系统不存在任何资金换积分的入口，`PointsService` 没有充值方法，余额只能由发放规则产生
2. **不可提现**——无提现端点、无积分换资金通道，商家礼品收入积分也永不开 RMB 结算
3. **不可转让**——无账户间转账方法，积分只能本人赚、本人花

**为什么商家收入积分永不开 RMB 结算**：一旦开放"积分 → 人民币"，立即触碰支付牌照与预付卡备案红线；且必然催生黑市收分套利（低价收分 → 平台高价套现），摧毁整个积分定价体系。三禁不是保守，是这套体系能长期存在的前提。

**兑换定性**：商城兑换 = 服务折扣 / 权益兑换，不是货币购买行为。

**商城页文案（精确表述，不得含糊）**：

> 积分不可转让、不可提现，兑换结算仅在平台内流通。礼品质量责任在商家，平台为信息中介。

## 2. 游戏币类比：欲望设计四支柱

### 2.1 欲望本质：不是"分值钱"，是心理机制

游戏币（魔兽金币、原神原石、王者荣耀点券）让玩家拼命想要的本质，**从来不是币本身值钱**——它们同样不可提现、不可换 RMB。欲望来自四根支柱：

| 支柱 | 一句话定义 | 反例（缺了会怎样） |
|---|---|---|
| 赚得可见且被庆祝 | 每次获得都有即时、醒目、带情绪的正反馈 | 默默加分 = 用户不知道自己有分，体系隐形 |
| 花得有意义且诱人 | 消耗口是"想要的东西"，不是"被扣的罚款" | 只有扣分场景（超额发布）= 积分是债务不是资产 |
| 地位可见 | 积分/成就转化为他人可见的身份信号 | 分数只有自己看得到 = 无法社交比较 = 无炫耀动力 |
| 稀缺真实 | 限量、限时、绝版的东西是真的拿不到 | "人人都有"的徽章 = 没有徽章 |

**本平台为什么必须靠四支柱而非 monetary value 制造欲望**：积分没有变现出口（三禁），"1 分 = X 元"的锚定不存在，也无法建立。若只靠"分值钱"驱动，用户第一次算账（20 分纠错 ≈ 无法兑现）就会流失。四支柱提供的是**心理价值**——被庆祝的爽感、兑换的期待、徽章的荣耀、绝版的焦虑——这些不需要 RMB 锚定也成立，且是游戏行业验证过三十年的成熟方法论。

### 2.2 支柱一：赚得可见且被庆祝

赚分动作必须有仪式感，对应玩法（详见第 8 章）：

- G1 积分暴击/双倍掉落：纠错 20 分有 10% 概率暴击 40、2% 概率传说 100，客户端播放暴击动画——把"审核采纳"这个延迟反馈变成开宝箱
- G2 每日任务板：签到 + 1 次纠错 + 1 次应答全完成额外 +30，给用户"今天上线要做的事"清单
- G3 连签里程碑：7/30/100/365 天节点大额奖励 + 徽章，把日活习惯变成收集进度

已实现基座中的庆祝反馈：签到成功长震动 + toast "+N 积分"、任务中心 7 格日期条（漏签一眼可见）。

### 2.3 支柱二：花得有意义且诱人

- G4 限时橱窗/闪购：每周限时折扣 SKU（置顶卡半价等），制造"这周不换就亏"的紧迫感
- G5 积分抽奖/扭蛋：50 分一抽，奖池含置顶卡/次数包/限定徽章/积分返还——小额积分的娱乐化出口
- 商城实体（第 5 章）：虚拟权益（置顶、装扮）+ 商家实物挂礼，让大额积分有明确的"想要清单"

原则：消耗口必须是用户**主动想要**的东西。寻货超额扣分是"罚款型"消耗（必要但不产生欲望），商城才是"欲望型"消耗——两者比例决定积分体系的情绪基调。

### 2.4 支柱三：地位可见

- G7 等级/称号：累计积分 → Lv1-10，挂在个人资料页、寻货应答署名、纠错署名旁——B2B 场景里"Lv8 老用户"的应答天然更被信任
- G8 成就徽章墙（第 7 章）：个人徽章排 + 商户徽章排，商户徽章直接变成 B2B 信任资产
- G9 排行榜 + 赛季：月度赚分 Top 榜 + 赛季称号

### 2.5 支柱四：稀缺真实

- G10 赛季重置：赛季榜单每月清零，上赛季称号绝版
- G11 限量徽章："创站元老"（前 100 名注册用户）永久绝版，之后注册的人**真的**拿不到——这是 WoW "Feats of Strength"（光辉事迹）机制：不可复得的成就比高难成就更能制造 longing
- 限时/限量 SKU：闪购橱窗售完即止，不搞"补货"

稀缺的前提是**执行纪律**：说绝版就绝版，说限量就限量。一次"应广大用户要求返场"就摧毁整个支柱。

## 3. 已实现基座（与代码同步）

本章为代码事实记录（grounding 于 v1.36.1 之后的当前代码），后续所有设计均以此为地基。

### 3.1 数据模型（四表）

| 表 | 职责 | 关键约束与结构事实 |
|---|---|---|
| `PointAccounts` | 一人一户：Balance / TotalEarned / TotalSpent / LastCheckinDate / ConsecutiveCheckinDays | `UserId` 唯一索引；余额守卫在实体 `Debit` 内（不足抛异常）；**无并发令牌**（见 3.6） |
| `PointTransactions` | 收支流水（账本唯一事实源）：Direction（1 入账 / 2 出账）/ GrantType / Amount（恒正）/ BalanceAfter 快照 / BizId / Remark / ExpireAt | `BizId` **部分唯一索引**（仅非空行，`UX_PointTransactions_BizId`）承担幂等；`UserId+CreatedAt` 与 `UserId+GrantType+CreatedAt` 查询索引；**ExpireAt 预留未启用**；**无批次（lot）明细**——将来做过期只能按时间窗整批过期，无法 FIFO 按笔核销 |
| `PointGrantRules` | 赚分/定价规则：GrantType / DisplayName / Amount / DailyLimit / LadderJson / IsEnabled / Description | `GrantType` 唯一；Admin 实时可改（`GrantAsync` 每次实时读表，量小不缓存） |
| `PointRewardClaims` | 一次性奖励防刷台账：BizKey / GrantType / FirstClaimerUserId | `BizKey` 唯一索引即幂等防线；键 = 跨账号不变量（手机号/统一社会信用代码）；**注销不清**（流水随注销删除，台账是平台防刷底账永久保留，仅存键与归属快照，不含可扩展 PII） |

台账键方案：`phone:{手机号}:register`（注册奖励）、`credit:{信用代码}:approved|profile|product`（入驻/资料完善/首件上架）；无号回退 `user:{userId}:register`、无照回退 `merchant:{merchantId}:approved`（或跳过发放，见 3.3）。

迁移：`AddPointSystem`（三表 + 五条默认规则种子，幂等 NOT EXISTS——存量库 SeedData 短路，规则种子必须走迁移）→ `AddPointRewardClaims`（台账 + 存量认领回填 + 商户两任务规则 + register_bonus 停用）→ `AddSourcing`（寻货两条定价规则）→ `AddBusinessTimeZoneAndCorrectionScore`（业务时区配置种子 + 纠错分值存量 10→20 对齐）。

### 3.2 PointsService 单一写入入口

`IPointsService`（Application/Services）→ `PointsService`（Infrastructure/Services），全系统唯一的积分写入口：

- **GrantAsync(userId, grantType, bizId, remark)**：规则开关检查 → BizId 幂等检查 → 日上限截断（发放到剩余额度为止，`SumTodayByTypeAsync` 按业务日界统计入账流水）→ 开户/入账 → 写流水（带 BalanceAfter 快照）→ 独立提交。**任何失败吞掉返回 0**——积分是附属账本，绝不反噬业务主流程（登录/审批/上架链路对积分失败无感，仅记 Warning 日志）
- **GrantOneTimeAsync(userId, grantType, claimKey)**：先向台账 `TryClaimAsync`（INSERT ON CONFLICT DO NOTHING 原子占坑），占到坑才调 GrantAsync（流水 bizId 同写 claimKey 做第二道幂等）——注销重注册（userId 变、手机号不变）、删店重入驻（merchantId 变、信用代码不变）循环免疫
- **DeductAsync(userId, sceneType, amount, bizId)**：余额不足**抛业务异常**（用户可感知，调用方转 400）；bizId 非空时先做幂等检查；扣减与流水同 `UnitOfWork` 提交
- **CheckinAsync(userId)**：`MarkCheckedIn` 推进连击（签到日 = 昨天则 +1，断签重置 1）→ 阶梯取档（LadderJson 按连续天数取，超末档恒取末档）→ 同日重复返回已签态；日键与连签基准用 `BusinessClock`（v1.36.1 日界修复：北京时间早 8 点前签到不再撞昨日 UTC 键漏发分）
- 时序纪律：赚分调用点均在业务事务提交后（事件订阅者）或无事务上下文（中间件/签到命令），故与 NotificationService 同款——Add 后显式 `SaveChanges` 独立落库；扣分调用点（寻货）在业务命令事务内，与建单同 `UnitOfWork` 窗口原子提交

| 动作 | GrantType | 分值 | 触发点 | 幂等/台账键 |
|---|---|---|---|---|
| 每日登录 | `daily_login` | 1 | `UserContextMiddleware` JIT 链路（当日首次请求，被动保底） | `daily_login:{userId:N}:{业务日键}` |

登录与签到并存（B站模式）：登录被动小额保底、签到主动阶梯大分，双习惯培养。

### 3.5 业务日界 BusinessClock

`Domain/Services/BusinessClock`（静态类）是全项目"今天"语义的唯一出口：

- 启动时 `Program.cs` 读 SystemConfig `Business.TimeZoneOffsetHours`（默认 +8 北京时间）调用 `Configure`；合法范围 -12~+14，越界忽略保留默认；**改配置需重启生效**（滚动期各副本日界不一致会导致幂等键漂移、部分用户当日双发）
- 提供 `Now / Today / TodayUtc / YesterdayUtc / Offset / DateKey`：DB 存储与写入仍纯 UTC（DateTime.UtcNow 规范不变），但签到日键、每日登录日键、日上限统计（`SumTodayByTypeAsync` 以 `TodayUtc` 起算）、任务完成态一律按业务日界
- WordPress options 式配置哲学：业务日界由管理员定义，不读服务器时区、不读 DB 会话时区（容器默认 UTC、连接串钉死 Timezone=UTC，读了必错）

### 3.6 已知缺陷与风险（如实记录）

| 级别 | 缺陷 | 事实与后果 | 处置 |
|---|---|---|---|
| **P0** | **PointAccounts 并发令牌缺失**——所谓"乐观并发"名不副实 | `PointConfiguration.cs` 未给 PointAccount 配置任何并发令牌（无 `xmin`、无 RowVersion 列）。`DeductAsync` 是读-改-写（读账户 → `Debit` → `UpdateAsync` → SaveChanges），两个并发扣减请求各自读到同一 Balance，后写覆盖先写（lost update）：用户并发双花只扣一次的钱，或余额快照错乱。BizId 幂等索引救不了——寻货扣分的 bizId 传 null，商城场景两笔扣减本就是不同 BizId | **商城（任何高频扣分场景）上线前必须补**：`builder.Property(p => p.Xmin).IsRowVersion()`（PostgreSQL 系统列，零迁移成本）+ `DbUpdateConcurrencyException` 捕获重试（2-3 次退避）或转原子 UPDATE ... WHERE Balance >= amount |
| **P1** | `AddPointSystem` 迁移中 correction_adopted 种子 SQL 语法损坏 | 该行现状为 `'correction_adopted', '', 纠错被采纳', 20, 100, ...`——DisplayName 变成空串后跟未加引号的中文与游离单引号，PostgreSQL 解析必报语法错误。存量库不受影响（迁移已执行过、被历史表短路），**全新安装库跑迁移即失败** | 修复引号恢复合法 SQL（Amount 保持 20，与后续对齐迁移无冲突——`AddBusinessTimeZoneAndCorrectionScore` 只 UPDATE 仍为 10 的存量行）。同时记取教训：该文件曾在应用后被就地编辑（10→20），违反"已应用迁移不可变"原则，此类存量对齐一律新开迁移 |
| P2 | `UserContextMiddleware` 注释陈旧 | 每日登录发放处注释仍写"bizId 含 UTC 日期"，实际 v1.36.1 起已用 `BusinessClock.DateKey`（业务日） | 下次触碰该文件时顺手订正 |

## 4. 消耗/燃烧口设计

### 4.1 寻货超额（已实现，首个真实消费场景）

额度模型：**免费额度（SystemConfig 可配）→ 积分加量（规则表单价）→ 硬上限拒绝（不可买）**：

| 动作 | 免费额度 | 积分加量 | 硬上限/天 |
|---|---|---|---|
| 发布寻货 | 3 条/天（`Sourcing.FreePublishPerDay`） | 20 分/条（`sourcing_publish_bonus`.Amount） | 10（DailyLimit） |
| 应答寻货 | 20 条/天（`Sourcing.FreeRespondPerDay`） | 20 分/条（`sourcing_respond_bonus`.Amount） | 50（DailyLimit） |

- **NEED_POINTS 协议**：超限且未确认时 API 以 400 文案 `NEED_POINTS:{分值}` 回传，前端弹"花 X 积分发布/应答"确认后带 `usePoints=true` 重提交
- **DeductAsync + 建单同 UnitOfWork**：扣分与需求/应答行创建在同一命令、同一事务窗口内原子完成（扣分成功建单必成、建单失败扣分回滚）。**这是积分留在 API 进程内的核心理由**——拆成独立积分服务即变分布式事务，单人项目不可维护
- 防绕细节：发布计数含已取消单（防发了删删了发绕额度）；重复应答 = 更新既有不占额度不重复扣分；硬上限用规则表 DailyLimit 表达，Admin 可调

### 4.2 积分商城（设计见第 5 章）

虚拟权益 + 商家挂礼两类 SKU，是"欲望型"消耗主战场。

### 4.3 消耗口薄是天然抗套利

当前及可预见的消耗结构里，付费段（超额寻货、商城大额兑换）只对**重度用户/商家**存在；多数商家永远用不到付费段（免费 3 发布/20 应答足够）。这意味着：

- 刷分的变现路径极窄（无提现、无转让、消耗口有限）
- 套利者刷 1000 分的"收益"只能是几张置顶卡——攻击动机被结构性压死
- 不需要为防套利预先建设重型风控，四闸（5.4）+ 台账 + 日上限已覆盖已知攻击面

**设计纪律**：新增消耗口时保持"罚款型少、欲望型多"的比例；任何消耗口定价都从规则表走（Admin 可调），不散落硬编码。

## 5. 积分商城设计

### 5.1 三类 SKU 来源

| 类 | 内容 | 履约 | 决策 |
|---|---|---|---|
| A 平台虚拟权益 | 寻货置顶卡 24h/72h、寻货次数包、头像框/昵称装扮 | 自动履约（下单即写权益字段，零物流零人工） | **做**（M1-b） |
| B 商家实物挂礼 | 商家把自己的 `MerchantBearing` 商品挂进商城当礼品（如样品轴承、周边），商家自发货 | 人工履约（订单状态机 + 物流单号） | **做**（M1-c，gated by 5.2 决策） |
| C 平台自营实物 | 平台采购实物做奖品库 | 平台发货 | **不做**——涉及资金采购、库存、物流、发票，违背三禁精神且单人不可运维 |

### 5.2 燃烧模型 vs 结算模型（P0 未决，gate M1-c）

用户兑换**商家挂礼**时，扣掉的积分去哪？两种模型，必须在 M1-c 开工前拍板：

**燃烧模型（审计推荐）**：用户兑换商家礼品，积分**直接烧掉**（流水 Direction=出账，不进任何商家账户），不结算给商家。商家的收益 = 礼品详情页曝光带来的流量 + 兑换人收货信息（姓名/电话/地址 = **真实 B2B 线索**，商家自发货时天然获得）。本质：商家用一件礼品换一条精准客户线索，等价于用实物支付广告费。

**结算模型**：积分托管（下单扣分入托管池）→ 用户确认收货后 → 积分入商家账户，商家可用这些积分买置顶、次数包、兑别家礼品。

**燃烧模型一次性消灭的问题清单**：

| 问题 | 结算模型下的形态 | 燃烧模型下 |
|---|---|---|
| 商家账户归属悖论 | `PointAccount` 唯一键是 UserId，商家是组织（多成员、成员会入职离职）——结算积分记到哪个 UserId？入驻人？操作人？归属随人员变动漂移。**必须新建按 MerchantId 键的商户积分账户实体（不得复用 PointAccount）** + 商户维度流水 | 不存在（没有商家积分账户） |
| 结算写入/追回 | 确认收货写商家账户、退款要从商家账户追回（余额可能不足 → 负余额或守恒破坏） | 不存在（退款 = 平台侧原路退用户，无追回链路） |
| 月结算上限与滚存 | 防挂礼量产积分需设单商户月结算上限，超限滚存次月——又一张表又一套 Job | 不存在 |
| 退款守恒 | 已结算后仲裁退款：积分既退了用户又已在商家手里，凭空多出一份 → 需要追回或平台垫付 | 不存在（未结算给任何人，退用户即守恒） |
| 结算侧刷分 | 商家自兑自礼品 = 无成本量产积分（需防刷四闸全套） | 无积分可刷（自兑仍要防——防刷单冲兑换榜/污染线索质量，见 5.4 闸一） |
| 结算后翻案纠纷 | "确认收货 7 天后发现质量问题"——积分已结算，翻案要跨账户追回，纠纷复杂度指数级 | 纠纷窗口内退用户即可，商家损失 = 一件礼品（其获客成本），权责清晰 |

**结算模型的唯一优势**：商家有积分资产沉淀，挂礼动机更强（"卖礼品赚积分买置顶"形成商家侧内循环）。

**审计推荐燃烧**，理由：商家的真实欲望是**客户**不是积分；收货信息的线索价值（一个精准的轴承采购方）远高于礼品积分价值；燃烧模型实现面小一个数量级（无商户账户、无结算 Job、无追回逻辑），对单人开发 + AI 维护的项目结构，复杂度就是风险。**本决策 gate M1-c 全部开发**（见第 11 章；该 P0 已在 6.8 落定为结算模型）。

### 5.3 兑换订单与状态机

```
下单（扣分）→ 待发货 → 已发货 → 已完成
                │           │
                │           └→（纠纷）→ Admin 冻结 → 原路退分/驳回
                └→（72h 未发货）→ 已取消（全额退分）
```

- **虚拟权益单**：下单扣分后自动履约（写 PinnedUntil / 发次数包 / 挂装扮），无发货环节，状态直接到已完成
- **实物挂礼单**：积分托管概念——扣分即离开用户账户，但未到"完成"前均处于可退状态（燃烧模型：退回 = 冲销燃烧；结算模型：退回 = 托管池退用户）
- **72h 未发货自动取消**：全额退分（Job 或惰性触发），保护用户不被挂空单
- **发货后 7 天自动收货**：发货满 3 天起提醒用户确认；用户可延长收货一次（+3 天）；可点"报告未收到"→ 订单冻结转 Admin 仲裁
- **纠纷处理**：Admin 冻结订单 → 调查（物流单号/双方陈述）→ 原路退分（全额/部分）或驳回解冻

### 5.4 防刷四闸

| 闸 | 规则 | 防的攻击 |
|---|---|---|
| 闸一 自兑自排除 | 兑换人是挂礼商家的商户成员（在职）→ 禁止兑换；成员状态 Active 与 Suspended 都拦；**Removed 成员设回看窗**（脱离后 30 天内仍禁兑，防"开除小号"过闸） | 结算模型：自买自卖量产积分；燃烧模型：刷单冲兑换热度榜、污染线索数据 |
| 闸二 月结算上限 | 单商户每月可结算积分封顶，超限滚存次月（**仅结算模型需要**；燃烧模型此闸天然不存在） | 商家批量挂低价礼品量产积分 |
| 闸三 收货信息去重 | 收货地址/手机号**规范化后**（去空白、统一大小写、地址拼接省市区）做去重键：同地址或同手机号每月限兑 3 单实物 | 一人多账号批量兑换薅礼品/刷线索 |
| 闸四 单价上限 + 先审后上架 | 商家礼品积分价**由平台审核定档**（商家申报 → Admin 核定），设单件积分价上限与下限：下限防"1 积分换千元货"恶性倾销冲榜，上限防天价礼品套现信誉；商家不可自行改价 | 定价权旁落导致的榜单操纵与套利 |

### 5.5 结算时点（仅结算模型）

下单扣分 → 积分入托管池 → 商家发货 → 用户确认收货**或** 7 天自动收货 → **此刻**积分入商家账户。纠纷窗口内冻结的订单不结算，仲裁后退用户。原则：积分只在"货真实到达用户手中"后才离开托管态——任何提前结算都会把退款守恒问题引回来。

### 5.6 运费口径

**M1 仅包邮**。平台无支付能力（三禁），无法代收运费；"到付/不包邮"意味着用户要掏现金——积分商城里出现现金支付是死路（破坏定性、引发纠纷、无法对账）。商家的运费成本**计入礼品积分价**，由闸四审核时核定合理性。

### 5.7 售后与纠纷

- **不支持七天无理由退货**：兑换不是买卖（不适用消法七天无理由），页面与条款明示
- **质量问题走 Admin 仲裁**：全额退分 / 部分退分 / 驳回三种裁决；结算模型下受退款守恒约束（已结算的追回或限窗口内裁决）
- **条款文案**："礼品质量责任在商家，平台为信息中介"——平台不担保实物质量，只提供仲裁通道

### 5.8 商家收入积分的使用限制（仅结算模型）

商家结算所得积分**只能在平台内花**：买寻货置顶、寻货次数包、兑换其他商家的礼品。永不兑现 RMB（见 1.2）。商家积分账户（MerchantId 键）与个人 PointAccount（UserId 键）物理分离，两套流水两套余额，不复用实体。

### 5.9 寻货置顶卡

- **平台统一定价**（非拍卖、非商家定价）：24h 置顶 100-150 分、72h 置顶 250-400 分（锚定推导见 10.2），Admin 可调
- **有时限**：购买写 `PinnedUntil`（UTC 时刻），到期自动回落普通排序（读时惰性判定，与寻货过期同款模式，不加 Job）
- **置顶区排序**：多条置顶之间按**购买时间**排序（先到先展示，不搞竞价）
- **"置顶"角标保透明**：置顶结果必须带角标，与自然结果明确区分——不欺骗用户，也保护置顶的信誉价值
- **满位拒绝**：置顶区位数量固定（如 feed 前 3 位），满位时拒绝新购买并提示（不做排队，排队 = 不确定性 = 客诉）
- **叠加二次确认**：已有置顶且剩余有效期 < 本次购买时长时，弹二次确认（明示"将与现有置顶叠加/顺延"的规则，防用户误买浪费）
- **提前关闭不退分**：用户主动取消置顶不退还积分（防止"买置顶刷曝光 → 用完退分"套利）

### 5.10 实物发货物流单号必填

商家发货动作中，**物流单号从选填改为必填 + 格式校验**（快递公司 + 单号，单号正则校验长度/字符集）。理由：单号是"报告未收到"仲裁与 7 天自动收货计时成立的唯一凭据；选填 = 假发货零成本 = 自动收货机制被架空。

### 5.11 前端与 Admin 触点（实施清单）

- Taro 商城页：虚拟权益 + 商家礼品两栏 SKU 列表、礼品详情（商家信息 + 徽章排联动第 7 章）、兑换确认（收货地址表单）、我的兑换订单（状态机可视化 + 确认收货/延长/报告未收到）
- 商家端（Taro 商家 Tab）：挂礼管理（申报积分价 → 审核状态）、礼品订单发货（物流单号必填）
- Admin：礼品审核页（闸四定档）、订单仲裁页（冻结/退分/驳回）、月度仪表盘（见 10.2）

## 6. 商家积分金库与工会模型（M1-c / M2）

本章是 5.2 燃烧 vs 结算 P0 决策落定后的设计展开（决策结论见 6.8：采用结算模型）。商家侧要有积分资产沉淀，就必须有按 MerchantId 键的金库账户；而"商家-成员"这层组织关系天然映射到 MMO 行业验证了三十年的工会范式——工会金库、工会福利、工会等级照搬进来，成为积分飞轮之上的组织层：成员赚分反哺工会（trickle），工会强大回馈成员（buff），商家挂礼收入沉淀为金库资产（结算）。

### 6.1 工会映射：商家即工会

| 工会概念 | 本平台映射 | 说明 |
|---|---|---|
| 工会 | 商家 Merchant | 入驻审核通过的组织 |
| 工会成员 | MerchantMember（状态 Active） | Suspended / Removed 不算在册成员 |
| 散人（无工会玩家） | 无 Active 归属的个人用户 | 赚分/花分完全不受影响，只是无工会福利 |
| 工会金库 | MerchantPointAccount | 商家积分账户（6.2） |
| 工会等级 | 商家等级 Lv1-Lv4 | 由运营事实推导，不可购买（6.6） |
| 工会福利 | 成员被动 buff | 单源不叠加（6.5） |
| 工会集体任务 / 工会排行 | M3 可选扩展 | 本章不设计，待用户基数起来后评估 |

B2B 场景下"工会"不是游戏比喻而是现实映照：代理商/业务员天然围绕品牌结成组织，一人可代理多个品牌（多归属），品牌实力（商家等级）直接决定其成员的门面与福利。

### 6.2 金库数据模型

| 表 | 职责 | 关键约束 |
|---|---|---|
| `MerchantPointAccounts` | 一商一户金库：Balance / TotalEarned | `MerchantId` 唯一索引；余额守卫同 `PointAccount.Debit` 款式（不足抛异常）；并发令牌（xmin）与用户账户 P0 修复同批配置（第 11 章 P0 项） |
| `MerchantPointTransactions` | 金库收支流水（与用户流水平行的独立账本）：Direction（1 入账 / 2 出账）/ Type（trickle / settle / spend / admin_adjust / burn）/ Amount（恒正）/ BalanceAfter 快照 / BizId / Remark | `BizId` 部分唯一索引承担幂等（同用户流水款式）；`admin_adjust` 类型允许把金库打成负额（6.8 追回链路） |

**用户账本不动**：`PointAccount` / `PointTransaction` 的唯一键是 UserId（自然人），不可复用给组织——这正是 5.2 对比表里"商家账户归属悖论"的结论：组织有多成员、成员会入职离职，结算积分记到任何自然人的 UserId 都会随人员变动漂移。金库两表与用户账本物理分离，两套余额、两套流水、各自独立的快照与幂等键。

### 6.3 流入渠道一：trickle（成员 → 工会）

成员赚分时，按其本次所得的 10% 加发给其归属工会的金库。trickle 是平台侧加发：成员自身所得全额入账不扣减（成员端发放链路、规则表 Amount 展示、toast 反馈、DailyLimit 计数全部不受影响），T 是按该笔发放金额另行发给金库的额度。

**白名单（可触发 trickle 的成员赚分类型）**：

| 赚分类型 | 是否 trickle | 理由 |
|---|---|---|
| 纠错被采纳 | 是 | 人工审核闸口，难批量刷 |
| 商户入驻通过 | 是 | 真实执照 + 人工审核 |
| 商户资料完善 | 是 | 人工审核口径 |
| 商户首挂商品 | 是 | 真实供给动作 |
| 应答被选定 | 是 | 对手方真实选定，交易性质 |
| 每日登录 | 否 | 被动触发，可批量刷 |
| 每日签到 | 否 | 被动触发，可批量刷 |
| 新用户注册 | 否 | 无短信验证期是水泵（与 3.3 register_bonus 默认停用同一理由） |

准入原则：白名单 = 经人工审核或真实交易的动作；被动可脚本化的动作一律排除。

**计算与守恒**：

- `T = floor(成员本次所得 × 10%)`
- T 平分给该成员全部 Active 归属商家：每家 `floor(T / N)`
- 整数余数（`T - N × floor(T / N)`）给其中工会等级最高的一家商家
- 守恒约束：实发合计恒等于 T，一分不多一分不少（单商家触顶时例外，见下）

示例：成员一次纠错被采纳得 20 分，T = floor(20 × 10%) = 2，归属 1 家商家则该家得 2；若 T = 5、N = 2，每家 floor(5 / 2) = 2，余数 1 给等级最高的一家。

**上限**：单商家 trickle 入账日顶 50 / 月顶 1000（业务日/月界走 `BusinessClock`）。触顶时该商家本次应得份额放弃发放、不向他家转移（防借多归属绕顶），守恒式在触顶场景退化为实发 ≤ T。

**触发与幂等**：trickle 与成员发放同源触发（复用既有事件订阅者链路，成员侧 `GrantAsync` 成功后追加金库入账），金库流水 BizId 派生自源事件幂等键（如 `trickle:{源 bizId}:{merchantId}`），事件重放/重试不重发。

**多归属与平分的合理性**：B2B 现实里一人可代理多个品牌（轴承贸易商同时服务几家厂商）。平分使发放总量恒等于成员所得 × 10%，不随归属商家数放大——多归属不会凭空多造积分，只会把同一份 T 拆薄。

### 6.4 流入渠道二：挂礼兑换结算（纯进商家）

用户兑换商家礼品 → 确认收货（或发货后 7 天自动收货）→ **全额积分入商家金库**。托管与结算时点沿用 5.5：积分只在"货真实到达用户手中"后才离开托管态。

约束套件（复用 5.4 防刷四闸，参数在本章定死）：

| 约束 | 规则 | 对应闸 |
|---|---|---|
| 月结算上限 | 单商家每月结算入账封顶 2000 分，超限滚存次月 | 闸二（随结算模型落地成真） |
| 自兑排除 | 该商家 Active / Suspended 成员禁兑自家礼品；Removed 成员设回看窗（脱离后 30 天内仍禁兑，防"开除小号"过闸） | 闸一 |
| 收货信息去重 | 收货地址/手机号规范化后，同址或同手机每月限兑 3 单实物 | 闸三 |
| 积分价审核定档 | 商家礼品积分价由平台审核定档（商家申报 → Admin 核定），先审后上架、与上架审核合并为一次审核，商家不可自行改价 | 闸四 |

### 6.5 流出：工会 → 成员 buff（M2）

金库对成员**只出荣誉不出分**：成员从工会得到的是被动 buff，不是金库里的积分。

- 成员享受其 Active 归属中**等级最高**商家的福利（单源不叠加——归属 3 家商家不会拿到 3 份 buff，也不会拿到 3 家最高档的并集之外的东西）
- **不设主工会 / IsPrimary 字段**（用户拍板）：养多个公司更累，等级最高的公司最能为自己赚钱——"自动享受最高等级归属的福利"符合现实逻辑，还省掉一个状态字段及其设立/撤销/漂移的全套问题
- buff 是被动加成（赚取加数/乘数、免费额度加数、消费折扣、非经济展示），**不是从金库提分到个人**——组织 → 个人提现 = 触犯不可转让红线（1.2）+ 打开"金库 → 小号提现"的刷分通道，禁止

**buff 目录（按工会等级）**：

| 工会等级 | buff 内容 |
|---|---|
| Lv1 入驻 | 签到 +1、应答免费额度 +1/日 |
| Lv2 认证 | 纠错 ×1.1、登录 +1、发布免费额度 +1/日 |
| Lv3 活跃供给 | 纠错 ×1.2、签到 +2、应答 +3/日、置顶卡 9 折 |
| Lv4 金牌 | 纠错 ×1.25、签到 +3、应答 +5/日、置顶卡 8 折、超额 9 折、金牌称号 + 徽章框 |

等级 buff 逐级解锁、同维度取最高档不叠乘（Lv4 的纠错倍率是 ×1.25，不是 ×1.1 × 1.2 × 1.25 连乘）；buff 参数进配置表 Admin 可调，不散落硬编码（4.3 设计纪律同款）。

**非经济福利**：

- 工会成员标识：寻货应答署名、纠错署名挂"XX商家成员"（地位可见支柱的组织维度延伸——有真实商家背书的署名，在 B2B 场景天然更被信任）
- 工会专属头像框：Lv2+ 解锁（与 5.1 装扮 SKU 位联动，但由 buff 授予而非兑换获得）

**约束**：

- 实质经济 buff 的门槛在 Lv2（认证）：Lv1 只有签到 +1 级别的象征性甜头，不构成套利动机；纠错倍率、额度加成、消费折扣自 Lv2 起
- buff 的赚取加成仍受 `PointGrantRule` DailyLimit 约束：倍率/加数先行计算，DailyLimit 截断最后执行（与 G1 暴击、第 8 章合规护栏第 4 条同一执行序）
- buff 不构成转让：无积分位移，只是发放链路的系数调整与消费链路的折扣调整

**反刷论证**：工会 buff 的获取门 = 被一个真实认证商家加进成员表，攻击成本 = 真实执照 + 人工审核 + 商家-小号共谋关系；对比 universal buff（获取门 = 建号，无短信验证期零成本批量），攻击成本高数个量级。商家侧也没有滥加假成员的动力：buff 收益在成员侧、不入金库，金库的两条流入渠道（trickle 白名单 / 结算四闸）各自另有闸门把守。

### 6.6 工会等级推导

等级由运营事实推导，不可购买、不可 Admin 直接指定：

| 等级 | 名称 | 推导条件 |
|---|---|---|
| Lv1 | 入驻 | 商户入驻通过（Active） |
| Lv2 | 认证 | 认证商家审核通过 |
| Lv3 | 活跃供给 | 在售商品 ≥ 20 且履约良好 |
| Lv4 | 金牌 | 金库累计入账高且纠纷率低 |

Lv3 / Lv4 的具体数值门槛（在售件数口径、履约与纠纷率定义、金库累计额）待 M2 实施时定种子进 Admin 配置（与 G7 用户等级阈值表同一模式）。等级徽章挂商户徽章排——与第 7 章成就系统的商户徽章（认证商家、货架满满等）同排展示，共同构成 B2B 信任资产。

### 6.7 金库支出与终局

- **支出主体**：仅 MerchantAdmin 可以商家名义动用金库，普通成员不可触碰
- **支出范围**：仅平台内花——买寻货置顶、买寻货次数包、兑换其他商家的礼品；永不开 RMB 结算（1.2 三禁，商家礼品收入积分同此约束）
- **终局**：商家关店或主体注销（detach）时，金库余额冻结后燃烧核销——无主积分不提现、不转移给成员、不转移给他商；燃烧流水（Type = burn）留痕可审计

### 6.8 结算模型确认（5.2 P0 决策落定）

**本章确认采用结算模型**（用户拍板："卖掉的积分归自己" + trickle 双流入），**燃烧模型作废**。5.2 的审计推荐与六问题对比表保留作决策过程记录；第 11 章未决决策清单中该 P0 条目就此关闭。

结算模型的唯一优势（商家积分资产沉淀、挂礼动机更强、"卖礼品赚积分买置顶"的商家侧内循环）被金库 + 工会模型放大成组织级飞轮；代价是 M1-c 必须承担结算复杂度，逐项确认如下：

| 复杂度项（对应 5.2 对比表） | 实施确认 |
|---|---|
| 结算写入与状态流转 | 确认收货（含 7 天自动收货）= 订单完结 + 金库入账 + 结算流水（Type = settle），三者同一 UnitOfWork 原子完成（4.1 寻货扣分同款强一致纪律） |
| 结算后追回 | 已结算后仲裁退款走 Admin 调整流水（Type = admin_adjust），允许金库负额或冻结——负额由后续结算入账优先冲抵 |
| 月结算上限队列 | 2000/月，超限滚存次月，需滚存台账或月界队列 Job（`BusinessClock` 月界） |
| 退款守恒 | 单笔订单约束 settle + refunds ≤ escrow：已结算 + 已退款合计不得超过托管总额，仲裁裁决前先复核守恒 |

### 6.9 路线归位

| 里程碑 | 工会/金库模块归属 |
|---|---|
| M1-c | trickle + 金库两表 + 挂礼兑换结算（结算复杂度全量落地） |
| M2 | 成员 buff + 工会等级推导（Lv1-Lv4）+ 成员标识/专属头像框 |
| M3 | 工会集体任务 / 工会排行（可选，待用户基数起来后评估） |

与第 10 章原路线图的衔接：原挂在 M2 的"商户积分账户 + 月结算上限 + 退款守恒"前移并入 M1-c（结算模型的天然组成部分）；M2 转向 buff 与工会等级体系；实物品类扩展与二波游戏化（G3/G5/G8）不受影响。

### 7.3 个人/商户双轨

- **UserAchievement（UserId 键）**：挂个人资料页、寻货应答署名、纠错署名——个人荣誉与地位信号
- **MerchantAchievement（MerchantId 键）**：挂商户详情页 + 商户卡片（列表页）——**B2B 信任资产**：买家在寻货应答列表/商城礼品页看到商户徽章排（认证商家、货架满满、金牌红娘），徽章越多越敢下单/越敢兑换。商户徽章是商城转化率的基础设施，不是装饰

### 7.4 数据模型

| 表 | 字段要点 |
|---|---|
| `AchievementDefinitions` | Key（唯一）/ Scope（Personal / Merchant）/ Category（数据共创/寻货/商户/忠诚/彩蛋）/ Name / Description / Icon / AchievementPoints（成就点，只加不花）/ Rarity（普通/稀有/史诗）/ IsHidden / IsLimited（绝版标记 + 窗口字段）/ TargetCount（进度目标，1 = 无进度型）/ TitleReward（称号文案，可空）/ SortOrder / IsEnabled |
| `AchievementUnlocks` | OwnerType（User / Merchant）/ OwnerId / AchievementKey / Progress / UnlockedAt（null = 进行中未解锁）——**一表双轨**；唯一索引 (OwnerType, OwnerId, AchievementKey) |

### 7.5 UI 呈现

- **个人资料页徽章排**：横向滚动一行徽章（GitHub 贡献成就条 / 老将军军功章既视感），点亮的彩色、佩戴的称号挂昵称旁
- **成就墙页**：分类分组全量列表——已解锁彩色 + 解锁时间；未解锁灰色 + 条件提示 + 进度条（7/10）；隐藏成就显示 ??? 剪影；绝版成就带特殊标记
- **商户详情页 + 商户卡片**：商户徽章排（B2B 信任资产位）
- **解锁瞬间**：全屏/半屏 toast + 震动反馈（稀有以上特殊动画），"赚得可见且被庆祝"支柱的成就侧落点

### 7.6 解锁架构：事件驱动，不轮询不扫表

- **复用既有进程内领域事件订阅者模式**（与 CorrectionAdoptedPointsHandler / SourcingNotificationHandler 同款）：订阅 `CorrectionProcessedEvent`（纠错类成就）、`SourcingDemandClosedEvent`（伯乐/红娘类）、`MerchantApprovedEvent`（开张大吉）、签到命令内联钩子（忠诚/彩蛋类）、`PutOnShelf` 命令钩子（货架满满）等
- 订阅者收到事件 → 定位受影响的成就定义 → 重算 Progress（累计数从流水/行为表 COUNT，量小直查）→ 达标则写 UnlockedAt + 派发"成就解锁"通知/toast
- **成就点 ≠ 可花积分**：成就点是独立荣誉累计；解锁可附带小额可花积分甜头（+5~20，走 `GrantAsync`，bizId = `achievement:{key}:{ownerId}` 幂等防重发），但主体奖励是徽章 + 称号 + 成就点——防止成就系统变成刷分通道
- 新增成就 = 定义表加行 + （若是新行为维度）一个事件订阅者；既有行为维度的新成就零代码（订阅者按 Category 通用重算）

## 9. 架构定位：模块化单体

### 9.1 不拆微服务

积分、寻货、商城、成就**全部是 OpenFindBearings.Api 内的 DDD 聚合模块**，不拆微服务。理由：

- **解锁/发放靠进程内领域事件**（MediatR INotificationHandler 订阅 CorrectionProcessedEvent 等）：拆出去就要引入消息总线 + outbox + 幂等消费——对单人开发 + AI 维护的项目，这套基础设施是纯负资产
- **强一致刚需**：寻货扣分与建单同事务（4.1）、商城扣分与订单同事务——拆分即分布式事务
- **拆分触发条件一个都不满足**：无独立高频迭代需求（同一人同一节奏）、无独立团队（就一个人）、无独立扩缩容需求（单节点 K3s，积分 QPS 与主站同量级）
- **部署现实**：K3s 单节点 + GHCR 国内拉镜像慢，每多一个服务 = 多一个镜像、多一条 CI、多一面故障墙

### 9.2 留抽取缝（clean aggregate 纪律）

不拆 ≠ 长成一团泥。成就/寻货/商城聚合按"零内联依赖"纪律建设：

- 只引用外部聚合的 **Id**（UserId / MerchantId / BearingId / DemandId 存 Guid），**不建跨聚合导航属性**
- 跨聚合协作一律走**领域事件**（订阅者模式），不反向依赖别的聚合内部
- 积分写入口收敛在 `IPointsService`（Application 层接口），任何模块不直摸积分表

将来若真触发拆分条件，这些聚合可整体搬走：接口抽象换 MQ、事件换消息，业务调用点零改动。

### 10.2 防通胀与定价校准

- **Admin 月度仪表盘**：发放/燃烧/托管三条曲线（按 grantType 分组），月度净增量 = 发放 - 燃烧；连续两月净增为正且加速 → 调低发放或调高定价（全部 Admin 实时可调，不发版）
- **收入锚**：活跃个人用户月收入 ≈ **180 分**（口径：签到满勤 ≈ 144（阶梯 [2,3,4,5,5] 月累计）+ 每日登录 ≈ 30 + 纠错零星）
- **定价参考带**（让"月兑一次"可达——活跃用户一个月攒的分够兑一件中档权益，这是欲望支柱的经济学基础）：

| SKU | 参考定价 | 兑换节奏 |
|---|---|---|
| 寻货置顶 24h | 100-150 | 活跃用户月兑 1 次 |
| 寻货置顶 72h | 250-400 | 攒 1.5-2 月兑 1 次 |
| 寻货次数包 | 按单价 20 × 包量打折（如 5 次包 90） | 重度用户按需 |
| 商家实物礼品 | 500-3000 | 攒 3 月-1 年，稀缺感来源 |
| 抽奖单抽（G5） | 50（期望回报 < 50，净燃烧） | 小额积分娱乐出口 |
