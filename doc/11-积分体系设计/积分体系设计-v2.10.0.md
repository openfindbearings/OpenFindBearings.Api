# 积分体系设计 v2.10.0（商家金定名 + 默认金库支付 + 寻货需求置顶）

> 版本：v2.10.0 | 日期：2026-09-27 | 上一版：v2.9.0（批次二：G1 暴击 + G11 限量徽章 + 称号佩戴）
> 本版性质：商家经济增量版——金库货币定名、置顶卡拆分双对象、个人代付汇率。

---

## 一、商家金定名（货币单位与个人积分彻底区分）

- 商家金库（MerchantPointAccount）的余额单位定名 **商家金**，UI 与文案统一（金库=容器、商家金=货币）；个人侧仍叫"积分"。代码/DB 不改（数值同源），纯展示层定名。
- 商城目录中**商品置顶卡价格单位显示"商家金"**，需求置顶卡与礼品/权益显示"积分"。

## 二、商品置顶默认金库支付 + 个人代付汇率

- Taro 商家管理页置顶支付面板：管理员**默认选中金库通道**（置顶是经营行为，受益的是商家，走金库名正言顺）；员工仍只有个人积分通道。
- 新增配置键 `Business.MerchantGoldPayRate`（默认 2）：**个人代付商品置顶按汇率折算多付**（1 商家金 = 2 积分），金库通道原价。汇率走 SystemConfig 实时可调，经 `/api/mobile/config` 的 `merchantGoldPayRate` 字段下发（BFF 透传），Taro 支付面板显示"折算 N 分"。
- 设计意图：金库靠 trickle/挂礼结算/集体任务攒出来（稀缺），积分签到就能拿（易得）；汇率让经营支出自然流向金库，同时保留"金库没钱管理员自掏腰包"的弹性。个人通道失败引导按通道分流（金库不足→挂礼页，积分不足→任务中心）。

## 三、寻货需求置顶（置顶卡拆双对象）

- `MallItem` 加 `TargetKind`（1=商家在售商品 / 2=个人寻货需求，默认 1）；迁移 `AddDemandPin` 两列 + 种子两档**寻货置顶卡**（demand_pin_24h=60 积分 / demand_pin_72h=160 积分，幂等避让），商品置顶卡改名"24/72小时商品置顶卡"并描述标注商家金定价。
- `SourcingDemand` 加 `PinnedUntil` + `Pin/IsPinned`（未过期续加、过期从当前起算，与商品置顶同语义）。
- 履约路由（MallService.RedeemAsync）：需求置顶=本人校验+进行中校验+**仅个人积分原价**（无等级折扣——折扣是商家福利，寻货是个人动作）；商品置顶=原链路（成员资格+在售+金库/个人代付+汇率折算）。
- 公开大厅列表：服务端有效置顶排前（`GetListAsync(pinFirst)`，过期旧值不插队），feed 与"我的"输出带 `isPinned/pinnedUntil`；大厅卡片金色"置顶"角标。
- 入口：商城"去置顶"按 targetKind 分流——需求卡→我的寻货页（每条进行中需求"置顶/续置顶"按钮→选卡弹层→redeem）；商品卡→商家管理页（pins 过滤 targetKind=1）。
- Admin 商城管理：列表加"置顶对象"列、编辑表单加下拉可纠正类型（API admin PUT record 同步透传）。

## 四、边界与纪律

- 双账本无互转原则不变：个人代付不是"积分转商家金"，而是个人直接消耗积分购买商家向权益（平台扣分，无金库入账）——金库汇率差只是定价策略。
- Admin 商品置顶失败引导跳挂礼页（金库攒金路径），需求置顶积分不足跳任务中心（个人赚分路径）。
- 存量商品置顶卡行 TargetKind 默认 1，无需回填。
