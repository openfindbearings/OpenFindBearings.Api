## 零、本版变更（v1.9.0）

1. **成交回执（撮合事实链的唯一来源）**：新增 `POST /api/sourcing/responses/{id}/feedback`，需求方对已选定的合作回填结果——
   `Confirmed`（谈成）/ `NoStock` / `PriceRaise` / `Delayed` / `Other`；**只有"谈成"计入商家牌级**，
   负回执记负信号不计分，不填为中性且不惩罚需求方。选定（`Adopt`）仍是意向、本身不计分，只写 `SourcingResponse.AdoptedAt`。
   回执幂等（同响应重复提交=更新并写审计），首次计分写 `CountedAt`（v1.9.4），提交后触发商家牌级重算（反刷四项见《11-积分体系设计 v2.16.0》）。
2. **电话单向**：寻货详情**删除 `publisherContact`**——商家在任何阶段都拿不到需求方号码；
   需求方在选定/确认合作时获得商家号码并记录 `SourcingDemand.ContactUnlockedAt`（**取消"按需解锁"**，确认合作即下发）。
   商家侧只看到"有需求方选定了你 + 需求内容"，因此回执天然只能由需求方单方填写（杜绝被索要"五星好评"）。
3. **T1 会话**：绑定"寻货单 × 商户"的私域对话（`SourcingConversation` / `SourcingMessage`），
   从单据/应答进入，单据关闭后**只读保留**；端点见 v1.57.0 API 文档；不做全站通用 IM。
4. **商家可见商机**：选定后商家侧新增 `opportunity`（谁选了我 + 需求内容 + 是否已解锁联系方式），
   但不含需求方号码。

## 一、撮合模型定案（v1.5.0）

### 场景定位
寻货 = 撮合（平台价值终点是联系方式衔接，线下交易平台不管），因此取通用撮合机制中"终态之前"的部分，**去掉合同/成交环节**。术语不用招投标口径：发布方式只有「公开」与「邀请」两种。

### 机制对照
| 撮合机制 | 寻货实现 | 状态 |
|---|---|---|
| 公开发布（大厅，任何商户可应答） | 大厅公开，任何商户可应答 | 既有 |
| 点名邀请（定向） | 勾选收件商家，不进大厅 | v1.8.0 起支持 |
| 应答互不可见 | 应答者之间互不可见，发布人全见 | 既有，防串通必须保留 |
| 主体资格 | 商户认证标 isVerified | 既有 |
| 比价 | 发布人比价视图（结构化应答） | 本版强化 |
| 选定 | 选定（此时解锁联系方式） | 既有 |
| 顺延改选 | 顺延/改选（谈崩改选下一家） | 设计预留，本期未实现 |
| 无人应答 | 取消/到期关闭，或转公开继续等应答 | 设计预留，本期未实现 |
| 签订合同 | 线下交易 | 不做 |

### 关键设计决策：联系方式解锁时机
- **发布人侧**：选定才可见被选商户联系方式（应答内容虽可载明联系方式，但提前全给会让"选定"动作失去动力——发布人线下谈成就懒得走流程，故不退让）。
- **商户侧**：被选定后**只下发商家号码给需求方**（v2.18.0 起单向），商家始终看不到需求方号码，防扩散与"回头索取好评"。
- "凭什么选你"由**结构化应答 + 实力摘要**解决，不依赖提前拿手机号核实。
- 顺延（改选）发生频率天然低频（比价阶段已充分核实），发布人手机号扩散面天然为零；限顺延次数留待实现时定。

## 二、多行标书（v1.5.0 新增）

### 模型
- 一条应答（商家一份标书）= 多个型号行，每行：**型号 + 可引用在售商品 + 报价/库存/交期**。
- 需求明确时商家填一行（通常引用在售同款）；需求模糊时商家把自己认为相关的型号挨个列多行，供发布人按需挑选。
- **选定粒度不变 = 整条应答（商家）**，型号行是发布人的挑选依据，选中后线下谈具体哪个型号。
- 应答额度/通知/成就全部按应答（商家）计，行数不影响。

### 数据
- 新表 `SourcingResponseItems`（Id/ResponseId FK 级联/PartNumber/BearingId?/Price?/Stock?/LeadTime?/时间戳）。
- `SourcingResponse` 主表删除 Price/Stock/LeadTime，保留整份标书说明 Remark（必填）。
- 迁移 `AddSourcingResponseItems`：建行表 → 旧单型号应答按需求型号回填为一行 → 删主表内容列（顺序不可反，否则丢数据）。

### 接口契约
- `RespondDemandCommand` / `POST /api/sourcing/demands/{id}/respond` 请求体改 `{ items: [{ partNumber, bearingId?, price?, stock?, leadTime? }], remark, usePoints }`；至少一行、每行型号必填。
- 重复应答 = 更新语义不变（整份替换行：先清旧行再写新行，显式 Add 规避 EF 导航陷阱）。
- detail / Admin 详情 / 商家"我的应答"装配均透出 `items`。

## 三、证据力体系（v1.5.0 新增）

发布人选定前的判断依据 = **这次标书内容（有货+报价） × 商家历史信用（干过多少活）**。

### P0 应答引用在售商品
- 应答表单「从我的在售选择」：内嵌展开我的在售商品列表（getMyBearings onlyOnSale），点选即追加一行并引用 bearingId。
- 比价视图该行亮绿色「在售凭证」小标——"我确实有货"的实锤。

### P1 比价视图商家实力摘要
- detail 装配逐条应答透出：`companyName`（公司名）、`onSaleCount`（在售商品数，现货凭证）、`completedTaskCount`（集体任务累计达成，历史履约）。
- 比价卡片商户名下方一行小字展示；等级/勋章留给 P2 商家主页看全貌（不逐条透出）。

### P2 邀请谈判式深度考察
- 比价视图商户名**可点击** → `pages/merchant/merchantDetail?id=` 商家主页（等级/勋章/在售全貌），路由既有。

### 引导文案（界面说明）
- **发布表单**：引导卡"寻货信息越具体，商家报价越贴近——型号必填，品牌/数量/交期/地区尽量填全"。
- **应答表单**：引导卡"报价要素填全 = 发布人选你的概率更高。型号列得越全越容易被选中；写清货源/成色、报价/库存/交期，就是一份可信的标书"。
- **比价视图标题**：副文案"点商户名可看商家主页；应答内容越全、在售凭证越硬，越值得考虑"。

## 五、撤销应答（v1.5.0 同版本追加）

- **场景**：商户不想参与，有权在需求结束前撤回自己的应答——需求回到未应答状态、比价列表移除该商户，「我要应答」入口恢复。
- **状态守卫**：仅待处理 Pending 可撤（被选定 adopted / 已结束需求不显示取消）；需求方选定后联系方式已解锁，撤回应答语义矛盾，禁止。
- **端点**：`DELETE /api/sourcing/demands/{id}/respond`（登录+当前商户；操作人须为在职成员，员工可代商户撤）。API 仓储新增 `RemoveAsync`（行表 DB 级联删除）；BFF 同路径代理（`DeleteWithResultAsync`，错误透传）；Taro `cancelMyResponse` + 详情页我的应答卡双按钮（修改/取消）。
- **额度不退还**：当日免费应答计数不因撤销回退——每次应答都计频，防"撤-重答"反复占排序位/刷额度成本。
- **UI 独立页**：应答表单迁往 `pages/discover/respond.tsx` 单页竖流（需求摘要钉顶 + 型号行卡片 + 卡内从在售选择联动过滤 + 虚线添加 + 空态引导 + 自动预填 + 去重 + 配额降噪）；详情页回归纯阅读/比价。
- **对齐**：API 02 v1.45.0 / BFF v1.13.0 / Taro v1.7.30 同版本追加。

## 六、商户名义发布（v1.6.0）

- **场景**：寻货大厅此前只允许个人账户发布，而应答方是商户——身份不对称。发布人若为某商户在职成员（管理员或员工均可，与应答权限对称），可**以商户名义发布**求货单。
- **数据模型**：`SourcingDemand` 新增 `PublisherMerchantId`（可空，null=个人名义）+ `PublisherMerchantName`（名称快照，列表/详情展示免 join，商户改名不回刷）；迁移 `AddDemandPublisherMerchant`（两列+商户索引），存量单全部为个人名义无需回填。
- **守卫**：发布命令带 `merchantId` 时先验**在职成员**（`GetActiveByUserAndMerchantAsync`，与应答同款），身份非法直接拒绝且**不消耗额度/积分**（校验前置於额度评估）。
- **额度口径**：商户名义发布仍扣**经办人个人**每日额度（免费 N 条→积分加量→硬上限不变）——防一人挂多商户刷屏，不另设商户额度池。
- **联系方式分流**（选定解锁时）：商户单 → 被选商户看到**商户公开电话**（`Contact.Mobile ?? Phone`，与发布人看商户的取号口径完全对称，不暴露经办人个人手机）；个人单 → 维持发布人注册手机。
- **管理权限**：选定/取消/下架仍限**经办人本人**（`PublisherUserId` 判定不变）——商户其他成员可见（大厅徽章）不可管，原型期从简。
- **前端**：发布页顶部"发布身份"两段切换（**归属商户默认商户名义**，可切个人；多商户点商户名弹 ActionSheet 选本单商户，不改全局当前商户）；选择记忆本地存储；说明文案随身份联动（商户名义提示"被选中商家看到商户公开电话"）。大厅卡/我的寻货卡"商户"徽章；详情页"商户发布"徽章+商户名可点进商家主页。
- **输出契约**：feed / my/demands / detail 三处透出 `publisherMerchantId / publisherMerchantName / publisherType(merchant|individual)`；发布请求加可选 `merchantId`。
- **发布身份弹层（丙方案）**：弃用纯文字 ActionSheet，自绘 `PublishIdentitySheet`（三端统一：标题"选择发布身份" + 商户行 logo/全名/当前对勾 + "以个人名义发布"行 + 取消）——B2B 店铺名常为执照全称，logo+全名辨识度优于截断文字；页面级挂载，仅归属商户者弹出，纯个人用户零打扰。
- **对齐**：API 02 v1.46.0 / BFF v1.15.0 / Taro v1.7.32 同版本追加。

## 七、发布方式：公开 / 邀请（v1.8.0 - v1.8.2）

### 7.1 两个正交轴（取代"定向一家"）

发布方式由两个互相独立的轴决定，原 `TargetMerchantId`（把"受众=1 家"与"不进大厅"塞进一个字段）已废弃：

| 轴 | 取值 | 含义 |
|---|---|---|
| 曝光 `Visibility` | `Public` 公开 | 需求进公开大厅，全体登录用户可见，任何商户可应答 |
| | `Invited` 邀请 | 不进大厅，**仅发布人与收件商家可见**（非收件商户取详情 404） |
| 收件人 `InvitedMerchantIds` | 空 | 收件人 = 实时匹配的「公域可见在售本轴承 且 已认证」商家（口径唯一来源 `SourcingMatcher`；排除发布人在职全部商户与名义发布商户） |
| | 非空 | 收件人 = 勾选的认证商家（发布时点快照，`uuid[]` 一列承载）；**不要求该型号有在售**，逐家校验已认证 / 启用 / 非自家，非法项点名报错 |

- 勾选为空时按"全部匹配"解析；**空勾选且无匹配（N=0）才强制公开**，邀请请求返回 400（v1.10.0 起不再要求勾选商家必须在该型号在售）。
- 大厅 `GET /api/sourcing/demands` 只列公开单；`/my/demands`、`/merchant/demands`、`/matched`、`/opportunities` 透出 `isPrivate`。
- **通知 ≠ 曝光**：通知是点名触达（收件商家的在职管理员，按个人偏好多渠道 + 站内信恒发），公开是曝光面（大厅人人可见、任何商户可应答）；邀请通知文案只表达"邀请报价"，不承诺有货。
- "询价"是动作引导词而非单据类型：三处入口（轴承详情底部、在售商家行、商家主页）共用发布页 `pages/discover/publish`，从商家行/主页进入预勾选该家；v1.10.0 起首页搜索结果行也可直接"发布寻货"（预填型号/品牌/`bearingId`）。

### 7.2 边界收口（v1.8.1 / v1.8.2）

| 项 | 规则 |
|---|---|
| 应答权 | 邀请单只有收件商家可应答/更新（按发布时点快照判定），公开单不限——堵"知道 id 即可插队应答" |
| 邀请校验 | 勾选的每家须「已认证 + 启用 + 生效（`Status=Active`）+ 非发布人在职商户」，非法项一次性点名报错（v1.10.0 起不再要求该型号有在售；有货组默认全选，未在售的认证商家可手动勾选帮找货）；单次收件人上限 50 家（v1.10.1） |
| 详情可见性 | 邀请单对"发布商户在职成员"与"任一收件商户在职成员"可见（含一人多商户深链） |
| 通知限频 | 邀请单**豁免** `Sourcing.NotifyMaxPerMerchantPerDay`（受邀是点名勾选、受众可控，"受邀必达"优先）；公开保持限频抑制刷屏 |
| 转为公开 | 发布人可对**进行中**的邀请单 `POST /api/sourcing/demands/{id}/publish-public` 放开为公开（免取消重建的额度/积分损耗）；放开后**只按差集补发通知**——收件人 = 当前匹配 − 原邀请收件人（已通知过的原收件人不二次打扰；差集为空则一条不发）；已是公开或已终态一律拒绝 |
| 发布幂等 | 客户端可选带 `Idempotency-Key`：同发布人同 key 的重复提交（网络重试/连续点击/NEED_POINTS 二次确认）直接返回原单，不重复建单、不重复扣分 |
| 撤销应答 | 置 `SourcingResponseStatus.Cancelled` 留行（不物理删行）：可重新应答（`Revive()` 复用原行，守 `(DemandId, MerchantId)` 唯一约束），但**当日应答额度与"每日三件套"应答项不回退** |
| 在售口径 | "公域可见（出售中/补货中）"贯穿匹配、等级在售指标、应答实力摘要；成就仪表 `listing_count` **保持现货口径**（历史进度已按现货回填，放宽会凭空白送勋章） |
| 治理可见 | Admin 寻货列表/详情包含软删单并标 `isDeleted`——发布人撤销的终态单仍在治理视图可审计 |

> 收件人集合只解析一次：`SourcingDemandPublishedEvent` 携带**最终收件人集合**，通知订阅者不自行匹配（口径唯一来源 `SourcingMatcher`），故"转公开差集补发"只需构造集合即可复用同一订阅链。

## 六、自交易封堵（v1.9.3）

- **问题**：匹配原先只排除"名义发布的那一家商户"，于是个人名义发布、一人多商户时自家店铺照旧被匹配、被通知、可被邀请；公开单也能在自家店铺应答，形成自导自演闭环（订选自己、给自己解锁自己的号码）。反刷校验只拦"计分"，拦不住噪音与脏数据。
- **匹配侧**：`SourcingMatcher` 的排除参数改为集合——发布时传入"发布人在职的全部商户 + 名义发布商户"，转公开补发同口径，自家店铺既不进收件人也不收通知。
- **应答侧**（三条守卫，服务端强制）：发布人本人不得应答；应答商户不得是发布商户本身；发布人是应答商户在职成员时（同事代发）同样不得应答。
- **候选清单**：邀请勾选的商家列表在前端隐藏自家店铺；服务端逐家校验认证/启用/非自家，非法项点名报错（v1.10.0 起不再与在售匹配集取交集，未在售的认证商家也可受邀）。
- **不回溯**：已存在的历史自应答数据不做清理（测试期数据，且选中与回执仍有反刷校验兜底）。

## 九、型号联想与型号线索（v1.10.0）

### 9.1 型号输入：联想优先、自由文本兜底

- 发布页型号输入 ≥2 字触发联想（300ms 防抖、序号丢弃过期响应），候选最多 8 条，显示「型号 · 品牌 · 类型」。
- 选中候选：写入型号与品牌（品牌为空时补），绑定 `bearingId`，随即拉取该型号的有货认证商家清单；手改型号文本即解绑（清 `bearingId`、清单与勾选），避免"型号已改、匹配仍按旧轴承算"。
- 未选中直接发布允许：服务端只校验型号必填与 ≤100 字；`bearingId` 为空时 `SourcingMatcher` 以 `PartNumber` 精确匹配，未命中即收件人为 0（公开单进大厅、无定向通知）。前端必须显示"未关联平台型号：只进大厅，不会定向通知商家"提示。
- 首页搜索结果行可直接"发布寻货"，预填型号/品牌/`bearingId`，与轴承详情入口共用同一预填 storage 键；行内按钮须阻止 tap 冒泡，避免先跳详情页。

### 9.2 邀请候选：有货优先、认证即可邀

| 分组 | 来源 | 默认 | 说明 |
|---|---|---|---|
| 有货认证商家 | `/api/bearings/{id}/merchants` 中 `isVerified` 且非自家 | 全选 | 沿用匹配口径，行尾标「有货」 |
| 其他认证商家 | `/api/merchants/search?verifiedOnly=true&excludeInternet=true&sortBy=productcount` | 不勾 | 折叠 + 关键词搜索，行尾标「找货」；默认 20 条按在售数排序 |

- 两组共用同一勾选集合，已选区单独列出可逐个移除；勾选状态跨搜索保留（`id → {名称, 是否有货}`）。
- 提交时一律显式提交勾选集合（不再折叠为空数组"全部匹配"），至少勾选一家；从商家主页进入且无 `bearingId` 时沿用预填收件人。
- 服务端逐家校验，错误文案点名具体商家与原因（不存在 / 自己所在的商户 / 未认证 / 已停用）。
- 互联网来源商家无账号、收不到站内信，候选必须排除（BFF 商家搜索透传 `excludeInternet=true`）。

### 9.3 型号线索（未收录型号的证据池）

- **只记"型号库根本没有"**：型号存在但无人公域在售不算线索。
- 记录点两处：发布寻货（`bearingId` 为空且型号库未命中）、商家应答的型号行（`bearingId` 为空且型号库未命中）。
- 写入为原子 upsert（`INSERT ... ON CONFLICT (PartNumberKey) DO UPDATE`），去重键 = 去首尾空格 + 小写；只累加 `OccurrenceCount`、刷新 `LastSeenAt`、补写缺失品牌，**不建型号、不改单据**；写入失败只记日志，不影响发布/应答结果。
- 应答侧只在"首次应答"与"撤销后复活"记录线索（v1.10.1）：改价/改库存重提不再累加，避免同一商家反复编辑把冷门型号刷到列表首位。
- 表 `BearingLeads`：`PartNumber` / `PartNumberKey`（唯一）/ `Brand` / `Source` / `OccurrenceCount` / `FirstSeenAt` / `LastSeenAt` / `IsIgnored` / `IgnoredAt` / `IgnoredByUserId`。
- Admin 侧三态：待建档（默认）、已忽略、已入库；**已入库为计算态**（型号库存在同型号即自动判定，含已软删型号），无需人工标记。
- Admin 端点：`GET /api/admin/bearing-leads`（`bearing.view`）、`POST /api/admin/bearing-leads/{id}/ignore|restore`（`bearing.edit`）；页面从「轴承列表」进入，行内"去建档"跳回轴承列表并预填型号/品牌、自动打开新建弹窗（弹窗已补品牌/类型下拉与内径/外径/宽度，可直接保存成功，v1.10.1）。
- 线索只作建档参考，不做自动入库（错别字与非标写法会污染主数据）。
