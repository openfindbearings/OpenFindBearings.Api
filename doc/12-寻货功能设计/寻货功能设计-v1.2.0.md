# 寻货功能设计文档

> 版本：v1.2.0 | 日期：2026-09-25 | 状态：已实施

## 1. 定位与模型

寻货是平台"点对点找货"的核心撮合动作，采用 **RFQ（询价单）模型**（对标 1688 询价单、轴承行业询价通道）：

- 个人用户发布**结构化求购需求**（型号必填 + 品牌/数量/交期/地区/说明可选）
- 入驻商户对需求**应答报价**（报价/库存/交期可选 + 说明必填，一商户一需求仅一条可更新）
- 发布人**选定一家**结束需求，**双方联系方式解锁**——无交易闭环平台的价值终点（1688 靠订单衔接，本平台靠联系方式衔接）
- 14 天无人确认自动过期；发布人可主动取消；Admin 可下架违规单（先发后审）

架构决策：寻货作为 OpenFindBearings.Api 内的 DDD 聚合（模块化单体，不拆微服务）。理由：花积分发布/应答与积分账本必须同事务原子（DeductAsync+建单），拆分即分布式事务；单节点 K3s + 单人发布拿不到独立扩容收益。聚合保持零内联依赖（只引用 userId/merchantId/bearingId，不建导航属性，通知走领域事件），将来拆分成本低。

## 2. 数据模型

### SourcingDemand（寻货需求，聚合根）

| 字段 | 说明 |
|---|---|
| PublisherUserId | 发布人（个人账户，非商户） |
| BearingId | 关联平台轴承（可空；v1 自由文本为主，搜索联动后置） |
| PartNumber | 型号文本（必填 ≤100 字，feed 搜索键） |
| Brand/Quantity/ExpectedDelivery/Region/Description | 可选描述字段（B2B 单位多样不做死） |
| Status | 1 进行中 / 2 已选定 / 3 已过期 / 4 已取消 / 5 已下架 |
| ExpiryAt | CreatedAt+14 天；读时惰性过期（feed/详情触发 ExpireOverdueAsync 一条 UPDATE） |
| SelectedResponseId | 选定锚点（联系方式解锁判定依据） |
| ResponseCount | 冗余计数（列表免 COUNT JOIN） |

### SourcingResponse（应答，聚合内实体）

| 字段 | 说明 |
|---|---|
| DemandId / MerchantId | 归属商户（应答=商家行为）；(DemandId,MerchantId) 唯一索引 |
| RespondedUserId | 操作人审计列（员工可代商户应答） |
| Price / Stock / LeadTime | 报价/库存/交期（可选，"电话聊"习惯） |
| Remark | 应答说明（必填一句话） |
| Status | 1 待处理 / 2 被选定 / 3 未选中（需求关闭时批量流转） |

## 3. 额度与积分（防刷闭环）

免费额度（SystemConfig 可配）→ 积分加量（规则表单价）→ 硬上限拒绝：

| 动作 | 免费 | 积分加量 | 硬上限/天 |
|---|---|---|---|
| 发布寻货 | 3 条/天（Sourcing.FreePublishPerDay） | 20 分/条 | 10 |
| 应答寻货 | 20 条/天（Sourcing.FreeRespondPerDay） | 20 分/条 | 50 |

- 规则表 grantType：`sourcing_publish_bonus` / `sourcing_respond_bonus`（Amount=单价、DailyLimit=硬上限），Admin 积分任务页实时可调
- **这是 DeductAsync 的第一个真实消费场景**——积分"可赚可花"闭环从寻货开始（商城前置于此已有出口）
- 合规：积分兑"发布次数服务"（价格折扣定性），不碰资金属性；三纪律不变
- 协议：超限未确认时 API 以 400 文案 `NEED_POINTS:{分值}` 回传，前端弹确认后带 usePoints=true 重提交
- 发布计数含取消单（防发了删删了发绕额度）；重复应答=更新不占额度

## 4. 可见性与联系方式解锁

| 查看者 | 应答列表 | 联系方式 |
|---|---|---|
| 发布人 | 全部明细（商户名/认证徽标/报价，比价依据） | 选定后见被选商户电话（Contact.Phone 回退 Mobile） |
| 有当前商户的登录者 | 仅自己商户的应答 | 被选定后见发布人手机号 |
| 匿名/他人 | 仅应答数 | 不可见 |

防报价泄露（商户间互相看不到报价）+ 防扒号（未选定双方联系方式均不可见）。

## 5. 通知（领域事件四链路）

SourcingRespondedEvent → 发布人"收到新应答"；SourcingDemandClosedEvent → 被选商户管理员"应答被选定"（含联系方式引导）+ 落选商户"寻货已结束"；SourcingDemandCancelledEvent → 全体待处理应答商户"寻货已取消"；SourcingDemandTakenDownEvent → 发布人"已下架+原因"。类型统一 `sourcing`，商户侧发给全部在职管理员。

## 6. 端点（11 个）

用户组 `/api/sourcing`：GET demands（feed，公开）、GET demands/{id}（详情，公开分级）、POST demands（发布）、POST demands/{id}/respond|select|cancel、GET my/demands、GET my/responses。
Admin 组 `/api/admin/sourcing`：GET demands（sourcing.view）、GET demands/{id}（详情含发布人联系方式）、POST demands/{id}/takedown（sourcing.manage）。
BFF 代理 `/mobile/sourcing/*`（浏览匿名透传，写操作透传 NEED_POINTS 文案）。

## 7. 前端页面（Taro）

发现 tab 转正为寻货 feed（搜索+全部/等待应答过滤+发布入口）；寻货详情页（需求卡+解锁联系卡+发布人比价列表/商户应答表单内嵌）；发布页（表单+积分确认弹窗）；我的寻货（八格入口转正）；商家寻货应答页（商家 Tab 功能区新按钮，员工可见——应答是商家行为）。

## 8. Admin 治理

寻货管理页（审核管理组，菜单按 sourcing.view claim 动态渲染）：全状态列表（状态筛选/型号搜索/发布人列）→ 详情抽屉（需求全文+应答明细+发布人联系方式）→ 下架（showPrompt 原因，透传发布人站内信）。
