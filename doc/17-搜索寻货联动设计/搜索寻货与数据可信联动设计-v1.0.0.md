# 搜索—寻货—认证商家与数据可信联动设计 v1.0.0

> 版本：v1.0.0 | 日期：2026-10-15 | 性质：定案版（首版）
> 关联文档：《寻货功能设计》《数据状态字段设计》《积分体系设计》《商户入驻与认证体系》
> 目标：把"首页搜索 → 轴承货源 → 认证商家触达 → 寻货撮合"串成闭环，并明确"可信/仅供参考"数据口径。

---

## 一、定位与边界

- **开源 = 信息撮合**：平台价值终点是**双方互给联系方式**（电话）。线下的成交、报价执行平台不管。
- **互联网采集数据 = 仅供参考**：只读展示、**不导流、不给联系方式**；它存在的价值是让用户"看得到这个型号存在、长什么样"，而不是作为可交易的货源。
- **认证商家数据 = 可信可用**：商家自维护的在售、认证商家的报价，是平台真正鼓励流转的资产。

一句话：**查到不等于结束**——查到之后要能"进一步联系"，而"联系"统一收敛到**寻货撮合**这一条链路上。

---

## 二、数据可信标注

### 2.1 信任两档

| 档位 | 判定 | 展示 | 可行动 |
|---|---|---|---|
| 可信 | 认证商家（`Merchant.IsVerified`）及其在售商品 | 商家**等级徽标**（入驻/认证/口碑/金牌） | 可询价、可寻货 |
| 仅供参考 | `DataSource ∈ {Internet, OcrExtract, SeedData}` | 灰标「参数来源：互联网 · 仅供参考」 | **只读**，不导流 |

- 商家不做"认领/未认领"标注——超过认证等级的标注意义不大；**入驻后商家等级徽标本身就是可信信号**。
- 轴承参数区沿用与商品一致的口径：「参数来源：互联网 · 仅供参考」（互联网）/ 无标（人工校对 `Manual`）。

### 2.2 行动门（核心约束）

**「询价 / 发起寻货」只对认证商家的在售开放**。仅供参考数据（互联网收录的商家/商品）**只展示、不导流**，避免"不可信数据"被当成可交易资产。

### 2.3 技术支撑

- `BearingDto` / `MerchantBearingDto` 下发 `DataSource`（此前仅有实体、未下发）。
- 前端统一 `provenanceBadge()` 映射：`Internet/OcrExtract/SeedData → 仅供参考`，其余 → 可信（无标或"已校对"）。

## 三、电话单轨

### 3.1 规则

- **查询页（轴承详情、商家主页）永不显示电话号码**（对所有用户，含注册用户）；只给入口：「发起寻货」/「向该商家询价」。
- **号码只在寻货撮合达成后互给**（唯一结束点）：
  - 广播寻货：商家应答 → 发布人**选定** → 双方互给；
  - 定向询价：发布人**定向**发起 → 商家**接受** → 双方互给。
- **游客**端商家主页电话行显示「**登录后发起询价**」（不再是"暂无"），点击引导登录/注册。
- 互联网来源的联系方式：**不给**。

### 3.2 实现口径

- 公共查询 DTO **移除** contact 字段；联系方式改由**寻货撮合上下文**承载（`GET /api/sourcing/demands/{id}` 已在"选定/被选定"后按身份返回 `selectedMerchantContact` / `publisherContact`，沿用此机制）。
- 移除"仅对游客屏蔽 contact"的旧逻辑分支（`ToDetailDto(..., isAuthenticated)` 中仅为此存在的分支）。

## 四、搜索↔寻货联动

### 4.1 打通 bearingId

- 轴承详情「发起寻货」预填 型号 + 品牌 + **bearingId**（修 Taro 发布页此前硬编码 `bearingId: null` 导致寻货单与轴承目录断链）。
- 发布寻货请求体 `PublishDemandRequest` 已含 `BearingId`，仅前端未传；后端字段无需新增。

### 4.2 发布即触达匹配的认证商家

- 新增领域事件 `SourcingDemandPublishedEvent`（发布成功后由命令处理器发布）。
- 订阅者匹配「**在售本轴承（公域可见）的认证商家**」并向其通知：
  - 强匹配：`MerchantBearing.BearingId == demand.BearingId` 且公域可见（`ReviewStatus=Approved` 且 `SaleState ∈ {OnSale, Restocking}`）且商家认证。
  - 兜底：无 `bearingId` 时按型号文本精确匹配主数据再匹配（与既有 `opportunities` 口径一致）。
- **限频**：同一认证商家 + 同型号，每日最多推 3 条；超量只进商家侧聚合面、不再弹信。
- **触达范围**：固定为「在售本轴承的认证商家」（精准、不打扰）；只发给**有货（在售本轴承）的认证商家**，不做「全体认证商家」广播。

### 4.3 定向询价

- `SourcingDemand` 新增 `TargetMerchantId`（可空）：
  - `null` = 广播（进公开大厅 + 匹配推送）；
  - 非空 = 定向（仅推给该商家，**不进公开大厅**）。
- 入口：轴承详情「在售认证商家」行「向该商家询价」→ 生成定向单 → 该商家通知（站内信 + 短信）→ 接受 → 互给电话。

### 4.4 商家侧「为你匹配的寻货」

- 复用/增强既有 `GET /api/sourcing/opportunities`（当前按型号文本、未应答聚合）：升级为**按 bearingId 精确匹配在售型号**，作为商家工作台「为你匹配的寻货」tab 数据源。

### 4.5 站内信深链

- 寻货通知 `bizType` 由字面量 `"SourcingDemand"` 改为正式常量 `Notification.BizSourcingDemand`，前端消息中心路由到寻货详情（修"点去处理没反应"）。

## 五、通知（多通道 + 用户偏好）

### 5.1 多通道

- 扩 `INotificationService`：站内信（现有 `AddInAppAsync`）+ **短信/微信/邮件**兄弟方法；未配置网关的通道**只记日志不外发**。
- **同时多方式发出**：一次事件按用户偏好**扇出到全部启用的通道**。
- 触发点：认证商家收到"匹配寻货"→ 站内信**必发** + 短信（受偏好多门控）。

### 5.2 通知设置（用户自选）

- 位置：设置页 → 子页「通知设置」。
- 可勾选：**站内信**（必开、不可关，消息中心兜底）；**短信**（**仅短信网关就绪时显示**，避免"勾了收不到"）；**微信通知**、**邮件通知** 可勾。
- 后端：写复用 `UpdateUserPreferenceCommand`；**补** `GetUserPreferenceQuery` + `GET/PUT /api/notifications/preferences` + BFF 代理。

### 5.3 通知分发矩阵（谁收 / 在哪设）

统一规则：**通知一律投递给个人账号，渠道接收设置也一律在个人账号级**（我的 → 设置 → 通知设置）；商户不设统一接收开关。

| 触发 | 通知谁 | 落地账号 |
|---|---|---|
| 发布寻货（广播） | 有货（在售本轴承）的认证商家在职管理员 | 各商户管理员自己的账号 |
| 发布寻货（定向询价） | 目标商户在职管理员 | 各自账号 |
| 商家应答（**商户名义发布**） | 发布商户**全部在职成员** | 各成员自己的账号 |
| 商家应答（**个人名义发布**） | 发布人本人 | 发布人账号 |
| 发布人选定 | 被选商户管理员 + 其余应答商户管理员 | 各自账号 |
| 发布人取消 | 已应答商户管理员 | 各自账号 |
| 平台下架 | 发布人本人 | 发布人账号 |

> 站内信为兜底通道**恒发不可关**；短信/微信/邮件在**各接收人自己**的偏好 + 网关就绪上双重门控。故"全店在职成员"意味着全店成员都会收到站内信，外部渠道按各自设置。
> 本节仅为寻货相关分发；**完整通知体系（模型/渠道/设置/清单/深链）见《18-通知消息体系设计 v1.0.0》**。

## 六、分享（真实货源查询结果）

### 6.1 定位

**主场景**：查到某轴承 → 得出"**谁家真实有货**"（认证商家在售清单）→ 分享到微信群 / 发给询价人 → **引流回平台**发起寻货或后续交易。

### 6.2 入口

- **主**：轴承详情「在售认证商家」区「分享货源」；
- **次**：商家主页「分享」（给该商家曝光引流）。
- 搜索结果页**不做**分享（列表缺上下文，价值低）。

### 6.3 落地与内容

- 复用轴承详情，带 **`?view=supply`** 进"货源视角"：**认证货源主位**，轴承参数折叠并标源。
- 卡片文案：`{型号} {品牌} · {N}家认证商家真实有货，来平台比价询价`。
- 游客打开：看在售认证商家 → 「登录后发起询价」→ 转化闭环。

### 6.4 三端策略

| 端 | 方式 |
|---|---|
| 微信/抖音小程序 | `useShareAppMessage`（原生分享菜单） |
| H5 | 优先 `navigator.share`，否则**复制链接**兜底（可选微信 JSSDK 增强） |
| RN | `Share.share()` |

- 原则：只分享**可信/认证**数据；仅供参考页分享时文案明示「仅供参考」。

## 七、端到端漏斗

```
游客：搜索→轴承详情（在售=认证商家名单 + 仅供参考灰标）→商家主页「电话：登录后发起询价」
        ↑                                                          │
        └── 分享货源到微信群/微信 ← 「{N}家认证商家有货」卡片 ←────┘
─────────────── 注册分水岭 ───────────────
注册：①向该商家询价（定向）→商家通知（站内信+短信）→接受→互给电话
      ②发起寻货（广播，预填 bearingId）→匹配认证商家通知→应答→选定→互给电话
认证商家：工作台「为你匹配的寻货」→应答   ← 入驻价值；通知按偏好多渠道
互联网数据：只读 + 灰标，不导流、不给号
```

---

## 八、边界

- 开源信息撮合**终止于「互给电话」**（选定应答 / 接受定向询价那一刻）；此后线下成交由双方自行完成，不在本设计范围内。
- 预留 `MatchCompletedEvent`（撮合达成，即电话互给）作为该终止点的衔接钩子；本设计不含其消费实现。

## 九、实施范围（本期一次到位）

- **API**：`DataSource` 下发；公共 DTO 去 contact；撮合上下文 contact（沿用寻货详情）；`SourcingDemand.TargetMerchantId` + 迁移；`SourcingDemandPublishedEvent` + 订阅者（匹配 + 多渠道 + 限频）；通知 `bizType` 常量；`INotificationService` 多通道；`GetUserPreference` + `GET /api/users/preferences`；`opportunities` 升级为 bearingId 匹配；`MatchCompletedEvent` 预留。
- **BFF**：新端点代理（偏好读 / 商家匹配寻货 / 定向询价）。
- **Taro**：分享（三端 + 货源视角）；游客电话 CTA；可信标注；询价入口；发布预填 + 触达范围；站内信深链；「为你匹配的寻货」tab；「通知设置」子页。
- **Admin**：寻货下架治理已具备，本期无新增。

## 十一、预留与不再做
