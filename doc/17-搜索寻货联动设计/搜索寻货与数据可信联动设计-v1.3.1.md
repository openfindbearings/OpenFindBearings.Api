# 搜索—寻货—认证商家与数据可信联动设计 v1.3.1

> 版本：v1.3.1 | 日期：2026-10-20 | 性质：定案版（v1.3.0 补全邀请边界与投递保障；本版仅术语统一——「公开招标 / 邀标」改「公开 / 邀请」，无口径变更）
> 关联文档：《寻货功能设计》《数据状态字段设计》《积分体系设计》《商户入驻与认证体系》
> 目标：把"首页搜索 → 轴承货源 → 认证商家触达 → 寻货撮合"串成闭环，并明确"可信/仅供参考"数据口径。

---

## 一、定位与边界

- **开源 = 信息撮合**：平台价值终点是**双方互给联系方式**（电话）。线下的成交、报价执行平台不管。
- **互联网采集数据 = 仅供参考**：只读展示、**不导流、不给联系方式**；它存在的价值是让用户"看得到这个型号存在、长什么样"，而不是作为可交易的货源。
- **认证商家数据 = 可信可用**：商家自维护的在售、认证商家的报价，是平台真正鼓励流转的资产。

一句话：**查到不等于结束**——查到之后要能"进一步联系"，而"联系"统一收敛到**寻货撮合**这一条链路上。

---

## 二、数据可信标注

### 2.1 信任两档

| 档位 | 判定 | 展示 | 可行动 |
|---|---|---|---|
| 可信 | 认证商家（`Merchant.IsVerified`）及其在售商品 | 商家**等级徽标**（入驻/认证/口碑/金牌） | 可发布寻货、可邀请 |
| 仅供参考 | `DataSource ∈ {Internet, OcrExtract, SeedData}` | 灰标「参数来源：互联网 · 仅供参考」 | **只读**，不导流 |

- 商家不做"认领/未认领"标注——超过认证等级的标注意义不大；**入驻后商家等级徽标本身就是可信信号**。
- 轴承参数区沿用与商品一致的口径：「参数来源：互联网 · 仅供参考」（互联网）/ 无标（人工校对 `Manual`）。

### 2.2 行动门（核心约束）

**「邀请 / 发布寻货」只对认证商家的在售开放**。仅供参考数据（互联网收录的商家/商品）**只展示、不导流**，避免"不可信数据"被当成可交易资产。

### 2.3 技术支撑

- `BearingDto` / `MerchantBearingDto` 下发 `DataSource`（此前仅有实体、未下发）。
- 前端统一 `provenanceBadge()` 映射：`Internet/OcrExtract/SeedData → 仅供参考`，其余 → 可信（无标或"已校对"）。

## 三、电话单轨

### 3.1 规则

- **查询页（轴承详情、商家主页）永不显示电话号码**（对所有用户，含注册用户）；只给入口：「发布寻货」/「邀请该商家报价」。
- **号码只在寻货撮合达成后互给**（唯一结束点）：
  - 公开：商家应答 → 发布人**选定** → 双方互给；
  - 邀请：发布人**指定收件商家**发起（可勾选多家）→ 商家**应答** → 发布人**选定** → 双方互给。
- **游客**端商家主页电话行显示「**登录后邀请报价**」（不再是"暂无"），点击引导登录/注册。
- 互联网来源的联系方式：**不给**。

### 3.2 实现口径

- 公共查询 DTO **移除** contact 字段；联系方式改由**寻货撮合上下文**承载（`GET /api/sourcing/demands/{id}` 已在"选定/被选定"后按身份返回 `selectedMerchantContact` / `publisherContact`，沿用此机制）。
- 移除"仅对游客屏蔽 contact"的旧逻辑分支（`ToDetailDto(..., isAuthenticated)` 中仅为此存在的分支）。

## 四、搜索↔寻货联动

### 4.1 打通 bearingId

- 轴承详情「发起寻货」预填 型号 + 品牌 + **bearingId**（修 Taro 发布页此前硬编码 `bearingId: null` 导致寻货单与轴承目录断链）。
- 发布寻货请求体 `PublishDemandRequest` 已含 `BearingId`，仅前端未传；后端字段无需新增。

### 4.2 发布即触达匹配的认证商家

- 新增领域事件 `SourcingDemandPublishedEvent`（发布成功后由命令处理器发布）。
- 订阅者匹配「**在售本轴承（公域可见）的认证商家**」并向其通知：
  - 强匹配：`MerchantBearing.BearingId == demand.BearingId` 且公域可见（`ReviewStatus=Approved` 且 `SaleState ∈ {OnSale, Restocking}`）且商家认证。
  - 兜底：无 `bearingId` 时按型号文本精确匹配主数据再匹配（与既有 `opportunities` 口径一致）。
- **限频**：同一认证商家 + 同型号，每日最多推 3 条；超量只进商家侧聚合面、不再弹信。
- **触达范围**：固定为「在售本轴承的认证商家」（精准、不打扰）；只发给**有货（在售本轴承）的认证商家**，不做「全体认证商家」广播。**（v1.2.0）** 公开与邀请共用同一收件人基数，邀请在其子集内按勾选再收敛（见 4.7）。

### 4.3 邀请（原"定向询价"，v1.2.0 重构）

- `SourcingDemand` 以"曝光范围 + 收件人快照"两轴表达受众（原 `TargetMerchantId` 单字段已弃用）：
  - `Visibility`：`Public`=公开（进公开大厅 + 通知匹配的认证在售商家）/ `Invited`=邀请（**不进公开大厅**，仅收件商家与发布人可见）；
  - `InvitedMerchantIds`：邀请收件人快照（`uuid[]`）；**空 = 通知全部匹配的认证在售商家**（等价"全部勾选"），非空 = 精确到这 N 家。
- 入口：轴承详情「在售认证商家」行「邀请报价」→ 预勾选该家 → 发布页（可再勾选/取消）；商家主页「邀请报价」同理；发布页也可直接切「邀请」并逐家勾选。
- 收敛校验：勾选集合 ∩ 认证在售匹配集合；交集为空则建单失败（拦截未认证/无货的勾选），守住"只找有货的认证商家"。
- 流转：邀请单 → 收件商家通知（站内信 + 外部渠道）→ 应答 → 发布人选定 → 互给电话（与公开同一条链路）。
- **转为公开**：邀请单进行中时由发布人一键放开为公开（`POST /api/sourcing/demands/{id}/publish-public`），免去"无人应答只能取消重建"的额度与积分损耗。

### 4.4 商家侧「为你匹配的寻货」

- 复用/增强既有 `GET /api/sourcing/opportunities`（当前按型号文本、未应答聚合）：升级为**按 bearingId 精确匹配在售型号**，作为商家工作台「为你匹配的寻货」tab 数据源。

### 4.5 站内信深链

- 寻货通知 `bizType` 由字面量 `"SourcingDemand"` 改为正式常量 `Notification.BizSourcingDemand`，前端消息中心路由到寻货详情（修"点去处理没反应"）。

### 4.6 两条路径可见化（v1.1.0）

**问题**：详情页只有「发起寻货」一个入口，用户看不出"有在售 → 直接推给这些商家"与"无在售 → 进大厅等应答"两条路径的差别，也看不出"在售"≠"可询价"。

**后端口径统一**：匹配逻辑抽为 `SourcingMatcher.GetMatchedMerchantIdsAsync`（公域可见在售本轴承 → 去重商户 → 仅认证商家；无 `bearingId` 时按型号文本精确匹配主数据兜底），**发布处理器**（回传家数）与**发布通知订阅者**（逐户推送）共用，避免"回传家数"与"实际推送对象"漂移；`POST /api/sourcing/demands` 响应回传 `matchedMerchantCount`（广播=匹配并推送的认证商家家数，定向=1，无匹配=0）。

**前端表达（Taro）**（下表主按钮文案为 v1.1.0 稿，**v1.2.0 已统一为「发布寻货」**，见 4.7）：

| 场景 | 主按钮 | 路径说明 |
|---|---|---|
| 认证在售 N>0 | 「向 N 家认证商家发起寻货」 | 同时进入寻货大厅，其他有货商家也能应答 |
| 认证在售 N=0 | 「发布寻货（进入寻货大厅）」 | 暂无认证商家在售，发布后如有匹配商家会收到通知 |
| 未登录 | 「登录后发起寻货」 | 登录后可向认证商家询价、发布寻货 |

- 在售商家卡标题改「**N 家认证商家真实有货**」（与分享文案同口径）；**未认证在售**归入「其他在售 · 仅供参考（未认证商家，暂不提供询价）」分段，只读不导流。
- 发布成功反馈按上述家数差异化：定向→「已定向推送给该商家」；广播 matched>0→「已通知 N 家认证商家」；=0→「已进入寻货大厅」。

> 口径不变：广播仍仅登录门槛（不加"仅认证在售才可发起"）；触达范围仍固定为"在售本轴承的认证商家"——**无需再单独发一轮定向**，一条广播即覆盖两条路径（见 4.2 触达范围）。

### 4.7 公开 / 邀请（v1.2.0）

**背景**：4.3 的"定向询价"把**受众**（只问谁）与**目的**（拿报价）混成了一个字段；同时"询价"被抬成与"寻货"平级的单据类型，与领域模型不符（价格本就是应答行的一个可选字段，选定才是终局动作）。v1.2.0 改为**两个正交轴**：

| 轴 | 取值 | 效果 |
|---|---|---|
| 曝光 | 公开 / 邀请 | 决定是否进公开大厅（`GET /api/sourcing/demands` 只列 `Visibility=Public`）；邀请单仅发布人与收件商家可见（非收件商家取详情返回 404） |
| 收件人 | 全部匹配的认证在售商家（默认）/ 指定勾选 | 决定站内信与商家侧「为你匹配」给谁；收件人快照 `InvitedMerchantIds`，空=全部匹配 |

- **无在售商家（N=0）强制公开**：邀请无人可邀，发布页邀请选项禁用（服务端同样拒绝，报"当前没有在售该型号的认证商家，无法邀请，请改为公开"）。
- **按钮文案统一「发布寻货」**（未登录「登录后发起寻货」）：N 家信息不再由按钮承载，改由按钮下方说明行与发布页「发布方式」区承载，避免文案随家数摇摆。
- **发布页交互**：发布方式二选一（公开 / 邀请）+ 说明"当前 N 家认证商家在售"；选邀请后列出**在售认证商家清单**供勾选（默认全选，可取消）；清单来自公开端点 `/api/bearings/{id}/merchants` 过滤 `isVerified`；从商家行/商家主页进入则**预勾选该家**（无 `bearingId` 清单时按预填收件人精确邀约）。
- **一致性铁律**：邀请单一定进收件商家的「为你匹配」（`GetOpenInvitedForMerchantAsync` 聚合）——**v1.3.0 起邀请还额外豁免日限频**（见 4.8），双保险确保"受邀必达"，不再出现"当天同型号 3 条推满后就彻底看不见这单"。
- **发布反馈**按收件人集合大小差异化：公开→「已通知 N 家认证商家，并进入大厅」（无匹配→「已进入寻货大厅」）；邀请→「已邀请 N 家认证商家」（无匹配→「已发布邀请」）。
- **商家端措辞**：原"定向询价"徽标统一改「邀请」；"我的寻货"/商户工作台/寻货详情对进行中的邀请单给「转公开」入口。
- **Admin 治理视图**：列表与详情透出「发布方式」（公开 / 邀请 N 家）+ 发布方身份（个人 / 商户名义），便于审核判断触达范围与责任主体。

### 4.8 邀请边界与投递保障（v1.3.0）

4.7 建立了"公开 / 邀请"两个正交轴，但**边界只在详情端点把住了一半**——应答、可见性、通知投递、聚合截断与计数维护各自留有缺口。本版逐处补齐，口径与实现见下：

| 环节 | 规则 | 理由 |
|---|---|---|
| 应答 | 邀请单**仅收件商家**可应答/更新（按发布时点快照判定，不按"当前是否仍有货"） | 详情已 404，若应答不设防，知道 id 的第三方可插队应答、混进发布人比价列表，选定即解锁电话；按快照判定则避免受邀商家事后下架被误拒 |
| 可见性 | 邀请单对**发布商户的在职成员**与**任一收件商户的在职成员**可见（不再只看当前选中商户/仅经办人本人） | 商户名义单是全店的事（与工作台"全员可见"一致）；一人多商户时通知深链携带的 `X-Merchant-Id` 未必是收件商户，只看当前商户会误 404 |
| 通知 | 邀请单**豁免** `Sourcing.NotifyMaxPerMerchantPerDay` 日限频；公开保持限频 | 受邀是发布人点名勾选（受众可控），"受邀必达"优先；公开匹配面广，需限频抑制刷屏 |
| 契约 | 发布响应 `recipientMerchantCount`（原 `notifiedMerchantCount`）；`visibility` 枚举校验；公开单携带 `invitedMerchantIds` → 400；收件人解析与"无人可邀"校验提到 NEED_POINTS 确认框之前 | 原名暗示"实际投递家数"，实际还取决于收件商户是否有在职管理员；非法枚举会产生"既不在大厅又不算邀请"的幽灵单；误用应有明确报错而非静默忽略；不能先让用户确认花积分再告知无人可邀 |
| 匹配口径 | `SourcingMatcher` 复用实体 `IsPubliclyVisible`（审核通过 且 出售中/补货中 且 未停用）与商户 `Status = Active`；「为你匹配」「需求信号」改用 `GetMatchableByMerchantAsync`；商户名义发布排除本商户 | 原匹配器与两个聚合面各写一套"在售"判定，出现"补货中商家被通知却在聚合面看不到"；自家商户无需自邀 |
| 聚合截断 | `/matched` 合并邀请与公开匹配时**邀请优先**参与 `Take(50)` | 邀请进聚合面是硬承诺，不能因公开匹配单多而被时间倒序挤出 |
| 计数维护 | 撤回应答同步递减 `SourcingDemand.ResponseCount` | 冗余列驱动"尚无人应答"推荐，残留计数会让单子在其他商家面前永久消失 |
| 候选清单 | 发布页邀请清单**全量分页拉取**（原只取首页 20 家）、失败与"确实无人在售"区分（失败给重试且不禁用）、排除自家商户 | 部分勾选时静默丢掉未展示商家与"勾选∩匹配"的精确语义不符；一次网络失败不应被误判为无货 |

**详情页与发布页（Taro）**：寻货详情加「邀请 N 家」徽章（受邀商家从通知进入即知受众），发布人且进行中时可就地「转为公开」；加载失败/无权查看给终态提示与返回入口（原静默失败致页面永远"加载中"）；型号被手动改写时清空关联轴承（防"邀的是 A 型号商家、单上写 B 型号"）。

## 五、通知（多通道 + 用户偏好）

### 5.1 多通道

- 扩 `INotificationService`：站内信（现有 `AddInAppAsync`）+ **短信/微信/邮件**兄弟方法；未配置网关的通道**只记日志不外发**。
- **同时多方式发出**：一次事件按用户偏好**扇出到全部启用的通道**。
- 触发点：认证商家收到"匹配寻货"→ 站内信**必发** + 短信（受偏好多门控）。

### 5.2 通知设置（用户自选）

- 位置：设置页 → 子页「通知设置」。
- 可勾选：**站内信**（必开、不可关，消息中心兜底）；**短信**（**仅短信网关就绪时显示**，避免"勾了收不到"）；**微信通知**、**邮件通知** 可勾。
- 后端：写复用 `UpdateUserPreferenceCommand`；**补** `GetUserPreferenceQuery` + `GET/PUT /api/notifications/preferences` + BFF 代理。

### 5.3 通知分发矩阵（谁收 / 在哪设）

统一规则：**通知一律投递给个人账号，渠道接收设置也一律在个人账号级**（我的 → 设置 → 通知设置）；商户不设统一接收开关。

| 触发 | 通知谁 | 落地账号 |
|---|---|---|
| 发布寻货（公开） | 匹配的有货（在售本轴承）认证商家在职管理员 | 各商户管理员自己的账号 |
| 发布寻货（邀请） | 勾选的（空=全部匹配）认证在售商家在职管理员 | 各自账号 |
| 转为公开 | **不发新通知**（收件人集合不变，仅曝光面放开进大厅） | — |
| 商家应答（**商户名义发布**） | 发布商户**全部在职成员** | 各成员自己的账号 |
| 商家应答（**个人名义发布**） | 发布人本人 | 发布人账号 |
| 发布人选定 | 被选商户管理员 + 其余应答商户管理员 | 各自账号 |
| 发布人取消 | 已应答商户管理员 | 各自账号 |
| 平台下架 | 发布人本人 | 发布人账号 |

> 站内信为兜底通道**恒发不可关**；短信/微信/邮件在**各接收人自己**的偏好 + 网关就绪上双重门控。故"全店在职成员"意味着全店成员都会收到站内信，外部渠道按各自设置。
> 本节仅为寻货相关分发；**完整通知体系（模型/渠道/设置/清单/深链）见《18-通知消息体系设计 v1.1.0》**。

## 六、分享（真实货源查询结果）

### 6.1 定位

**主场景**：查到某轴承 → 得出"**谁家真实有货**"（认证商家在售清单）→ 分享到微信群 / 发给询价人 → **引流回平台**发起寻货或后续交易。

### 6.2 入口

- **主**：轴承详情「在售认证商家」区「分享货源」；
- **次**：商家主页「分享」（给该商家曝光引流）。
- 搜索结果页**不做**分享（列表缺上下文，价值低）。

### 6.3 落地与内容

- 复用轴承详情，带 **`?view=supply`** 进"货源视角"：**认证货源主位**，轴承参数折叠并标源。
- 卡片文案：`{型号} {品牌} · {N}家认证商家真实有货，来平台比价询价`。
- 游客打开：看在售认证商家 → 「登录后发起询价」→ 转化闭环。

### 6.4 三端策略

| 端 | 方式 |
|---|---|
| 微信/抖音小程序 | `useShareAppMessage`（原生分享菜单） |
| H5 | 优先 `navigator.share`，否则**复制链接**兜底（可选微信 JSSDK 增强） |
| RN | `Share.share()` |

- 原则：只分享**可信/认证**数据；仅供参考页分享时文案明示「仅供参考」。

## 七、端到端漏斗

```
游客：搜索→轴承详情（在售=认证商家名单 + 仅供参考灰标）→商家主页「电话：登录后邀请报价」
        ↑                                                          │
        └── 分享货源到微信群/微信 ← 「{N}家认证商家有货」卡片 ←────┘
─────────────── 注册分水岭 ───────────────
注册：①发布寻货-邀请（勾选/预勾选认证在售商家）→收件商家通知→应答→选定→互给电话
      ②发布寻货-公开（预填 bearingId）→匹配认证商家通知 + 进公开大厅→应答→选定→互给电话
        （邀请无人应答可一键「转为公开」，免去取消重建的额度/积分损耗）
认证商家：工作台「为你匹配的寻货」（公开匹配 + 邀请给我）→应答   ← 入驻价值；通知按偏好多渠道
互联网数据：只读 + 灰标，不导流、不给号
```

## 八、边界

- 开源信息撮合**终止于「互给电话」**（选定应答 / 接受定向询价那一刻）；此后线下成交由双方自行完成，不在本设计范围内。
- 预留 `MatchCompletedEvent`（撮合达成，即电话互给）作为该终止点的衔接钩子；本设计不含其消费实现。
