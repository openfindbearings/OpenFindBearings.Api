# 替代品治理设计 v2.0.1

> 版本：v2.0.1 | 日期：2026-10-18 | 上一版：v2.0.0 | 状态：已实施（字典化重构 + 独立权限键）
> 取代 v1.0.0（"商家报候选 + 平台审核"模型）

## 一、定位：替代关系是主数据（字典）

轴承"替代关系"是**跨品牌的等效知识**——同样的内径/外径/宽度/精度可以用另一个品牌型号顶上。这一知识与"轴承、品牌、类型"同级，属于**平台主数据（字典）**：

- **由平台建、由平台维护、由平台背书**——可信度来自平台，而非商家的自述；
- 商家只对"我有没有货、能不能供"作答（**可供性**），不对"两者是否等效"下结论；
- 采购方/技术方对"这批工况能不能用"负最终责任（**工况适配**）。

一句话：**平台提供标准化的等效知识，商家提供货源，采购方确认工况。**

### 1.1 为什么撤销"商家报候选 + 平台审核"（v1.0.0 模型）

| 问题 | 说明 |
|---|---|
| 归域不当 | 替代关系是跨品牌等效知识，属主数据；把"候选提交权"交给商家，等于让经营者参与字典编纂 |
| 利益冲突 | 商家有动机把 `functional`（功能近似）说成 `exact`（完全等效），审核拦不全，字典可信度会被稀释 |
| 重复设卡 | 互联网抓取候选的审核**已经发生在数据管线侧**（Sync staging 的 `IsManuallyApproved`），推到 API 的本来就是已确认行；API 侧再挂一套"候选 → 审核"是第二道关卡 |
| 通道重复 | 商家/用户表达"这条替代关系不对 / 缺一条"的需求，由既有**纠错**通道承载（结构化选字段 + 积分激励 + 结果通知），闭环更完整、更轻 |

因此 v2.0.0 **移除** `InterchangeReviewStatus` 状态机与商家候选流，保留三级类型标签与责任提示。

## 二、三级替代类型（`InterchangeType`，保留不变）

| 值 | 口径 | 自动推荐 |
|---|---|---|
| `exact` | 标准等效替代（同尺寸/精度/结构，可直接替换） | 是 |
| `conditional` | 条件替代（精度/密封/游隙/品牌系列差异，需技术确认） | 是（带"需评估"标签） |
| `functional` | 仅供参考（类似用途，不构成平台推荐） | **否**（仅作人工咨询入口） |

前端统一以 `typeLabel`（标准等效替代 / 条件替代（需评估） / 仅供参考）呈现，并附责任提示。

## 三、数据来源与维护通道

| 通道 | 主体 | 记录方式 | 生效 |
|---|---|---|---|
| 权威网站抓取 | 平台（数据管线） | `DataSource.SourceType=Internet`，候选经 Sync staging 审核（`IsManuallyApproved`）后入库 | 进 API 即生效 |
| 平台人工维护 | 平台管理员 | `DataSource.SourceType=Manual`（Admin「替代品管理」页新建/编辑/删除） | 进 API 即生效 |
| 纠错反馈 | 商家 / 用户 | 对轴承提交可纠错字段 `interchange`（自由文本描述"哪条不对 / 应补哪条"） | **不自动应用**：平台核实后在「替代品管理」页落地该关系，再审批该纠错单 |

> 纠错字段 `interchange` 是唯一例外——它无法确定性解析为"源 → 目标"一对轴承，故审批动作只代表"该报告已核实处理"，实际关系由平台维护动作写入。

## 四、生效与可见规则

- **无审核位**：`BearingInterchange` 不再有 `ReviewStatus`/`ReviewComment`/`ProposedByMerchantId`；进 API 即生效。
- **公域查询**：`GET /api/bearings/{id:guid}/interchanges` 返回该轴承全部生效关系，按 **"源 ∪ 双向反向"** 合并——该轴承作为源（正向），或作为目标且 `IsBidirectional=true`（反向）均返回，使双向标记真正生效。仍返回含 `typeLabel` 的富 DTO。
- **自动推荐口径**：`IsAutoRecommendable` = 未删除 且 非 `functional`。
- **去重**：同一（源，目标）组合唯一；平台新建时查重后拒绝重复。

## 五、实现清单（v2.0.0）

**Domain**
- `BearingInterchange`：删除 `ReviewStatus`/`ReviewComment`/`ProposedByMerchantId` 与 `IsPubliclyVisible`；保留 `UpdateDetails`，`IsAutoRecommendable` 简化为"未删除且非 `functional`"。
- 仓储 `IBearingInterchangeRepository`：`GetForBearingAsync`（源 ∪ 双向反向，原 `GetApprovedForBearingAsync` 更名）、`GetPagedAsync`（关键字 + 创建时间 + 来源，**无审核状态参数**）、`GetBySourceBearingAsync`、`ExistsAsync`、`Add/AddRange/Update/Delete(物理)`、`GetTotalCountAsync`、`GetCountSinceBySourceAsync`；删除无调用方的 `GetByTargetBearingAsync`、`GetPendingAsync`、`GetByProposerAsync`、`GetPendingCountAsync`。
- 枚举 `InterchangeReviewStatus` 整体删除。
- 迁移 `RemoveInterchangeReview`：先物理清除历史"待审核/已驳回"行（从未生效、字典化后无出口），再删三列与 `IX_BearingInterchanges_ReviewStatus`。

**Application**
- 命令：`CreateInterchange` / `UpdateInterchange` / `DeleteInterchange`（平台）。删除 `SubmitInterchange` / `ApproveInterchange` / `RejectInterchange`。
- 查询：`GetInterchanges`（平台列表，去掉 `ReviewStatus` 过滤）、公域 `GetBearingInterchanges`（返回 `BearingInterchangeDto`）。删除 `GetPendingInterchanges` / `GetMyInterchanges`。
- DTO：`BearingInterchangeDto`（公域条目）、`InterchangeAdminDto`（管理行，删审核状态/驳回理由/提出商户字段）。
- 纠错：`GetCorrectableFieldsQueryHandler` 的轴承字段清单新增 `interchange`（当前值恒空）；`ApproveCorrectionCommandHandler` 对其显式 `break`（不自动应用）。

**API 端点**
- 平台（读 `interchange.view` / 写 `interchange.manage`）：`GET /api/admin/interchanges`、`POST /api/admin/interchanges`、`PUT /api/admin/interchanges/{id:guid}`、`DELETE /api/admin/interchanges/{id:guid}`。
  - 权限归属：替代关系已是与轴承/品牌/型号同级的主数据（字典），故 v2.0.1 起使用独立权限键，不再借用 `merchant.verify`（认证审核语义）。`interchange.view`（查看替代关系）用于列表与页面进入，`interchange.manage`（维护替代关系）用于新建/编辑/删除；目录键数 32→34，迁移 `AddInterchangePermissions`。
- 公域：`GET /api/bearings/{id:guid}/interchanges`（全部生效，源 ∪ 双向反向）。
- 仪表盘：`GET /api/admin/dashboard/stats` 的 `interchanges` 块保留 `totalCount`/`internetAdded`/`manualAdded`，删除 `pendingCount`。

**Admin**
- 「替代品管理」页：列表 / 关键字 + 创建时间 + 来源筛选 / 新建（选源·目标型号）/ 编辑 / 删除；页面明确"平台维护 + 纠错核实"口径。
- 删除「替代品审核」页与相关代理；保留轴承列表"替代品"查看弹窗。

**Taro**
- 轴承详情「替代品」区：三级标签 + 尺寸 + 责任提示（副标题改"替代关系由平台维护"）；区块内新增"替代关系有误或缺失？点此报告"入口（打开 `CorrectionSheet`）。
- 删除商家"替代提交"页与入口。

**BFF**
- 公域替代 DTO 透传；删除商家替代提交/我的提交代理。

## 六、责任边界提示

- 展示层统一提示：替代关系由平台维护；"需评估/仅供参考"档请人工确认工况适配。
- `functional`（仅供参考）不进自动推荐。
- 平台对"等效性"背书，商家对"可供性"负责，采购方对"工况适配"负责。

## 七、后续（预留）

- 替代关系的证据化与失败反馈（品牌授权、样本参数、图纸、历史成交；替代失败反馈修正置信度）依赖后续交易域的数据积累，届时另行设计；本版不引入相关字段。
