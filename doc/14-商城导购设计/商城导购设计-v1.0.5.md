> 版本：v1.0.5 | 日期：2026-10-27 | 上一版：v1.0.4
> 新增：**商家商品实拍图**——商家在商品管理维护自己的 1-3 张图，商城卡片与商品详情优先展示商家图，无图回退型号主图。

## 变更日志

### v1.0.5 (2026-10-27)

- **商家商品实拍图上线**：`MerchantBearings.ImageUrls`（`text[]`，最多 3 张，首个为首图），商家在商品管理上传/删除/换首图；商品已通过审核时改图自动重新送审，通过前商城不可见。
- **展示口径**：`MerchantBearingDto.coverImageUrl` = 商家首图，无商家图回退 `Bearing.Image3DUrl → Image2DUrl`；商城卡片（`ProductCard`）统一用它。
- **型号主图不动**：首页搜索、型号详情顶部、分享卡片仍用平台主图（认型号）；商家图只影响商城/店铺/在售商家行（认货）。
- **后端**：`GetMallFeed` 不做任何图片维度的额外过滤，只透出 `merchantImageUrls`/`coverImageUrl`；无迁移以外的查询变化。

### v1.0.4 (2026-10-25)

- **移除客户端开关**：`GET /api/mall/feed` 不再接受 `verifiedOnly` 查询参数，Handler 固定 `VerifiedOnly = true`。理由：货源口径是产品定义（商城只出可联系、可成交的货源），不应被查询串绕过；运营排查改走后台数据页。
- 上一版遗留的"运营排查可传 `verifiedOnly=false` 看全量"说法作废，`MallFeedSearchParams.VerifiedOnly` 仅作仓储内部参数保留。

### v1.0.3 (2026-10-25)

- **货源口径收敛为"可成交货源"**：`GET /api/mall/feed` 新增商家维度过滤——商家必须 `Status=Active` 且未停用，且只出 `IsVerified=true`（认证商家）。
- 修复缺陷：原实现只过滤商品（未删 + 审核通过 + 出售中），**完全没有商家维度过滤**，导致未认证商家、爬虫商家（创建即 `Pending`、从不认证）乃至已停用/已关店商家的商品都会出现在商城。
- 与详情页口径对齐：详情页对未认证/互联网来源只列在"参考在售"段并注明不提供联系与报价；商城作为成交型入口不再平铺这类数据，避免"看着有货、点进去联系不上"。
- 不变：商品侧过滤（`IsActive` + `ReviewStatus=Approved` + `SaleState=OnSale`）、排序、分页、响应结构、匿名可访问均不变；补货中与已下架仍不进商城。

### v1.0.2 (2026-10-23)

- 同一陷阱的 API 侧全量收敛：`/api/mall/feed` 的 `Page`/`PageSize`、以及 `/api/bearings/search`（`SearchBearingsQuery`）、`/api/merchants/search`（`SearchMerchantsQuery`）的同名字段一并改为可空，Handler 侧兜底第 1 页、20 条。
- 原因：这三个端点用 `[AsParameters]` 绑定查询对象，非空值类型属性会被判为必填；此前不带分页参数直接返回 400 空体（BFF 与前端都带参所以未暴露，第三方直调或调试时必现）。
- 契约不变：请求参数、响应结构与默认页大小均未变，仅缺省参数生效。

### v1.0.1 (2026-10-23)

- **修复货源流全站为空**：`GET /api/mall/feed` 自上线起恒返回 400 空响应，BFF 无法解析即兜底为空列表，商城页一直显示"暂无货源"，与数据无关。
- 根因：`GetMallFeedQuery.IsAuthenticated` 声明为 `bool`，最小 API 的 `[AsParameters]` 绑定会把**非空值类型属性视为必填查询参数**，而 BFF 转发时不带 `isAuthenticated`（该值本应由端点用登录态覆盖），绑定阶段直接 400 且响应体为空。
- 改法：`IsAuthenticated` 改为 `bool?`（不再参与必填校验），Handler 侧按 `?? false` 兜底匿名；端点依旧以登录态覆盖，客户端传入值无效、无越权面。
- 同类问题（BFF 侧）：`/mobile/*` 的 `[AsParameters]` 分页 DTO 的分页字段同样被判必填，调用方不带 `page`/`pageSize` 时返回 400 空体；本次一并改为可空并在调用处兜底 1/20 页（涉及轴承搜索与在售商家、商家搜索与在售商品、我的收藏/关注/浏览历史/纠错）。
- 契约不变：请求参数与响应结构均未改动，仅让缺省参数真正按默认值生效。

## 一、定位与信息架构

商城 Tab = **供给侧货源导购**，与既有 Tab 互补：

| Tab | 角色 | 侧 |
|---|---|---|
| 首页 | 工具查询（按型号查） | 工具 |
| 发现 | 求购/寻货 | 需求侧 |
| **商城** | **货源/商品导购**（本版） | 供给侧 |
| 入驻/商家 | 商户工作台 | 经营 |
| 我的 | 个人中心 | 个人 |

- 商品行 = 一条"某商家在某轴承上的在售货源"（MerchantBearing 在售条目）。
- 卡片主体点击 → 货源详情（复用 `pages/home/bearingDetail`，看该型号全部商家与报价）。
- 卡片商家行点击 → 店铺页（复用 `pages/merchant/merchantDetail`）。
- 不新建商品详情页：轴承详情页"规格 + 在售商家列表"本就是更贴合 B2B 的货源详情形态。

### 1.1 货源口径（v1.0.4 收敛）

商城只出**能联系、能报价**的货源，行级条件为：

1. 商品未删（`IsActive`）
2. 商品审核通过（`ReviewStatus=Approved`）——商家新建落"仓库中"，点"上架"才提交审核，后台批准后才进商城
3. 商品出售中（`SaleState=OnSale`）——补货中、已下架不进商城
4. 商家有效（`Status=Active` 且 `IsActive`）——停用、关店商家不出
5. 商家已认证（`IsVerified`）——固定强制，无查询参数可关闭

未认证商家与互联网来源商家（爬虫数据，无账号、联系方式受 PIPL 限制不可暴露）只在型号详情页的"参考在售"段出现，且明确标注不提供联系与报价。两处口径的一致性由本条约束保证。

## 三、筛选能力

商城主页与搜索页共用同一套筛选维度（对齐既有结果页范式）：

- 排序：综合（创建时间）/ 价格 / 热度，点击已选字段切换升降序。
- 筛选：品牌、类型（横向 chips）、尺寸范围（内径/外径/宽度），已选以 chips 回显、可清除。
- 品牌/类型字典来自 `/mobile/home` 聚合（`brands` / `bearingTypes`）。

> 后续可抽共享 `FilterBar` 组件，令搜索页与商城页、乃至交易前台复用同一份筛选 UI。

## 四、扩展点：商品卡操作位

商品卡操作位 `ProProductAction` 走扩展点（`src/ext/pro`）：

- 开源版渲染"**联系商家**"（落到货源详情，信息撮合闭环）。
- fork/自用版可在 `ext/pro` 替换本扩展点的动作实现，**共享商品卡不变**。

约定：共享文件只 `import` 扩展点路径；开源版提供签名对齐的默认实现，替换方须保持 props 签名一致。这是"共享骨架、行为差异收敛在扩展点"的落地方式，避免 fork 时回改共享源码。

---

## 五、权益兑换归属

原商城 Tab 的积分权益橱窗（置顶卡/挂礼 + 我的兑换）迁至 `pages/my/redeem`（"我的"线）：

- 商城页顶部留小入口"轴承币权益兑换"。
- 收支明细页（`pages/my/points`）新增"权益兑换"入口。
- 理由：商城 = 货源导购前台；积分兑换 = 虚拟账本权益，两者心智与数据模型不同，分离避免互相污染。
